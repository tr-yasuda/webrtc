# STUN Binding サービス

単独 STUN サーバーとしての Binding の提供と要求・応答を定める。メッセージの解析・検証には [共用メッセージ処理](messages.md)を適用する。

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
DTLS の条件は [共通 DTLS 仕様](../dtls/association.md)に従う。
管理状態の件数・総量・寿命は、[共通の資源管理](../platform/resources.md#資源管理)に従う。

## 機能と公開条件

STUN サーバーは、RFC 8489 の Binding に対応する。
要求元の IP アドレスとポートを応答し、端末が接続候補を取得できるようにする。

IPv4・IPv6 に対応する。
UDP、TCP、TLS-over-TCP、DTLS-over-UDP で要求を受け付ける。
既定の待受ポートは UDP・TCP が 3478、TLS-over-TCP・DTLS-over-UDP が 5349 とする。
待受ポートは変更可能とする。

接続先をホスト名とポートで公開し、Client SDK へ設定できるようにする。

単独の STUN サーバーによるアドレス確認には認証を要求しない。
不正な要求の扱いと処理量の制限は、本書のセキュリティの節と [共用メッセージ処理](messages.md)で定める。

ICE 接続確認に使う認証付き STUN 処理は、ICE / WebRTC Transport の仕様で定める。
TURN の認証と中継は、TURN サーバーの仕様で定める。

## 自作範囲・既存実装の利用

STUN のプロトコル処理は Rust で実装する。

Binding では、要求元アドレスを取得し、成功応答・エラー応答を生成する処理を自作する。
各トランスポート上のメッセージ境界の判定と要求処理も、自作範囲に含める。

これらの処理は自作し、完成済みの STUN 実装には委ねない。

ソケット入出力、非同期実行、タイマー、暗号学的な乱数生成には、Rust の標準ライブラリや汎用ライブラリを利用できる。
TLS / DTLS 自体には既存実装を利用する。
DTLS の利用条件は、[共通 DTLS 仕様](../dtls/association.md)で定める。

## セキュリティ

単独の Binding によるアドレス確認には、利用者認証を要求しない。
ICE と TURN で必要な認証は、それぞれの用途で適用する。
単独の Binding を受け付ける設定によって、ICE・TURN の認証を省略しない。

STUN サーバーは、成功・エラーとも、要求を受信したトランスポートで返す。TCP / TLS-over-TCP では、受信した接続をそのまま使用する。

UDP / DTLS-over-UDP では、複数のアドレスで待ち受ける場合も要求の送信元と受信先を特定する。応答先の IP アドレス・ポートを要求の送信元に、応答元の IP アドレス・ポートを要求の受信先に合わせる。指定された応答元を使用できない場合は、代替アドレスから応答しない。DTLS-over-UDP では、要求を受信した DTLS Association 上で応答を保護し、別の UDP ソケットから平文で返す経路も設けない。
[RFC 8489 §6.3.1.2](https://www.rfc-editor.org/rfc/rfc8489.html#section-6.3.1.2)に従う。

要求を処理して応答する際は、送信元別とサーバー全体の両方で、要求処理数と応答帯域の制限を適用する。要求が並行しても、同じ処理枠や送信予算を重複して取得せず、エラー応答も送信量に計上する。制限によって処理できない要求は破棄し、制限超過を知らせる追加応答は生成しない。

レート制限管理表には、件数・総メモリ量・TTL と上限到達時の扱いについて [共通の資源管理](../platform/resources.md#資源管理)を適用する。管理表の項目を削除・再登録しても、サーバー全体に適用中の制限は引き続き有効とする。

反射攻撃への対策として、ネットワーク側の送信元アドレス検証・フィルタリングを運用条件に含める。
アプリケーション側の処理量・応答帯域の制限と併用する。
[RFC 8489 §16.1.2](https://www.rfc-editor.org/rfc/rfc8489.html#section-16.1.2)に従う。

TCP / TLS-over-TCP では、接続数、処理待ち要求、受信・送信バッファに上限を設ける。
不完全なメッセージを保持する時間にも上限を設け、少量の追加受信だけで保持期限を無期限に延長しない。

TLS / DTLS 接続では、サーバーが接続先に対応する適切な証明書を提示する。
証明書の信頼・有効性・接続先名は、接続するクライアント側が検証する。
この検証は、WebRTC の SDP フィンガープリント照合とは別に扱う。

DTLS Cookie、到達性確認、ハンドシェイク、断片再構成、再送、送信予算は、[共通 DTLS 仕様](../dtls/association.md)に従う。
DTLS 接続の確立を、利用者認証や TURN の利用許可として扱わない。

## 受け入れ条件

IPv4・IPv6 と、UDP・TCP・TLS-over-TCP・DTLS-over-UDP の各組み合わせで、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| Binding の成功応答 | サーバーが観測した要求元の IP アドレス・ポートを応答する。応答の Transaction ID が要求と一致する |
| 待受設定 | 既定ポートと変更後のポートで接続できる。公開した接続先と実際の待受設定が一致する |
| 認証の分離 | 単独の Binding は利用者認証なしで処理できる。その設定によって、ICE・TURN の認証を省略しない |
| UDP の応答アドレス | 成功・エラーの両応答で、応答先を要求の送信元、応答元を要求の受信先に一致させる。複数アドレスで待ち受ける場合も維持する |
| 応答元を使用できない場合 | 別のアドレスから代わりに応答しない |
| DTLS による応答 | 要求を受信した DTLS Association を通じて、保護された成功・エラー応答を返す。別の DTLS Association への混入や、平文の UDP 応答への切り替えが起きない |
| Request の再送 | UDP / DTLS-over-UDP で、同じ Transaction ID の同一トランザクションの要求を再送し、元の応答だけ、再送への応答だけ、両方を受信する場合について、[RFC 8489 §6.3.1](https://www.rfc-editor.org/rfc/rfc8489.html#section-6.3.1)に従ったクライアント・サーバーの状態と応答の整合性を維持する。再送によって不要な資源確保を繰り返さず、再送要求の処理と応答にも処理量・応答帯域の制限を適用する |
| TCP / TLS のメッセージ境界 | 分割受信・複数メッセージの連続受信でも境界を正しく判定し、要求を受信した同じ接続で応答する。TLS では応答も保護される |
| 処理量・応答帯域 | 送信元別・サーバー全体の制限を守る。エラー応答も計上し、上限付近の並列処理でも処理枠・送信予算を重複取得しない |
| 制限超過時 | 処理できない要求を破棄し、制限超過を知らせる追加応答を生成しない |
| レート制限管理表 | 件数・総メモリ量・TTL の条件を守る。制限期間中の早期削除や、削除・再登録による全体制限のリセットが起きない。空きがなければ、登録を必要とする要求を処理しない |
| 接続・バッファの上限 | 大量の接続、不完全な要求、低速送信、読み取りの遅い相手でも、接続数・処理待ち要求・バッファの上限を超えない。不完全なメッセージの保持期限を、少量の追加受信だけで無期限に延長しない |
| 資源の確保・解放 | 並列要求、途中失敗、完了通知の消失・重複・遅延、管理記録の喪失について、共通の資源管理条件を満たす。結果不明の枠を安易に再利用せず、安全な照合・回収ができる |
| 証明書とクライアント検証 | サーバーが接続先に対応する証明書を提示する。検証用クライアントは、信頼・有効性・接続先名の検証に失敗した接続を拒否する |
| 共通 DTLS 条件 | 実際の STUN 組み込み構成で、共通 DTLS 仕様の受け入れ条件を満たす。到達性確認や接続確立だけで、ICE・TURN の利用認証を満たしたとは扱わない |

ネットワーク側の送信元アドレス検証・フィルタリングについて、適用箇所と検証可能な範囲を記録する。
アプリケーション側のレート制限だけでは、送信元偽装の防止を保証しない。

ブラウザーとの相互接続は、対象ブラウザーが実際に利用するトランスポートで確認する。
ブラウザーで利用できない組み合わせは、対応する検証用クライアントで確認し、ブラウザーで確認済みの条件と区別する。

試験結果には、サーバーとクライアントのバージョン、アドレスファミリー、トランスポート、待受設定、TLS / DTLS の条件、資源上限、レート制限、通信条件と観測結果を記録する。
証明書の秘密鍵や認証情報は記録しない。
