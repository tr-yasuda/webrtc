# WebRTC の暗号化通信の確立・維持

WebRTC 接続への DTLS の組み込みと、SRTP/SRTCP の確立・保護・鍵状態・復旧を定める。送信可能な経路と送信同意は [ICE 仕様](ice.md)に従う。

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
DTLS の条件は [共通 DTLS 仕様](../dtls/association.md)に従う。
管理状態の件数・総量・寿命は、[共通の資源管理](../platform/resources.md#資源管理)に従う。

## 暗号化通信の確立・維持

参加端末と SFU 間の音声・映像は DTLS-SRTP による SRTP/SRTCP、DataChannel は DTLS によって保護する。
暗号化していない RTP/RTCP や、保護されていないアプリケーションデータへ切り替えない。

DTLS は 1.2 と 1.3 に対応し、バージョン交渉、暗号条件、到達性確認、ハンドシェイク、再送、鍵の使用上限は、[共通 DTLS 仕様](../dtls/association.md)に従う。

### DTLS の相手認証と SRTP/SRTCP の鍵確立

WebRTC Transport は、Signaling で受け取った対象接続のフィンガープリントについて、ハッシュ方式と形式が許可条件を満たすことを確認し、DTLS 証明書と照合する。フィンガープリントが未取得または照合中であれば、DTLS ハンドシェイクが成立していても、保護対象のアプリケーションデータの送受信は開始しない。不一致なら対象接続を拒否し、期待するフィンガープリントを提示された証明書に合わせて自動的に置き換えない。相手を信頼する条件と正当な更新条件は、[Signaling](../signaling/session.md#接続情報の交換)に従う。

音声・映像を保護するには、DTLS-SRTP の `use_srtp` で Protection Profile を交渉し、DTLS Exporter で鍵素材を導出する。鍵素材の長さ・分割・導出は採用するプロファイルに合わせ、送信・受信ごとに DTLS のロールに対応する鍵を使用する。
[RFC 5764 §4](https://www.rfc-editor.org/rfc/rfc5764.html#section-4)に従う。

許可する SRTP Protection Profile は、次を基準とする。

| プロファイル | 方針 |
|---|---|
| `SRTP_AES128_CM_HMAC_SHA1_80` | WebRTC の相互接続用に対応する |
| `SRTP_AEAD_AES_128_GCM` | 対応し、AEAD のプロファイルを優先する |
| `SRTP_AEAD_AES_256_GCM` | AES-GCM SRTP の対応範囲に含める |

この基準は [RFC 8827 §6.5](https://www.rfc-editor.org/rfc/rfc8827.html#section-6.5)と [RFC 7714 §12](https://www.rfc-editor.org/rfc/rfc7714.html#section-12)を踏まえたプラットフォーム方針とする。
未許可のプロファイル、NULL 暗号、SDP による平文の鍵配送は使用しない。
共通の許可プロファイルがなければ、接続を失敗として扱う。
WebRTC Transport では、SRTP Master Key Identifier（MKI）を使用しない。

### 送受信時の SRTP/SRTCP の暗号状態

SRTP のパケットインデックス（Index）は、RTP シーケンス番号の周回を管理する ROC（Rollover Counter）と、RTP シーケンス番号（SEQ）で構成する。SRTCP では固有のパケットインデックスを使う。WebRTC Transport は、DTLS Association、方向、SSRC など、プロトコルが要求する範囲ごとに暗号状態を保持し、その状態にパケット番号、ROC、SRTCP パケットインデックス、リプレイ判定状態を対応付ける。

SRTP の送信時は、同じ暗号鍵で (ROC, SEQ, SSRC) の組を再利用しない。マスター鍵を共有する範囲全体で、SSRC の割り当てと送信パケットインデックスを管理して IV の一意性を確保する。SSRC の変更・再利用、SFU による転送・ヘッダーの書き換え・送信ストリームの切り替えでも、SSRC の衝突やパケットインデックスの再利用を暗号化前に防ぐ。
[RFC 7714 §8.4](https://www.rfc-editor.org/rfc/rfc7714.html#section-8.4)に従う。

受信側は、正当な順序逆転を処理しつつ、認証に失敗したパケットで確定済みの受信状態を更新しない。SRTP/SRTCP の認証が成功した内容だけを後続のメディア処理に渡す。E2EE が有効な場合も、SRTP/SRTCP の認証とリプレイ対策を適用する。

### 鍵の使用上限と再確立

SRTP/SRTCP の鍵には、暗号方式・プロファイルごとの上限を適用する。パケット数、暗号化量、パケットインデックスの使用範囲など、適用する上限と計数範囲を明示し、同じ鍵を共有する複数のストリームがある場合は、上限の判定に必要な合計量も計上する。

新しい鍵が必要になったら、準備・切り替えにかかる時間と通信損失を考慮し、上限に達する前に接続再確立を始める。再確立が間に合わなければ、上限に達した鍵による送信を停止する。DTLS 1.2 を使用している場合は、再ネゴシエーションを行わず、正当な Offer / Answer 交渉を経て新しい DTLS Association を確立する。
[RFC 8827 §6.5](https://www.rfc-editor.org/rfc/rfc8827.html#section-6.5)に従う。

DTLS レコードの鍵と SRTP/SRTCP の鍵は使用量を別々に計上する。DTLS 1.3 の KeyUpdate では DTLS レコードの鍵を更新するため、SRTP/SRTCP の鍵を更新したり、その使用量を初期化したりする条件にはならない。

ICE restart、経路変更、Signaling の再接続だけでは、同じ鍵の送信パケットインデックスや使用量を初期化しない。暗号状態を失った場合は、過去の Nonce の再利用や暗号文の再受け入れを防げることを確認する。保証できなければ、対象の通信を停止して新しい鍵を確立する。鍵更新時のパケットインデックスは、採用するプロファイルの条件に従って扱う。

### SFU 移行と E2EE との連携

SFU 移行時は、新旧の WebRTC Transport と暗号状態を別々に管理し、新しい接続でも相手を認証して鍵を確立する。遅延受信に備えて旧状態を保持する場合は、保持期間と資源上限を適用し、不要になった鍵と状態を解放する。

SFU は参加端末との WebRTC Transport の鍵を保持する。
一方、SFrame や DataChannel 本文の E2EE 復号鍵は保持しない。
WebRTC Transport の復号後も E2EE の本文は暗号化されたまま転送し、その鍵状態の継続・更新は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## 自作範囲・既存実装の利用

ICE / WebRTC Transport のプロトコル処理は Rust で実装する。
Rust の実行方式は Wasm、Native Addon、独立 Worker を選択肢として残し、後続の技術選定で決定する。
Rust で実装しても、独立プロセスでの実行は必須としない。

| 自作する部分 | 内容 |
|---|---|
| 通信の振り分け | 同じ受信経路で扱う STUN、DTLS、SRTP/SRTCP の識別と、対象接続への対応付け |
| DTLS の組み込み | 対象接続との対応、フィンガープリント検証の適用、交渉結果の確認、資源制限と接続状態の連携 |
| SRTP/SRTCP | パケットの読み書き、保護・検証に必要な入力の組み立て、SSRC・パケットインデックス・ROC・リプレイ判定状態の管理 |
| 鍵状態の管理 | 方向・接続・プロファイルとの対応、IV の一意性、使用上限、鍵の切り替えと旧状態の解放 |
| 資源管理 | ICE 候補、ソケット、トランザクション、タイマー、バッファ、暗号状態の予約・計上・解放 |

これらの中核処理は自作し、完成済みの ICE / WebRTC スタックや SRTP/SRTCP のプロトコル実装には委ねない。

DTLS の暗号処理、レコード処理、ハンドシェイク、Transcript、ACK、再送、Exporter には既存実装を利用する。
利用条件は、[共通 DTLS 仕様](../dtls/association.md#既存実装の利用条件)に従う。

AES、AEAD、ハッシュ、HMAC、鍵導出、署名、暗号学的な乱数生成には既存の暗号実装を利用する。
暗号アルゴリズムそのものを独自実装しない。
SRTP/SRTCP では、プロファイルに従う入力・Nonce・認証対象の組み立てと、結果に基づく状態更新を、自作するプロトコル処理が担う。

ソケット入出力、非同期実行、タイマー、バッファ管理、形式の読み書きには、汎用ライブラリを利用できる。
形式の読み書きに利用する範囲は、バイト列や数値の入出力など、中核プロトコルの自作方針と矛盾しない補助処理に限定する。
ICE や SRTP/SRTCP の解析・検証・状態管理を、完成済みのプロトコル実装へ委ねない。
既存ライブラリの利用によって、接続との対応確認やプロトコル上の検証を省略しない。

ブラウザー側は、Browser SDK がブラウザーの WebRTC API を利用する。
サーバー側の SCTP / DataChannel と SFU の転送処理は、それぞれのコンポーネントで実装し、WebRTC Transport に重複実装しない。

既存実装の内部状態・バッファ・タイマーも、全体の資源管理に含める。
ライブラリ自身の制限または組み込み側の制御によって、本仕様の上限を保証する。

採用する実装、バージョン、設定、実行方式を記録する。
実際の組み込み構成で、相互接続性、暗号状態の管理、資源上限、障害時の動作を確認する。
セキュリティ修正を追跡し、更新できる構成とする。

実装と検証には、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)を適用する。
WebRTC Transport 固有の検証対象と確認する結果は、「受け入れ条件」で定める。

## セキュリティ

WebRTC Transport の利用には、C-Plane が認可した参加端末・接続・操作との対応を必要とする。
ICE の認証、DTLS の相手認証、SRTP/SRTCP の認証に成功したことだけで、参加・発行・購読・データ送信の権限を取得したとは扱わない。

権限の失効時と、必要な権限情報を確認できない場合の停止条件は、[Signaling の再接続](../signaling/session.md#再接続)に従う。
Signaling が切断している間も適用し、対象の通信を無期限に継続しない。

受信パケットは、形式に基づくプロトコルの識別と、対象接続への対応確認、認証、状態遷移の検証を分けて処理する。
先頭バイトや送信元アドレスの一致だけで、検証済みの通信として扱わない。

STUN、DTLS、SRTP/SRTCP の振り分けでは、多重化の規定に従う。
TURN 経由では、外側の TURN メッセージと、取り出した通信内容を区別する。
不正な長さや未対応の形式を、別のプロトコルとして無条件に処理し直さない。
[RFC 7983 とその更新仕様](https://www.rfc-editor.org/rfc/rfc9443.html)を踏まえて適用する。

DTLS の到達性確認・ハンドシェイク・断片再構成・再送・送信予算は、[共通 DTLS 仕様](../dtls/association.md)に従う。
ICE による到達性確認を DTLS Cookie 交換の省略に利用する場合も、確認済みの相手・経路との対応を検証する。

DTLS の相手認証、暗号プロファイル、MKI の不使用、SRTP/SRTCP の IV の一意性と使用上限は、「暗号化通信の確立・維持」に従う。
E2EE が有効であることを理由に、これらの保護を省略しない。

不正な DTLS・SRTP/SRTCP パケットを、後続のメディア処理や SCTP へ渡さない。
認証に失敗したパケットによって、確定済みの ROC・パケットインデックス・リプレイ判定状態を更新しない。

未知の SSRC、過大なパケットインデックス、重複・順序逆転したパケットによって、暗号状態やバッファを無制限に生成しない。
検証に必要な一時状態にも上限を設け、認証前の情報だけで継続利用する状態を確定しない。

ICE 候補、候補ペア、ICE 接続確認、Consent Freshness、暗号状態、ソケット、タイマー、送受信バッファに資源上限を適用する。
接続単位・利用者単位・サーバー全体の上限を対象に応じて設け、並行処理でも超過しない。
確保・解放の結果が不明な場合は、共通の資源管理に従う。

ICE・DTLS・SRTP/SRTCP の秘密情報、TURN 資格情報、保護対象の本文をログやエラー通知へ出力しない。
失敗通知には、対象接続と原因の判別に必要な情報だけを含める。

## 受け入れ条件

実際の Browser SDK、Signaling、WebRTC Transport、STUN / TURN を組み合わせ、IPv4・IPv6、複数アドレス、NAT 配下、直接接続・TURN 経由の条件で検証する。
遅延・損失・重複・順序逆転、経路変更、状態喪失も発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 権限の失効 | Signaling 切断中も権限・失効を確認する。失効時や期限内に権限を確認できない場合は、規定の期限で対象通信を停止する |
| DTLS の相手検証 | 対象接続のフィンガープリントと証明書を照合する。未確認・不一致では保護対象のデータを送受信せず、期待値を実際の証明書へ自動変更しない |
| DTLS の組み込み | DTLS 1.2 / 1.3 を対応する相手で確認し、共通 DTLS の受け入れ条件を満たす。WebRTC Transport で DTLS 1.2 の再ネゴシエーションを使用しない |
| SRTP の交渉と鍵導出 | 許可プロファイルを交渉し、AEAD を優先する。Exporter の鍵素材をロール・方向・プロファイルに従って使用する。MKI、NULL 暗号、平文の鍵配送を使用しない |
| SRTP/SRTCP の受信 | 正当な順序逆転を処理し、改変・リプレイを拒否する。認証失敗で ROC・パケットインデックス・リプレイ判定状態を更新せず、未認証の内容を後続処理へ渡さない |
| IV の一意性 | 生成済み暗号文の再送と、新しい暗号化処理を区別する。新しい暗号化処理では、同じ鍵・IV を再利用せず、同じ鍵で (ROC, SEQ, SSRC) の組を再利用しない。異なる平文や認証対象の RTP ヘッダーを、同じ鍵・IV で新たに保護しない。SSRC の変更・再利用、並列送信、SFU の転送・ヘッダー書き換え・ストリーム切り替えについて、既存暗号文を再利用する場合と再暗号化する場合を分けて検証する。既存暗号文の再利用では、その暗号文に対応する鍵・SSRC・パケット番号などの保護条件と、保護対象の内容が変わっていないことを確認する。SRTCP にも固有の IV・パケットインデックス条件を適用する |
| 鍵の使用上限 | プロファイルごとの計数範囲と上限を守り、必要な複数ストリームの合計も計上する。再確立が間に合わなければ上限で送信を停止する。DTLS KeyUpdate だけで SRTP/SRTCP の鍵や使用量を初期化しない |
| 状態喪失と SFU 移行 | パケットインデックス・使用量・リプレイ判定状態の喪失後に、Nonce の再利用や過去の暗号文の再受け入れを起こさない。保証できなければ停止して新しい鍵を確立する。新旧接続の暗号状態を混同しない |
| 多重化と不正入力 | STUN、DTLS、SRTP/SRTCP と TURN の外側・内側を区別する。不正な形式・長さ・未対応入力を使って検証を迂回できず、範囲外アクセスを起こさない |
| 資源上限と回収 | 大量の ICE 候補・確認要求・未知の SSRC・過大なパケットインデックスでも、内部状態を含む上限を超えない。並行確保、結果不明、通知の重複・遅延でも誤計上せず、安全に回収する |
| E2EE と機密情報 | WebRTC Transport の保護を理由に E2EE を省略せず、SFU に E2EE 復号鍵を渡さない。WebRTC Transport の秘密情報、TURN 資格情報、保護対象の本文をログへ出力しない |

検証には、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)を適用する。
次を重点対象とする。

| 検証方法 | 重点対象 |
|---|---|
| Fuzzing | STUN・TURN・SRTP/SRTCP の解析、多重化、長さ・境界・パディング、不正な認証情報、DTLS ライブラリとの接続部分 |
| Property-based Testing | ICE 候補・役割・世代の操作列、ROC・パケットインデックス・リプレイ判定、IV の一意性、鍵使用量、再送・順序逆転、資源計上 |
| 形式的な証明の評価 | IV・パケットインデックスの構成、境界計算、資源・送信予算の不変条件について、Lean 4・Verus・Aeneas などの適合性を評価する |

標準のテストベクトルがある暗号処理は、それとの一致を確認する。
モデル検査、形式的な証明、Fuzzing、Property-based Testing、静的解析、統合試験の結果を区別し、未検証の範囲を成功・証明済みとして扱わない。

Chrome・Firefox・Safari と実際の Browser SDK で相互接続を確認する。
ICE Lite、各 DTLS バージョン、各 SRTP プロファイルなど、ブラウザーだけで確認できない条件は検証用クライアントで確認し、その範囲を区別する。

結果には、ブラウザー・Browser SDK・サーバー・ライブラリのバージョン、実行方式、ネットワーク・NAT の構成、ICE 候補と選択経路、暗号条件、期限・資源上限、検証範囲と観測結果を記録する。
記録に秘密情報を含めない。
