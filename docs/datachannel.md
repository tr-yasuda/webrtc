# SCTP / DataChannel

共通の前提・用語・利用場面は [共通仕様](spec.md) に従う。
本文の暗号化は、[E2EE・鍵管理](e2ee.md#datachannel-本文の保護)に従う。

## 接続

DataChannel は、参加端末と SFU 間の WebRTC Transport 上に確立する。
参加端末間の P2P 接続は使用しない。
SFU は各接続の SCTP を終端し、認可された転送先へ E2EE の本文を復号せずに中継する。

SCTP は DTLS 上で使用する。
接続・相手認証・Consent Freshness の条件は WebRTC Transport 仕様に従う。
SCTP の利用方法は [RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html)、SDP による交渉は [RFC 8841](https://www.rfc-editor.org/rfc/rfc8841.html)に従う。

次の状態を区別する。

| 状態 | 意味 |
|---|---|
| WebRTC Transport の利用可能 | 必要な経路・認証・暗号・送信同意の条件を満たしている |
| SCTP Association の確立 | 対象接続で SCTP の通信が成立している |
| DataChannel の利用可能 | 対象の DataChannel について、DCEP の進行段階に応じた送受信条件と必要な設定を満たしている |
| アプリケーション送受信の許可 | 現在の通信権限と E2EE の鍵状態を確認している |

下位の接続が成立しただけで、アプリケーション送受信を許可しない。

RFC 8831 は Out-of-band Negotiation も認めるが、今回のプラットフォームでは DataChannel の確立に [RFC 8832](https://www.rfc-editor.org/rfc/rfc8832.html)の DCEP を採用する。
SCTP ストリーム番号の割り当ては DTLS ロールなどの規定に従い、重複や競合を処理する。
DataChannel のラベルやプロトコル名だけで、送信元の識別や通信権限を確定しない。

以下では、DCEP の DATA_CHANNEL_OPEN を OPEN、DATA_CHANNEL_ACK を ACK と記載する。
今回のプラットフォームは、DATA_CHANNEL_OPEN の送信後、対応する DATA_CHANNEL_ACK の受信前にユーザーデータを送信する動作にも対応する。
OPEN の送信側は、その DataChannel で ACK またはほかのメッセージを受信するまでは、ユーザーデータを ordered で送信する。
受信後は、交渉した DataChannel の ordered / unordered の設定に従う。
OPEN の受信側は、OPEN の形式・パラメーター・SCTP ストリーム割り当てを検証し、正当な場合に ACK を送信して対象の DataChannel のデータを扱う。
未使用の SCTP ストリームへ OPEN による確立なしに届いたユーザーデータや、不正な OPEN は、RFC 8832 のエラー処理に従って対象の DataChannel を閉じる。
ACK 前の送信とその受信・中継でも、C-Plane の認可と E2EE 仕様が定める鍵状態の確認を省略しない。
SFU は E2EE 本文を復号せず、参加端末側が鍵の使用可否・認証・復号を確認する。
ACK の受信を、認可・鍵状態の確認や相手アプリケーションへの送達確認の代わりにしない。

ルーム内で扱う論理チャネルと、接続ごとの DataChannel・SCTP ストリーム番号を区別する。
DCEP の確立・終了は DataChannel、ルーム内の配送先・権限・E2EE との対応は論理チャネルの状態として管理する。
転送元と転送先で、同じ SCTP ストリーム番号を使用することを前提にしない。
対応関係は、参加端末・接続・論理チャネルに結び付けて管理する。

論理チャネルの作成・利用は、C-Plane が認可した用途と送受信先の範囲に限る。
DCEP の要求を受信しただけで、任意の論理チャネルや転送先を登録しない。
送信先への権限と E2EE の鍵配布範囲は、E2EE 仕様に従って一致させる。

DataChannel の終了は、規定の SCTP ストリームリセット手順に従う。
終了処理中の SCTP ストリーム番号を、新しい DataChannel へ早期に割り当て直さない。
遅延したデータや終了通知を、新しい DataChannel のものとして処理しない。

ICE restart と SCTP Association の再確立は、別の操作として判断する。
既存の SCTP Association を継続できるかは、WebRTC Transport と SCTP の状態に基づいて判断する。
再接続・SFU 移行で新しい SCTP Association が必要な場合は、新旧の状態を分離する。
論理チャネルの継続と、未配送データ・順序・重複の扱いは「データ配送」で定める。

SCTP Association 数、DataChannel 数、確立・終了待ちの処理、バッファ、タイマーには、設定可能な上限を設ける。
並行する作成・終了でも共通の資源管理要件を満たす。
失敗や期限切れは Browser SDK に通知し、無期限に接続準備中のまま保持しない。

## データ配送

メッセージは、送信元の参加端末・論理チャネル・認可された宛先に対応付けて配送する。
SFU は送信元の接続と現在の権限を確認し、許可された宛先へ E2EE の本文を復号せずに中継する。
ルーム全体への送信と、特定の参加端末への送信を区別する。

配送方式は、順序保証と再送条件を分けて指定する。

| 項目 | 選択できる条件 |
|---|---|
| 順序 | ordered / unordered |
| 再送 | reliable / 再送回数による制限 / 有効時間による制限 |

既定は reliable・ordered とする。
再送回数と有効時間の制限は、同時に指定しない。
DCEP の確立中には、前節で定めた ordered 送信の条件を適用する。

これらの SCTP の保証は、個々の SCTP Association 内で適用する。
SFU で受信しても、転送先への配送完了とは判断しない。
reliable でも、接続終了、権限失効、資源制限によって相手アプリケーションへ届かない場合がある。
SCTP のメッセージ境界と配送条件は、[RFC 8831 §6](https://www.rfc-editor.org/rfc/rfc8831.html#section-6)に従う。

送信元から SFU、SFU から宛先への各区間で、選択した配送方式に対応する DataChannel を使用する。
対応する方式を利用できない宛先については、方式を黙って変更せず、配送できないことを通知する。
ordered の順序は、同じ送信元の参加端末・論理チャネルから同じ宛先へ送るメッセージの範囲で維持する。
各 SCTP Association・SCTP ストリームの順序保証だけに依存せず、SFU 内の並行処理・待機キュー・転送先への引き渡しでも、受信したメッセージの順序を維持する。
接続をまたぐ順序保証は対象外とし、異なる送信元の参加端末間の全体順序は保証しない。

SCTP の再送回数・有効時間の制限は、各区間の条件として扱う。
各区間の制限だけでは、送信元から宛先までの合計再送回数や有効時間を保証しない。
Browser SDK・SFU の待機キューにも保持期限を設け、期限切れのメッセージを新たに転送しない。

Browser SDK は、次の状態を区別して通知する。
内部で確認できない状態を、確認済みとして通知しない。

| 状態 | 意味 |
|---|---|
| 送信受け付け | Browser SDK が送信処理を受け付けた |
| 中継受け付け | SFU が対象メッセージを受け付けた |
| 宛先の Browser SDK への送達確認 | 宛先の Browser SDK から、認証・復号とアプリケーションへの引き渡しに対応する確認を受けた |
| 失敗・送達不明 | 送信できなかった、または期限内に送達を確認できなかった |

送達確認が必要な場合は、メッセージと宛先を識別する確認応答を使用する。
確認応答にも E2EE 仕様に従う認証と権限確認を適用する。
SCTP の ACK や DCEP の ACK を、この確認応答の代わりにしない。
宛先の Browser SDK への送達確認では、相手アプリケーションの業務処理の完了は保証しない。
複数宛先への送信結果は、宛先ごとに扱う。
宛先の Browser SDK が受信・引き渡しを完了しても、確認応答が失われる場合がある。
送信側が期限内に確認応答を得られなかった場合は、未配送だったと断定せず、送達不明として扱う。
この状態から再送する場合も、同じメッセージの識別情報に基づく重複検出を維持する。

アプリケーションメッセージの境界を維持する。
本文は E2EE の暗号化形式に格納し、DataChannel 上ではバイナリーとして送信する。
送信可能なサイズは、相手の受信上限とプラットフォームの上限の両方を満たし、暗号化・配送情報による増加分を含めて判定する。
SDP の `max-message-size` の扱いは、[RFC 8841 §6](https://www.rfc-editor.org/rfc/rfc8841.html#section-6)に従う。
相手がサイズ制限なしを示しても、プラットフォームの資源上限は維持する。
上限を超えるメッセージは、黙って切り詰めず送信を拒否する。

送受信キュー、断片の再構成、順序待ち、確認応答待ちには、件数・総バイト数・保持期間の上限を設ける。
送信量が処理能力を超える場合は、Browser SDK に待機・送信拒否などの状態を通知する。
一つの大きなメッセージや遅い宛先が、ほかの論理チャネル・宛先や音声・映像を無期限に妨げない。
SCTP の輻輳制御とは別に、SRTP を含む経路全体の帯域を管理する。

再接続・SFU 移行で SCTP Association が変わる場合、未配送メッセージを無条件に自動再送しない。
送達不明を Browser SDK に通知し、接続をまたぐ再送は明示的な操作として扱う。
再送時もメッセージの識別情報を維持し、現在の宛先権限と鍵状態を確認する。
暗号化済みでも旧鍵による新規送信が許可されない場合は、現在の条件で暗号化し直すか送信を中止する。

受信先の参加端末は E2EE 仕様に従って、認証成功後に重複・リプレイ判定状態を更新する。
旧・新接続からの重複受信でも、同じメッセージを繰り返しアプリケーションへ渡さない。
接続をまたぐ順序の継続は自動的に保証せず、継続できない場合は Browser SDK に通知する。
アプリケーション処理まで含む exactly-once の実行保証は提供しない。

購読解除・権限失効・論理チャネルの終了と送信が競合する場合も、古い認可で新しい送信処理を開始しない。
判定の基準は、SFU 仕様で定めた実際の送信処理への引き渡し直前とする。
送信前の鍵状態の確認、復号失敗時の処理は E2EE 仕様に従い、平文への切り替えは認めない。

## 自作範囲・既存実装の利用

サーバー側の SCTP / DataChannel のプロトコル処理と中継処理は Rust で実装する。
論理チャネルの利用認可とアプリケーションからの制御は、TypeScript の C-Plane が担う。

| 自作する部分 | 内容 |
|---|---|
| SCTP Association | 確立・維持・終了、対象接続との対応、異常時の状態遷移 |
| SCTP パケット処理 | パケット・チャンクの読み書きと検証、チェックサム、確認応答、重複・順序逆転の処理 |
| 配送制御 | 断片化・再構成、再送、部分信頼性、フロー制御、輻輳制御 |
| SCTP ストリーム管理 | 番号の割り当て、順序管理、リセット、再利用条件 |
| DCEP | OPEN・ACK の処理、パラメーター検証、ACK 前のユーザーデータの扱い |
| 論理チャネルと中継 | 接続ごとの SCTP ストリームとの対応、宛先の確認、中継時の順序維持 |
| 配送状態と復旧 | 受け付け・送達確認・送達不明の区別、再接続・移行時の状態分離 |
| 資源管理 | バッファ、キュー、タイマー、処理中の要求の予約・計上・解放 |

完成済みの SCTP スタックや DataChannel 実装に、これらのサーバー側の中核処理を委ねない。
必要な SCTP 拡張も、自作するプロトコル処理の対象に含める。
対応する拡張と交渉結果は、接続・配送要件に従って管理する。

[RFC 8831 §6.1](https://www.rfc-editor.org/rfc/rfc8831.html#section-6.1)で要求される拡張は、次を自作範囲に含める。

| 必須の拡張 | 実装する機能 |
|---|---|
| 部分信頼性（RFC 3758・RFC 7496） | 有効時間と再送回数による制限、放棄したデータを受信側が処理するための FORWARD TSN と関連する状態管理 |
| SCTP ストリーム再構成（RFC 6525） | DataChannel の終了に必要な SCTP ストリームリセット、要求・応答、完了と再利用条件の管理 |
| 対応通知（RFC 5061） | SCTP ストリームリセットへの対応を通知するために必要な機能。その他の動的アドレス再構成機能を一律に必須とはしない |

Message Interleaving（[RFC 8260](https://www.rfc-editor.org/rfc/rfc8260.html)）は、RFC 8831 の推奨を踏まえて対応対象として検討する。
採用する場合は、能力通知、I-DATA、部分信頼性と組み合わせる I-FORWARD-TSN、再構成・順序・スケジューリングの処理を自作範囲に含める。
未対応の相手との配送と大きなメッセージによる占有対策を確認する。
検討結果にかかわらず、ブラウザーとの相互接続に必要な機能を省略しない。

SCTP のチェックサムは CRC32c の生成・検証に対応する。
Zero Checksum 拡張（[RFC 9653](https://www.rfc-editor.org/rfc/rfc9653.html)）は評価対象とし、採用する場合も CRC32c の対応を維持する。
利用可否は SCTP Association の確立時に、Zero Checksum Acceptable パラメーターによる方向ごとの受け入れ通知と、対象の代替誤り検出方式に従って確認する。
送信側は、相手から対応する受け入れ通知を受信し、SCTP over DTLS の保護条件を満たす場合に限って、規定に従いチェックサム計算を省略できる。
INIT・COOKIE ECHO・ASCONF を含むパケット、OOTB パケットへの応答など、RFC 9653 が CRC32c を要求する条件では正しいチェックサムを使用する。
受信側は、自身が通知した受け入れ条件と DTLS の検証を満たす場合だけ、計算を省略したゼロ値を受け入れる。
それ以外は CRC32c を検証し、計算結果が正当にゼロとなる場合と、未検証のゼロ値を区別する。
未対応の接続相手や利用条件を満たさない通信では、通常の CRC32c による互換性を維持する。

ICE、DTLS、相手認証、Consent Freshness は、WebRTC Transport の共通処理を利用する。
SCTP / DataChannel に同じ処理や DTLS の暗号状態を重複実装しない。
SCTP が管理する確認応答・再送・輻輳状態と、DTLS が管理する状態を区別する。

ブラウザー側は、Browser SDK がブラウザーの WebRTC API を利用する。
Browser SDK は論理チャネルの管理、配送方式の指定、E2EE、送達確認、重複検出、結果通知を担う。
ブラウザー内部の SCTP を Rust で置き換える必要はない。

本文の暗号化・復号と鍵状態の確認は、E2EE 仕様に従って参加端末側で行う。
SFU の中継処理は本文を復号しない。
配送用の識別情報と、E2EE で認証するメッセージ情報の対応を維持する。

汎用的な入出力、非同期実行、タイマー、バッファ管理、チェックサム計算には既存ライブラリを利用できる。
チェックサムの対象範囲や格納形式、検証結果に基づく処理は、自作する SCTP の責務とする。
バイト列・数値の読み書きなどの補助処理の利用によって、パケット解析・検証・状態管理を完成済みのプロトコル実装へ委ねない。
暗号処理と暗号学的な乱数生成には、既存の安全な実装を利用する。

既存ライブラリの内部バッファやタイマーも、全体の資源管理に含める。
ライブラリ自身の制限または組み込み側の制御によって、資源上限を保証する。

C-Plane と D-Plane の分離は論理的な責務の分離とし、別プロセスでの実行を必須としない。
Rust の実行方式は Wasm、Native Addon、独立 Worker を選択肢として残し、後続の技術選定で決定する。
SCTP 内部の実装方式も、この段階では固定しない。

採用する既存実装のバージョン、設定、依存する機能を記録する。
実装と検証は、共通仕様の「実装・検証の共通方針」に従う。

## セキュリティ

SCTP / DataChannel は、認可された参加端末・WebRTC Transport・論理チャネルに対応付けて利用する。
DTLS の認証、SCTP Association の確立、DCEP の成功だけで、論理チャネルの作成・送信・受信の権限を取得したとは扱わない。

DTLS の検証を通過した SCTP パケットだけを処理する。
認証済みの接続相手から受信した場合も、SCTP の形式と状態遷移を検証する。
ポート番号、Verification Tag、チャンク・パラメーターの長さ、パディング、組み合わせ、SCTP ストリーム番号、PPID を確認する。
未知のチャンク・パラメーターは、各仕様が定める処理に従う。
CRC32c と Zero Checksum の条件は、前節に従う。

SCTP State Cookie は、DTLS Cookie や利用者認証とは区別する。
MAC、対象の SCTP Association との対応、有効性を、[RFC 9260 §5](https://www.rfc-editor.org/rfc/rfc9260.html#section-5)に従って検証する。
不正な SCTP State Cookie や重複した確立要求で SCTP Association を増殖させない。
SCTP State Cookie の生成・検証には既存の暗号実装を利用し、検証前の処理と保持状態にも資源上限を適用する。

SACK、FORWARD TSN、SCTP ストリームリセットなどの制御情報は、対象の SCTP Association・SCTP ストリームと現在の送受信状態に対応付けて検証する。
未送信のデータを確認済みにする、不正な番号で受信状態を飛ばす、別の DataChannel の状態や資源を変更することを防ぐ。
番号の周回、重複、順序逆転、古い制御情報も含めて確認する。
Message Interleaving を採用する場合は、I-DATA・I-FORWARD-TSN とメッセージ識別情報にも対応する検証を適用する。

DCEP の OPEN・ACK は、対象の SCTP ストリーム、確立状態、パラメーターとの対応を検証する。
ラベル・プロトコル名は信頼できない入力として扱い、長さと文字列処理を検証する。
表示やログ出力に利用する場合も、安全な表現へ変換する。
不正な OPEN や未確立の SCTP ストリームのユーザーデータは、[RFC 8832 §6–7](https://www.rfc-editor.org/rfc/rfc8832.html#section-6)に従って処理する。
ACK 前のユーザーデータでも、認可・鍵状態の確認を省略しない。

受信したメッセージの宛先情報だけで転送を許可しない。
送信元の接続、論理チャネル、現在の送受信権限を確認し、別ルームや未許可の参加端末へ中継しない。
解除・失効・終了と送信の競合には、「データ配送」で定めた送信開始の判定条件を適用する。
Signaling 切断中も、権限情報の有効期限と失効時の停止条件を維持する。

SCTP の断片とメッセージの長さ・境界・順序を検証し、別メッセージや別の SCTP ストリームの断片を混合しない。
再構成が完了していないメッセージを、完了済みとして中継・アプリケーションへ引き渡さない。
大量の未完了メッセージ、順序の欠落、重複断片、過大なサイズでも、保持メモリと処理量の上限を超えない。
期限切れや上限到達時は、配送方式とプロトコルの状態に従って破棄・失敗通知・DataChannel の終了などを行う。

SCTP Association・DataChannel の確立と終了、再送、制御応答、確認応答待ちには、処理量・帯域・状態数・保持期間の上限を適用する。
制御情報の連続受信や DataChannel の作成・終了の繰り返しで、制限を回避できないようにする。
複数宛先への中継では、宛先ごとの送信量と全体の送信量を計上する。
並行する確保・解放、結果不明、隔離した資源の回収は、共通の資源管理に従う。

接続終了・再接続・SFU 移行では、古い SCTP Association のデータや通知を新しい状態へ適用しない。
SCTP ストリーム番号の再利用だけで、過去の論理チャネルとの対応を復活させない。
重複・リプレイ判定の状態を失った場合の復旧条件は、E2EE 仕様に従う。

SFU は E2EE 本文の正当性を検証できたとは扱わない。
参加端末は、本文の認証・復号と使用権限の確認に成功した場合だけアプリケーションへ渡す。
送達確認応答も、対象メッセージ・宛先との対応と認証を確認する。
復号や鍵の確認に失敗しても、平文配送へ切り替えない。

ログ・計測・エラー通知には、認証情報、暗号鍵、SCTP State Cookie、メッセージ本文、パケット全体を出力しない。
識別情報・通信状況は必要な範囲だけ記録し、アクセス制御と保持期限を適用する。

## 受け入れ条件

実際の Browser SDK、Signaling、SFU、WebRTC Transport、STUN / TURN を組み合わせて検証する。
損失・遅延・重複・順序逆転、切断、再接続、SFU 移行、権限失効を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 接続状態の分離 | WebRTC Transport、SCTP Association、DataChannel、アプリケーション送受信の許可を区別する。下位の接続成立だけで送受信を許可しない |
| SCTP Association の確立・終了 | 正常な確立、同時開始、重複要求、再送、異常終了を処理する。SCTP State Cookie の検証と対象接続との対応を維持し、重複した状態を生成しない |
| DCEP | OPEN・ACK、SCTP ストリーム番号の割り当て、パラメーター、不正入力を処理する。ACK 前のユーザーデータにも、規定の順序条件と認可・E2EE 条件を適用する |
| SCTP ストリームの終了・再利用 | リセットの要求・応答と完了を管理する。終了前に番号を再利用せず、古いデータ・通知で新しい DataChannel を変更しない |
| 必須 SCTP 拡張 | 部分信頼性の有効時間・再送回数制限、FORWARD TSN、SCTP ストリームリセット、その対応通知が動作する |
| 配送方式 | reliable・ordered を既定とし、各配送方式を正しく適用する。宛先で利用できない方式へ黙って変更しない |
| ordered の中継 | 同じ送信元の参加端末・論理チャネル・宛先の順序を、SCTP だけでなく SFU の並行処理・待機キュー・送信への引き渡しでも維持する |
| 部分信頼性と欠落 | 期限切れ・再送上限による放棄を正しく処理する。後続メッセージを無期限に待たせず、各区間の制限を参加端末間全体の保証として通知しない |
| 送達確認 | Browser SDK の受け付け、SFU の受け付け、宛先の Browser SDK への送達確認を区別する。SCTP・DCEP の ACK を宛先の Browser SDK の確認応答と混同しない |
| 確認応答の消失 | 宛先で引き渡し済みでも応答が届かない場合は、送信側で送達不明とする。未配送と断定せず、明示的な再送でも重複したアプリケーションへの引き渡しを防ぐ |
| 宛先と認可 | ルーム全体・特定の参加端末への配送を区別する。複数宛先の結果を個別に扱い、別ルームや未許可の参加端末へ中継しない |
| 解除・失効との競合 | キュー待機中・送信直前・再送中に解除や失効を発生させる。規定の確定順序に従い、古い認可で新しい送信処理を開始しない |
| メッセージ境界・サイズ | 境界を維持し、暗号化・配送情報を含むサイズで送受信上限を守る。過大なメッセージを切り詰めず拒否する |
| 断片化・再構成 | 損失・重複・順序逆転・不正な境界でも、別メッセージの断片を混合しない。未完了の内容を完成済みとして渡さない |
| E2EE | 宛先権限と鍵の配布範囲を一致させる。未送信データの鍵状態を再確認し、必要なら再暗号化または中止する。認証成功後に重複・リプレイ判定状態を更新し、平文へ切り替えない |
| 再接続・SFU 移行 | 新旧 SCTP Association の状態を分離する。接続をまたぐ自動再送・順序保証を行わず、送達不明や順序の継続不能を通知する。重複受信でも同じメッセージを繰り返し渡さない |
| 制御情報の検証 | 不正な SACK、FORWARD TSN、リセット、番号の周回や遅延通知で、未送信データの確認、別の DataChannel の変更、不正な資源解放を起こさない |
| CRC32c | 正しい値を検証し、破損を検出する。計算結果が正当にゼロとなる場合も扱う |
| 資源上限と回収 | 大量の DataChannel、未完了断片、順序待ち、再送、確認応答待ちでも上限を超えない。並行確保・解放、結果不明、遅延通知を共通の資源管理に従って処理する |
| 輻輳と公平性 | 大きなメッセージや遅い宛先が、ほかの論理チャネル・宛先・音声・映像を無期限に妨げない。宛先別・全体の送信量と待機状態を制限する |
| ログ・通知 | 認証情報、暗号鍵、SCTP State Cookie、本文、パケット全体を出力しない。識別情報の記録にアクセス制御と保持期限を適用する |

Message Interleaving を採用する場合は、能力通知、I-DATA、I-FORWARD-TSN、複数メッセージの再構成・順序・部分信頼性を検証する。
未対応の相手との相互接続と、大きなメッセージによる占有対策も確認する。
Message Interleaving が利用できない区間では、[RFC 8831 §6.6](https://www.rfc-editor.org/rfc/rfc8831.html#section-6.6)の推奨を踏まえ、原則として最大 SCTP ユーザーメッセージサイズを 16 KiB（16,384 bytes）に制限する。
この上限には、E2EE と配送情報による増加分を含め、相手の受信上限やプラットフォームの上限がさらに小さい場合は、その上限を適用する。
16 KiB を超えるサイズを許可する場合は、対象ブラウザー・接続構成、許可する最大サイズ、負荷条件、公平性と遅延・キュー使用量の合否基準を事前に定める。
損失・遅延がある条件でも、大きなメッセージと並行するほかの論理チャネルの配送および音声・映像への影響と、相互接続性を実測して基準を満たすことを確認し、例外の適用範囲と根拠を記録する。

Zero Checksum を採用する場合は、方向ごとの受け入れ通知と DTLS の完全性保護が利用条件を満たすことを確認する。
未交渉のゼロ値を、DTLS 保護だけを理由に受け入れない。
[RFC 9653 §5.2](https://www.rfc-editor.org/rfc/rfc9653.html#section-5.2)に従い、INIT・COOKIE ECHO を含むパケット、所定の OOTB 応答、ASCONF を利用する場合の当該パケットなど、正しい CRC32c が必要な条件を区別して検証する。
代替誤り検出方式の利用条件を満たさない場合にも正しい CRC32c を使用し、拡張の交渉成功だけですべての SCTP パケットをゼロ値にしない。
拡張に未対応の相手との CRC32c による互換性も確認する。
Message Interleaving と Zero Checksum の採用可否は未確定とし、両拡張について、採用の評価結果と実装・試験の完了を区別する。

性能試験では、メッセージサイズ、送信頻度、送信者数、宛先数、配送方式、E2EE、ネットワーク条件を固定して比較する。
メッセージ処理量、宛先の Browser SDK までの遅延、送達確認時間、欠落・重複、送達不明の件数、CPU・メモリ・帯域・キュー使用量を記録する。
メディア併用時は共通仕様の基準負荷を維持し、DataChannel の負荷と音声・映像への影響を記録する。
再接続・移行では、中断時間と未配送・重複・送達不明を測定する。

性能・復旧時間の合否基準は、試験前に定める。
測定の完了と目標達成を区別し、未達の値と制約を記録する。
安全性の要件は、性能目標の達成を理由に緩和しない。

検証には、共通の実装・検証方針を適用する。

| 検証方法 | 重点対象 |
|---|---|
| TLA+ によるモデル検査 | SCTP Association・DCEP・リセットの状態遷移、中継順序、送達確認、解除・失効と送信開始の競合、移行、資源管理 |
| Fuzzing | SCTP パケット・チャンク・パラメーター、DCEP、断片・長さ・境界、制御情報、配送情報の解析 |
| Property-based Testing | 番号の周回、再送・放棄・重複・順序逆転、断片の再構成、中継順序、通知の操作列、資源計上 |
| 形式的な証明の評価 | 番号比較、境界計算、再構成・順序・資源上限の不変条件について、Lean 4・Verus・Aeneas の適合性を評価する |

安全性に加え、必要な通信・処理・障害回復の前提の下で、確立・終了・放棄・回収が完了する活性を検証する。
モデル検査、形式検証、Fuzzing、テスト、静的解析、統合試験の結果と保証範囲を区別する。

Chrome・Firefox・Safari と実際の Browser SDK で相互接続を確認する。
ブラウザーから直接制御できない不正入力や拡張条件は、検証用クライアントを使用し、その検証範囲を区別する。
結果には、各実装のバージョン、Rust の実行方式、交渉した機能、配送方式、E2EE、ネットワーク、期限・資源上限、試験負荷と観測結果を記録する。
