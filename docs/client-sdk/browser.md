# Browser SDK

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## 公開インターフェース

Browser SDK は、ブラウザーの WebRTC API を利用し、ルームへの参加、発行・購読、DataChannel、状態取得・通知を行う TypeScript のインターフェースを提供する。
アプリケーションが SDP、ICE、SCTP ストリーム番号を直接操作しなくても、通常の通話とデータ通信を制御できるようにする。
対象環境は、共通仕様で定めたデスクトップ版の Chrome・Firefox・Safari とする。
Node.js での動作は現時点では保証しない。

| 操作の範囲 | 提供する機能 |
|---|---|
| 対応状況の確認 | 必要なブラウザー機能、E2EE、コーデック、Simulcast・SVC、エンコーディング制御の利用可否を取得する |
| 参加・退出 | 参加 JWT を用いた参加、対象の参加端末の退出、終了理由の取得 |
| 発行 | 音声・カメラ映像・画面共有の開始・停止、発行状態の取得 |
| 購読 | 発行の選択、購読の追加・変更・解除 |
| 品質指定 | 希望品質、最大解像度・フレームレート、優先度の指定 |
| データ通信 | 論理チャネルの利用、配送方式・宛先を指定した送信、受信、送達確認、明示的な再送 |
| 状態取得 | 参加端末、発行・購読、接続、品質、E2EE、配送の現在の状態 |
| 通知 | 状態変更、受信データ、権限変更、失敗・終了・復旧の理由 |
| 診断 | 接続・品質・資源制限などの診断情報と通信統計の取得 |

参加者、参加端末、接続、発行、購読、論理チャネルを区別して識別する。
再接続や SFU 移行で接続が変わっても、継続する参加端末・発行・購読を別のものとして通知しない。
識別情報を指定できることを、対象への操作権限があることとは扱わない。

非同期操作は、受け付けと完了を区別する。
戻り値がどの段階の完了を示すかを、操作ごとの契約として定める。
参加端末の登録、WebRTC Transport の成立、E2EE の準備、発行・購読の成立、実際の受信・再生を、一つの成功状態へまとめない。
送信・送達の結果は、SCTP / DataChannel 仕様の状態区分に従う。

操作の失敗には、原因を判別できる型付きの情報を提供する。
権限不足、非対応、交渉不成立、資源上限、期限切れ、接続終了、結果不明を区別する。
応答が失われた操作は未実行と断定せず、状態の照合結果を通知する。
再試行で発行・購読・論理チャネルを重複生成しない。

現在の状態の取得と変更通知を組み合わせ、通知の重複・欠落・順序逆転があっても整合する状態を取得できるようにする。
アプリケーションがイベントの到着順だけから正しい状態を推測する構成にしない。
終了済みの操作や接続から届いた通知で、現在の状態を過去へ戻さない。

メディア取得では、ブラウザーの権限要求、利用者による拒否、デバイスの利用不能、画面共有の終了を通知する。
アプリケーションが渡すトラックと Browser SDK が取得するトラックについて、所有・停止・解放の責務を公開契約で区別する。
ミュート、発行の停止、購読解除、品質制御によるエンコーディング停止を区別する。
需要に応じて送信を停止しても、利用者がカメラ・マイクを停止した状態には変更しない。

希望品質と実際の転送品質を分けて取得できるようにする。
Simulcast・SVC やエンコーディング停止・再開に対応しない場合は、その制約と適用した制御を通知する。
品質変更の要求と、送信側での変更・受信側でのデコードの完了を分けて扱う。

E2EE の準備中、更新待ち、送信停止、復旧、非対応、失敗を通知する。
鍵の使用条件と受信権限は E2EE 仕様に従って Browser SDK が確認する。
必要な機能がない場合や鍵状態を確認できない場合は、該当する送受信を許可せず、暗号化を無効にして継続しない。
通常の状態取得・診断インターフェースに秘密鍵や復号鍵を含めない。

Signaling の一時切断、WebRTC 通信の中断、再接続、SFU 移行を区別して通知する。
明示的な退出・除外・ルーム削除・通話時間上限による終了を、自動再接続で取り消さない。
復旧を待つ間も、現在の状態と終了・失敗理由を取得できるようにする。

データ送信では、送信可能なサイズ、待機量、送信を受け付けられる状態を取得できるようにする。
送達不明を未配送と断定せず、接続をまたぐ自動再送やアプリケーション処理の exactly-once 保証を提供しない。
再送時も、メッセージの識別情報、重複検出、現在の権限・鍵状態を維持する。

Browser SDK の終了時には、管理する接続、処理待ち、通知購読、メディアと鍵の関連状態を、定めた所有・保持条件に従って解放する。
終了処理の繰り返しで状態を復活させたり、アプリケーション所有の資源を誤って解放したりしない。

React Native、Python、Go など、異なる環境・言語向けの SDK は将来の拡張候補とする。
今回の仕様では、それらへの対応や共通実装を要求しない。
具体的な型名、メソッド名、イベント名、引数と戻り値、React の Hooks・Context・コンポーネント、パッケージ構成は、これらの契約に従って後続の設計で定める。

## 自作範囲・既存実装の利用

Browser SDK と React SDK は TypeScript で実装する。
Browser SDK は通信と状態管理の中核を担い、React SDK はその機能を React アプリケーションへ提供する。

| 実装する部分 | 責務 |
|---|---|
| Browser SDK：参加・操作 | 参加 JWT の受け渡し、参加・退出、発行・購読、操作結果の照合 |
| Browser SDK：WebRTC の制御 | ブラウザー API による交渉、接続・トラック・DataChannel の管理 |
| Browser SDK：状態同期・復旧 | 現在の状態と通知の整合、再接続、SFU 移行、古い処理結果の排除 |
| Browser SDK：品質制御の適用 | 品質指定、需要に応じたエンコーディング停止・再開、適用結果の確認 |
| Browser SDK：E2EE の組み込み | 鍵状態と送受信可否の管理、メディア・データの暗号化処理への接続 |
| Browser SDK：データ配送 | 宛先・配送方式の指定、送達確認、重複検出、送達不明の通知 |

ブラウザー側の ICE、DTLS、SRTP/SRTCP、SCTP は、ブラウザーの WebRTC 実装を利用する。
サーバー側の Rust プロトコル実装を、ブラウザー側へ重複実装することは求めない。
Browser SDK は、ブラウザー内部の接続状態と、プラットフォームの参加・権限・発行・購読状態を対応付ける。

E2EE は、[E2EE・鍵管理仕様](../e2ee/key-management.md)の既存実装の利用条件に従って組み込む。
暗号アルゴリズムは独自実装しない。
SFrame と鍵管理は、採用した実装が保証する範囲と、Browser SDK が保証する参加権限・状態管理・復旧条件を区別する。
MLS の採用と、E2EE 処理に使用する実装言語・ライブラリ・実行方式は、この段階では固定しない。

WebSocket、入力スキーマ検証、状態通知、計測、React との連携などには、既存の汎用ライブラリを利用できる。
完成済みの通話用クライアントライブラリや SFU 製品のクライアントライブラリに、プラットフォーム固有の通信・状態管理の中核を委ねない。
ライブラリによる解析成功や型付けだけで、通知の正当性・操作対象・更新順序を検証済みとは扱わない。

ブラウザーや既存ライブラリが管理する待機量・内部状態についても、利用可能な制御と計測を確認する。
Browser SDK が管理するキュー・通知・再試行・暗号処理待ちと合わせて資源を制限し、制御できない内部動作を無制限に利用する構成にしない。

Node.js や、React Native・Python・Go などへの対応と共通実装は、今回の要件に含めない。
具体的な API、Hooks、Context、コンポーネント、パッケージ構成は後続の設計で定める。

採用するライブラリのバージョン、設定、依存する機能と対応環境を記録する。
実装と検証は、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)に従う。

## セキュリティ

Browser SDK は、認証した参加者・参加端末と、対象ルーム・接続・発行・購読・論理チャネルを対応付けて操作する。
Browser SDK の状態や識別情報をアプリケーションが変更できることを、操作権限の取得とは扱わない。
最終的な認可は C-Plane・D-Plane が行い、Browser SDK 側の確認だけに依存しない。

Signaling との通信は HTTPS / WSS を使用し、接続先を検証する。
接続失敗を理由に平文通信へ切り替えない。
Browser SDK には、サーバー側で権限を発行・管理するための秘密情報を渡さない。
参加・再接続などの資格情報は、URL、ログ、診断情報、React の表示用状態へ露出させない。
Signaling の認証方式は、[ブラウザーの WebSocket API](https://websockets.spec.whatwg.org/#the-websocket-interface)では任意の認証ヘッダーを設定できない制約を考慮して選定する。
資格情報を URL やログへ露出させず、接続先の検証、認証した参加者・参加端末と接続の対応、認証完了前の操作制限を維持できる方式とする。
具体的な認証方式は、この段階では固定しない。

Signaling の通知、操作結果、鍵管理メッセージは、実行時に形式・サイズ・対象・更新順序を検証する。
TypeScript の型に加えて、外部入力を実行時に検証する。
別ルーム・別の参加端末・古い接続の情報や、遅延した操作結果によって、現在の状態を上書きしない。

E2EE の参加端末・公開鍵・秘密鍵の所持・失効・鍵更新は、E2EE 仕様に従って確認する。
Signaling を公開鍵の対応関係の信頼元とすることと、秘密鍵・復号鍵をサーバーへ渡すことを区別する。
Browser SDK は、E2EE の秘密鍵・復号鍵を C-Plane・D-Plane へ送信しない。
悪意ある Signaling による鍵の対応関係の偽装を防ぐ保証は、今回の信頼モデルに含めない。

送信前に、対象への現在の権限と、使用可能な鍵状態を確認する。
通知の欠落や一時切断があっても、権限・鍵状態を再確認せずに新規送信できる期間を無期限にしない。
期限の延長と復旧には正当な状態の確認を必要とし、単なる再接続や通知の再送で延長しない。
ブラウザーの処理中断から復帰した場合も、期限を再評価してから新規送信を許可する。

並列送信、エンコーディングの停止・再開、再接続、SFU 移行で、鍵・カウンター・リプレイ判定状態を不正に初期化しない。
必要な状態を復元できない場合は、E2EE 仕様に従って新しい鍵状態を確立してから送受信を再開する。
暗号化・復号・鍵確認の失敗や機能の非対応を理由に、平文へ切り替えない。

受信した本文は、認証・復号と使用権限の確認に成功した場合だけアプリケーションへ渡す。
DataChannel の重複・リプレイ判定は認証成功後に更新する。
確認応答を検証できない場合や応答が失われた場合は、送達済み・未配送のいずれも断定せず、配送仕様に従って通知する。

メディア取得はブラウザーの権限と利用者の選択に従う。
権限拒否や画面共有の終了を、自動的な再取得で取り消さない。
アプリケーション所有のトラックと Browser SDK 所有のトラックを区別し、解放・停止を所有関係に従って行う。

参加者名、論理チャネル名、エラー情報などの外部入力を、実行可能な HTML として描画しない。
React SDK が表示を提供する場合も、この条件を維持する。
Browser SDK の安全性を、同じページで動作する悪意あるスクリプトや侵害された参加端末から、平文・鍵を完全に隔離する保証とは扱わない。

操作待ち、通知待ち、再接続、暗号処理、未知の鍵を待つデータ、送達確認、通知購読には、件数・総メモリ量・保持期間などの上限を設ける。
重複通知や再試行によって上限を回避させない。
終了済みの処理結果で接続・送信・購読を復活させず、所有する資源を解放する。

ログ・診断・エラー報告には、認証情報、秘密鍵、復号鍵、メディア・データ本文、パケット全体を出力しない。
通常の状態通知には、対象と原因の判別に必要な情報だけを含める。
不要となった鍵・関連状態の保持と削除は E2EE 仕様に従い、Browser SDK の管理対象からの削除を参加端末内の全コピーの確実な消去とは扱わない。

## 受け入れ条件

実際の Browser SDK・React SDK と、C-Plane、Signaling、SFU、WebRTC Transport、STUN / TURN を組み合わせて検証する。
Chrome・Firefox・Safari について、通常動作に加え、権限拒否、接続切断、通知の欠落・重複・順序逆転、鍵更新、SFU 移行を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 対応状況の取得 | 必要な API の利用可否と、実際の通信・暗号化の動作確認を区別する。非対応の機能と理由を通知する |
| 参加・退出 | 登録、WebRTC Transport 成立、E2EE 準備、通信開始を区別する。通常の退出は対象の参加端末だけに適用する |
| 認証・認可との連携 | 参加 JWT の取得・提示・更新を採用方式に従って扱う。認証成功だけで未許可の操作を有効にせず、サーバー側の拒否・失効を反映する |
| 非同期操作の結果 | 受け付け・完了・失敗・結果不明を区別する。応答消失や再試行で発行・購読・論理チャネルを重複生成しない |
| 状態同期 | 現在の状態と変更通知を整合させる。古い接続・操作の通知で現在の状態を上書きせず、欠落後に再同期できる |
| メディア取得 | 権限要求・拒否、デバイス利用不能、画面共有終了を通知する。自動再取得で利用者の拒否や終了を取り消さない |
| 発行・購読 | 音声・カメラ映像・画面共有を独立して操作する。ミュート、発行停止、購読解除、品質上の一時停止を区別する |
| 品質制御 | 希望品質と実際の品質を分けて通知する。Simulcast・SVC の非対応や制限を通知し、要求の受け付けを適用完了と扱わない |
| エンコーディング停止・再開 | 対象発行と更新順序を確認して適用する。遅延・重複通知や停止中の需要変更でも最新状態へ収束し、実際の停止・再開・デコードを確認する |
| E2EE | 使用可能な鍵状態と権限を確認して送受信する。準備失敗・期限切れ・非対応時に平文へ切り替えない |
| 鍵更新と復旧 | 並列送信、停止・再開、移行、状態喪失でも Nonce の再利用や過去の暗号文の再受け入れを防ぐ。必要な状態を確認できなければ送受信を再開しない |
| DataChannel | 宛先・配送方式・サイズ・待機量の条件を守る。送達確認と送達不明を区別し、明示的な再送でも重複してアプリケーションへ渡さない |
| 再接続・SFU 移行 | Signaling 切断と通信中断を区別する。識別情報を維持して復旧し、二重再生を防ぐ。明示的な終了を自動再接続で取り消さない |
| 終了と所有関係 | Browser SDK 所有とアプリケーション所有の資源を区別する。終了処理の繰り返しや遅延結果で、誤解放や状態の復活を起こさない |
| 資源制限 | 操作・通知・暗号処理・鍵取得・再接続・送達確認の待機状態を有限に保つ。繰り返し操作や障害で保持状態が増え続けない |
| 秘密情報と表示 | 資格情報・鍵・本文を公開状態、React Context・props、状態管理、デバッグ、ログへ露出させない。外部入力を実行可能な HTML として描画しない |

権限や鍵状態の再確認期限では、通知の全欠落、ブラウザーの処理中断・復帰も検証する。
バックグラウンド化・スリープなどでブラウザーが処理を停止している間、Browser SDK が期限どおりに確認・停止処理を実行できるとは保証しない。
復帰時には権限・鍵状態・期限を再確認し、安全性を確認できるまで対象の新規送信を再開しない。
再接続や再試行だけで期限を延長せず、確認できなければ対象の新規送信を停止する。
ほかの参加端末の更新・復旧待ちによって、正常な参加端末の通信を無期限に妨げない。

### 共通の検証方法と結果の記録

性能試験では、参加端末・ブラウザー、発行・購読数、コーデック、解像度、フレームレート、DataChannel 負荷、E2EE、ネットワーク条件を固定する。
CPU・メモリ・帯域、操作完了時間、受信・再生開始時間、再接続・移行時の中断時間を記録する。
エンコーディング停止・再開は、送信ビットレート、CPU 使用量、再開時間、デコード開始時間を測定する。
合否基準は試験前に定め、測定完了と目標達成を区別する。

検証には、共通の実装・検証方針を適用する。

| 検証方法 | 重点対象 |
|---|---|
| TLA+ によるモデル検査 | 非同期操作、状態同期、再接続・移行、終了との競合、権限・鍵状態の期限、共有資源の所有 |
| Fuzzing | 通知・操作結果・受信データの入力、形式・サイズ・対象・更新順序、ライブラリとの接続部分 |
| Property-based Testing | 操作と通知の列、重複・欠落・順序逆転、再試行、鍵更新、所有・解放、状態の復活防止 |
| 形式的な証明の評価 | 状態更新、識別情報の対応、カウンター・期限・資源管理の数学モデルや性質について、Lean 4 などの適合性を評価する |

TLA+・Lean 4 による数学モデルや性質の検証と、実際の TypeScript 実装コードの検証を区別する。
モデルと実装の対応を確認し、モデルの検証成功だけで TypeScript 実装まで検証済みとは扱わない。
Verus・Aeneas は Rust 向けの検証手段として扱い、TypeScript 実装を直接検証できるものとはしない。
Rust で実装する部分に適用を検討する場合も、その範囲を区別する。

モデルやライブラリ単体の検証と、実際の Client SDK・ブラウザー・サーバーを組み合わせた統合試験を区別する。
ブラウザー内部の WebRTC や既存暗号ライブラリを、独自に検証し直すことは一律に要求しない。
Client SDK の設定・呼び出し・状態管理・結果の扱いは検証対象とする。

結果には、ブラウザー・React・Client SDK・サーバー・依存ライブラリのバージョン、機能の対応状況、設定、試験条件、検証範囲と観測結果を記録する。
Node.js・React Native・Python・Go は、今回の対応確認の対象に含めない。
