# Signaling による参加・接続確立・再接続・退出

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## 参加・退出

### 参加要求の確認と接続の準備

参加要求を受け取った Signaling は、参加 JWT を検証し、対象ルームへの参加権限を確認する。ルームの存在や参加者 ID を知っているだけでは、参加を許可しない。対象ルームが未作成の場合は、JWT が `room.create` と `room.join` の両権限を持つときだけ、最初の参加と同じ処理でルームを作成する。同じルームへの並行した初回参加では、ルーム作成・SFU 割り当て・参加登録を一意に確定する。参加を許可した後も、発行・購読・データ送信には個別の権限を適用する。

Signaling は、ルーム ID、参加者 ID、参加端末、Signaling 接続、WebRTC 接続をそれぞれ識別する。同じ参加者からでも端末ごとに登録し、その登録と端末を操作する接続を認証済みの参加者に対応付ける。別の参加端末を操作・引き継ぐ権限は、識別情報の指定だけでは得られない。再接続や SFU 移行で接続だけが変わる場合は、既存の参加端末を引き継ぐ。

最初の参加端末を受け入れるときはルームに SFU を割り当て、割り当て済みの場合は現在の配置と移行状態に従って接続先を決める。同時に複数の初回参加要求が届いても、通常時は同じルームの配置を一つに保つ。割り当ての詳細は [SFU の配置・移行・退役](../sfu/placement.md) に従う。

参加を受け入れた端末には、現在の参加端末、発行・購読、必要な接続情報のうち権限で許可されたものを通知する。初期状態とその後の変更の欠落・重複は、[再接続](#再接続)で定める同期方法で確認する。Browser SDK には、要求の受け付け、参加端末の登録、WebRTC 接続の確立、E2EE の準備のうち、何が完了したかを通知する。WebRTC 接続の準備は [接続情報の交換](#接続情報の交換) に従い、Signaling 上の登録だけでメディア・データの送受信は許可しない。

参加要求が再送されたり結果通知が失われたりした場合は、既存状態と照合してから未処理かどうかを判断し、参加端末・SFU 割り当て・資源確保・参加イベントの重複を防ぐ。途中で失敗した場合は、確定した参加状態と、有限の保持期限・資源上限を適用する準備中の状態を分けて整理する。資源の解放結果が不明な場合の照合と回収は [共通の資源管理](../platform/resources.md#結果が不明な場合の照合と回収) に従う。

### 退出の対象と通信の終了

通常の退出要求では、要求元の参加端末の発行・購読・DataChannel の通信を終了し、ほかの参加端末の通信を継続する。同じ参加者の別端末まで退出させる操作では、対象と権限を別に確認する。管理権限による除外、ルーム削除、通話時間上限に達した場合は、それぞれの対象となる参加端末の通信を終了する。Signaling の一時切断を検出した場合は、直ちに通常の退出とせず、[再接続](#再接続)で定める猶予と引き継ぎの条件を適用する。

Signaling は、退出・除外の受け付けと、D-Plane による通信停止、資源解放、E2EE の鍵状態への反映を分けて扱う。受け付けの時点では、後続の処理を完了として通知しない。Browser SDK には終了理由を通知し、明示的な退出・除外・ルーム削除・通話時間上限による終了を自動再接続で取り消さない。要求の再送や完了通知の遅延があっても、退出済みの参加端末は復活させない。

Management からの強制切断は、[Management と Signaling の通信](../platform/management.md#management-と-signaling-の通信)の Pub/Sub コマンドバスで受け取る。Signaling は `commandId` で重複を排除し、対象限定コマンドとして対象 Session・Participant を保持するインスタンスだけ処理する。実行結果を `signaling` schema の入退出履歴と管理コマンド状態に記録し、結果イベントを Management へ返す。結果イベントが届かない場合も、Management は受け付けや通知の送信を完了として扱わない。

参加・退出に伴う鍵の配布・更新と参加端末ごとの完了条件は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。E2EE の秘密鍵・復号鍵は Signaling へ渡さない。

### 最後の参加端末が退出した後の割り当て解除

最後の参加端末が退出した場合、現在の参加状態と進行中の処理を確認し、継続に必要な利用がなくなった SFU の通信資源を解放して割り当てを解除する。新規参加と退出処理が並行している場合や再接続待ちの端末がある場合は、使用中または継続が必要な割り当てを維持する。解除対象は現在の参加状態と割り当てに照合し、遅延した退出・解放処理が新しい参加状態や割り当てに及ばないようにする。排他制御や状態管理の実装方式は固定しない。ルーム情報は明示的な削除まで保持する。

Signaling は参加・退出・除外・発行・購読の開始終了と、TURN・SFU・DataChannel の資源計上イベントを `signaling` schema に記録する。TURN・SFU は DB に接続しないため、計上イベントを Signaling へ報告する。Signaling は報告元・対象・期間を検証し、1 分単位の集計を正本として管理する。

## 接続情報の交換

Signaling は、参加端末と、割り当てられた SFU の WebRTC 接続を確立・更新する情報を交換する。
参加端末同士の P2P 接続を確立する情報交換には使用しない。

交換する情報は、次を含む。

| 情報 | 用途 |
|---|---|
| SDP の Offer / Answer | メディア・DataChannel と WebRTC Transport の条件を交渉する |
| ICE 候補と ICE 候補の収集完了情報 | 利用可能な通信経路を通知する |
| ICE 資格情報 | ICE 接続確認と ICE restart に必要な情報を通知する |
| DTLS フィンガープリントとロール、tls-id | 接続相手の証明書確認と DTLS Association の識別・確立・再確立の判定に使用する |
| 発行・購読との対応情報 | メディアの送受信を、許可された発行・購読に対応付ける |

### 情報の対応確認と交渉

接続情報を受け取った Signaling は、クライアントからの情報なら認証済みの接続が操作できる参加端末と、SFU からの情報なら C-Plane が割り当てた SFU・接続と照合する。クライアントが指定した SFU やフィンガープリントを、信頼済みの情報として別の接続へ流用しない。

各情報をルーム、参加端末、対象の WebRTC 接続、交渉、必要な ICE 世代に対応付けて扱う。これにより別端末・接続・交渉の情報の混入や、古い情報による確定済み状態の上書きを防ぐ。具体的な識別子の形式は固定しない。

Offer / Answer は対象ブラウザーの状態遷移に整合する順序で処理し、Answer を対応する Offer に結び付ける。重複・遅延した Answer は別の交渉へ適用せず、双方が同時に Offer を生成した場合は競合を検出して整合する交渉へ収束させる。ブラウザーとの交渉は [JSEP（RFC 9429）](https://www.rfc-editor.org/rfc/rfc9429.html#section-3.2)に従う。発行・購読の変更に伴う再交渉でも操作権限を確認し、SDP の内容だけで未許可の発行・購読・データ送信を有効にしない。

ICE 候補は収集後に順次通知できるようにし、適用先の接続と ICE 世代を確認する。終了済みの世代や別接続の候補は適用せず、SDP より先に届いた候補を待機させる場合は、件数・総バイト数・保持時間を制限する。

### DTLS の相手確認と再確立

Signaling は、DTLS フィンガープリントを、認証した参加端末または割り当てた SFU と、対象の接続に対応付けて管理する。SDP で通知したフィンガープリントとの証明書の照合は [WebRTC Transport](../transport/secure-transport.md#暗号化通信の確立維持) が行うため、SDP の交換成功だけでは相手の確認は完了しない。

DTLS Association の再確立が必要かどうかは、フィンガープリント集合の変更・追加・削除、交渉された DTLS ロールの変更、tls-id の変更による明示的な再確立要求を考慮して判断する。tls-id の有無に応じた互換性処理を含め、[RFC 8842 §3–5](https://www.rfc-editor.org/rfc/rfc8842.html#section-3.1)に従う。ICE restart は DTLS Association の再確立とは別に判断し、[RFC 8842 §5.5](https://www.rfc-editor.org/rfc/rfc8842.html#section-5.5)の条件に従って、ICE 資格情報の変更だけで証明書やフィンガープリントの変更を許可しない。

フィンガープリントの変更を許可するのは、権限を確認した接続の再確立、SFU 移行、証明書更新などに伴い、新しい DTLS Association を確立する正当な交渉に対応する場合に限る。新しい DTLS Association の確立には、権限を確認した Offer / Answer の成功と、対象の接続相手の検証を必要とし、新しい証明書も通知したフィンガープリントと照合する。

### 移行中の交渉と結果通知

SFU 移行中、Signaling は接続情報と交渉状態を新旧の接続ごとに管理する。旧接続から遅延した通知が届いても新接続の情報に適用せず、新接続の準備に失敗した場合もその失敗だけで旧接続の情報を破棄しない。通信を継続する場合も切り戻す場合も、現在の権限と暗号条件を適用する。

交渉と ICE 候補の交換には、処理期限、同時処理数、メッセージサイズ、保持状態の上限を設ける。不正・不整合な情報は拒否し、対象と理由を識別できる結果を、ICE の秘密情報などを含めず Browser SDK へ通知する。

接続が成立しても、E2EE の鍵状態の準備完了は別に扱う。公開鍵や鍵管理メッセージの対応は [E2EE・鍵管理](../e2ee/key-management.md) に従って確認し、秘密鍵・復号鍵は Signaling へ渡さない。

## 再接続

### 切断を検出したとき

Signaling の切断を検出したら、参加端末を再接続待ちとして扱う。切断の検出条件と再接続猶予は設定可能とし、猶予には有限の期限を設ける。Browser SDK は再接続中であることを通知し、Signaling 接続の回復を試みる。この間も既存の WebRTC 通信が利用可能で、現在の権限と暗号条件を満たす場合は通信を継続できる。

Signaling が切断されている間も、D-Plane は現在の参加権限・通信権限と失効情報を確認する。権限が失効した場合は、[認可仕様の反映期限](../auth/authorization.md#有効期限権限変更失効の反映)内に対象通信を停止する。必要な権限情報を確認できない場合は、最後に確認した権限での継続を有限の期間に限り、その期限までに有効な権限を確認できなければ対象通信を停止する。Signaling の再接続や権限情報の取得を試みただけでは、その期限は延びない。権限情報の同期方法と有効期限の管理方式は固定しない。

### 接続の引き継ぎと状態同期

再接続要求を受けた Signaling は参加者を再認証し、現在の参加権限と対象の参加端末を引き継ぐ権限を確認する。参加者 ID、参加端末の識別情報、以前の接続情報を知っていることだけでは引き継ぎを許可しない。

引き継ぎでは、対象の参加端末を操作できる有効な Signaling 接続を決める。複数の要求が並行しても、参加端末を重複登録せず、どの接続が操作権限を持つかを一貫して決定する。成立後は旧接続の操作や遅延した要求による状態変更を防ぎ、引き継ぎと並行して届く要求や処理中の操作結果は、現在の接続・参加状態と照合して扱う。通知の到着順だけで接続の所有関係を巻き戻さない。排他制御や識別子の形式は固定しない。

再接続時は、次の状態を同期する。

| 対象 | 同期する内容 |
|---|---|
| 参加状態 | 現在の参加端末、権限、退出・除外・ルーム終了の状態 |
| 発行・購読 | 現在有効な発行・購読と、処理中の変更 |
| 接続状態 | 担当 SFU、移行状態、対象の WebRTC 接続と交渉・ICE 世代 |
| 時間制限 | 通話時間の上限、SFU の退役期限、必要な予告 |
| E2EE | 許可された鍵状態へ同期するために必要な参加・更新情報 |

取得した状態と変更通知は、共通の基準に対応付ける。初回取得でも再取得でも、取得中に起きた変更を取り込み、変更通知への切り替えで欠落が生じないようにする。同じ通知は二重に反映せず、古い通知で現在の状態を巻き戻さない。

再接続時に、最後に反映した位置から変更を取得できる場合は、差分で状態を同期する。履歴の欠落や保持期限切れなどで差分を使えない場合は、現在の状態を取り直す。履歴・待機通知・同期処理には、件数・総メモリ量・保持期間・処理期限の上限を設ける。

切断前に送信した操作の結果が不明なら、受け付け応答の有無にかかわらず、サーバーの状態と照合して処理済みかどうかを確かめる。再送があっても発行・購読・接続・資源確保の重複を防ぐ。照合後も結果を確定できなければ、Browser SDK に結果不明を通知する。

### 再接続の完了と猶予切れ

Signaling は、再認証・接続の引き継ぎ・必要な状態同期がそろった時点で、Browser SDK へ再接続完了を通知する。接続が開いただけの場合や一部の通知しか届いていない場合は、完了条件がそろうまで通知を待つ。未認証の接続試行、未完了の同期、同じ通知の再送では猶予を延ばさない。

WebRTC 通信が失われた場合は、現在の配置と接続情報に従って再確立する。通信を利用できる場合は、Signaling の復旧だけを理由に接続を作り直さない。再確立や SFU 移行でも、通話時間の起点と退役期限を維持する。暗号化通信の再開には、Signaling の復旧後も [E2EE・鍵管理の同期・復旧条件](../e2ee/key-management.md#再接続sfu-移行鍵状態を失った場合の扱い)に従って鍵状態を確認する。

猶予内に復帰できなかった場合は、その参加端末の参加を終了して、通信停止・鍵管理への反映・資源解放を進める。SFU の割り当てを解除する前に、新しい参加やほかの参加端末の再接続待ちを [退出時の条件](#最後の参加端末が退出した後の割り当て解除)に従って確認する。終了後は遅延した要求で参加状態を復活させず、その後の接続は現在の権限を確認する新しい参加として扱う。明示的な退出・除外・ルーム削除・通話時間上限による終了も自動再接続の対象外とする。

## 自作範囲・既存実装の利用

Signaling サーバーは、TypeScript の C-Plane として実装する。
C-Plane と D-Plane の分離は、論理的な責務の分離とし、実行プロセスの分離を必須としない。
Signaling の公開サーバーには Fastify を使用し、WebSocket 接続には `@fastify/websocket` を使用する。Cloud Run は WebSocket を長時間 HTTP request として扱う。そのため Signaling は request timeout の上限内で接続を維持し、期限切れ・切断後の再接続と状態同期を必須にする。
Rust Worker の実行方式は Wasm、Native Addon、独立 Worker を選択肢として残し、後続の技術選定で決定する。公開サーバー・リクエスト受付は TypeScript host が担い、Rust をサーバー公開プロセスとして使用しない。

| 自作する部分 | 内容 |
|---|---|
| 参加・退出の制御 | 参加 JWT の検証、未作成ルームの初回参加時作成、参加端末の登録、権限の適用、退出・除外と通信停止の調整 |
| 接続情報の交換 | SDP・ICE 候補・DTLS 情報を、対象の参加端末・接続・交渉へ対応付ける処理 |
| 交渉の制御 | Offer / Answer の対応、競合、重複・遅延・期限切れの処理 |
| 再接続と状態同期 | 接続の引き継ぎ、差分・現在の状態の同期、結果不明の操作の照合 |
| D-Plane との連携 | 接続準備・変更・終了の指示、権限・失効の反映、処理結果の確認 |
| 制御資源の管理 | 接続、処理中の操作、履歴、入退出・資源計上、待機通知、タイマーの上限と解放 |

ルーム配置などの C-Plane 内の共通機能は、同じ管理状態と権限判定を利用する。
Signaling 専用に別の状態を管理し、それを独立した判断基準にしない。

HTTP / WebSocket、TLS、認証情報の署名・検証、入力スキーマ検証、永続化、メッセージ配送には、既存の汎用ライブラリや基盤を利用できる。
採用した基盤が保証する順序・重複・永続性と、Signaling 側で保証する条件を区別する。

SDP などの形式の読み書きには、形式処理用の既存ライブラリを利用できる。
解析の成功とは別に、操作権限と接続・交渉との対応を検証する。

ブラウザー側の Offer / Answer の生成・適用と WebRTC の状態遷移は、Browser SDK がブラウザーの WebRTC API を使って制御する。
サーバー側の ICE、DTLS、SRTP/SRTCP、SCTP の通信処理は、Rust の D-Plane が担う。
Signaling に同じプロトコル処理を重複実装しない。

Signaling は、情報交換や操作の受け付けと、WebRTC Transport の接続成立・相手認証・通信停止の完了を区別する。
D-Plane の処理が成功したことを確認せず、通信処理まで完了したと通知しない。

E2EE の鍵管理メッセージは、[E2EE・鍵管理](../e2ee/key-management.md)に従って配送・対応確認を行う。
Signaling 内で参加端末の秘密鍵や本文の復号鍵を保持しない。

採用する既存実装のバージョン、設定、依存する機能を記録する。
実際の組み込み構成で、資源上限、並行処理、再接続、障害時の動作を確認する。
セキュリティ修正を追跡し、更新できる構成とする。

実装と検証には、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)を適用する。
Signaling 固有の検証対象と確認する結果は、「受け入れ条件」で定める。

## セキュリティ

ブラウザーと Signaling 間の通信は、HTTPS / WSS によって保護する。
クライアントは接続先を検証し、暗号化された接続の失敗を理由に平文通信へ切り替えない。

接続時に参加者を認証し、各操作で現在の権限と対象へのアクセスを確認する。
一度認証した接続であることだけを理由に、失効後も操作を許可しない。

参加者・参加端末・ルーム・発行・購読・WebRTC 接続の識別情報を、認証した接続の操作範囲に照合する。
識別情報を知っていることや、メッセージの形式が正しいことだけで操作を許可しない。

状態取得、差分同期、通知購読にもアクセス制御を適用する。
操作を拒否する場合だけでなく、別のルームや参加端末の接続情報・権限情報・鍵管理メッセージを取得できないようにする。

ブラウザーからの WebSocket 接続では、許可された Origin を確認する。
Origin の検証を利用者認証の代わりにしない。
HTTP Cookie などブラウザーが自動送信する資格情報を使用する場合は、第三者のサイトから本人の意図しない接続・操作を実行されないようにする。
[RFC 6455 §10.1–10.2](https://www.rfc-editor.org/rfc/rfc6455.html#section-10.2)を踏まえて適用する。

認証方式、資格情報の受け渡し、更新・失効の条件を定める。
資格情報を URL やログ、エラー報告へ露出させない。
接続の引き継ぎに用いる情報も保護し、その所持だけで現在の権限確認を省略しない。

権限確認から処理の実行までに、退出・失効・接続の引き継ぎ・SFU 移行が起きる場合を考慮する。
処理対象と現在の権限・状態との対応を確認し、古い接続や失効した権限による操作を、遅延した実行や再送によって成立させない。

Signaling の切断中も含む D-Plane の権限確認と転送停止は、「再接続」に従う。
権限・失効情報の反映期限を、単なる再接続や再試行で延長しない。

C-Plane と D-Plane の境界では、指示元、操作対象、利用権限、処理結果との対応を確認する。
同一プロセスで実行する場合も、論理的な境界で必要な検証を省略しない。
別プロセス間の通信では、共通のセキュリティ条件に従って相互認証と通信の保護を行う。

受信メッセージは、型・形式・長さ・値の範囲・対象状態を実行時に検証する。
TypeScript の型定義だけを入力検証の根拠にしない。
SDP、ICE 候補、鍵管理メッセージにも、用途ごとの検証と資源上限を適用する。

接続数、未認証接続、認証試行、操作数、同時交渉数、履歴、待機通知、送受信バッファに設定可能な上限を設ける。
送信元・参加者・参加端末・ルーム・サーバー全体のうち、対象に応じた範囲で制限する。

分割入力、低速送信、大量の ICE 候補、通知を読み取らない接続でも、資源上限を超えない。
圧縮や再構成を利用する場合は、展開後・再構成後の量も制限する。
認証前の接続や未完了の処理にも有限の期限を設ける。

制限に達した場合は、新規受け付けの抑制、操作の拒否、対象接続の終了を、制限対象に応じて行う。
エラー応答も処理量・送信量に含め、過負荷によって認証・認可や入力検証を省略しない。
資源の計上・解放は、[共通の資源管理](../platform/resources.md#資源管理)に従う。

本プラットフォームは、認証した参加者・接続とフィンガープリントの対応関係を管理する Signaling サーバーを信頼する。
HTTPS / WSS による経路の保護だけでは、Signaling サーバー自身による不正なフィンガープリントの通知を防げない。

参加者・接続との対応関係と、SDP 更新時のフィンガープリント変更の許可条件は、「接続情報の交換」で定める。
E2EE の公開鍵の対応関係について信頼する範囲と、秘密情報を渡さない条件は、[E2EE の信頼モデル](../e2ee/key-management.md#保護する情報と信頼モデル)に従う。

認証情報、ICE の秘密情報、TURN 資格情報、E2EE の秘密鍵・復号鍵を、ログやエラー通知へ出力しない。
SDP や受信メッセージの全文を、そのままログへ記録しない。
通知には、対象と失敗理由の判別に必要な情報だけを含める。

## 受け入れ条件

実際の Browser SDK、C-Plane、D-Plane を組み合わせ、正常動作に加えて、要求・通知の欠落、重複、遅延、順序逆転、接続障害、処理結果の消失を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 参加と権限 | 参加 JWT と対象ルームへの参加権限を確認する。参加成功だけで発行・購読・データ送信を許可せず、`room.create` 権限がない未作成ルームを自動作成しない |
| 未作成ルームの作成 | `room.create`・`room.join` 権限付き JWT の初回参加だけがルームを作成する。並行した初回参加でルーム・SFU 割り当て・参加登録を重複させない |
| 参加端末と接続の識別 | 同じ参加者の複数の参加端末を区別する。識別情報の指定だけで別の参加端末を操作・引き継ぎできず、接続変更だけで参加端末を重複登録しない |
| 同時参加と配置 | 同じルームへの並行した初回参加で、通常時の SFU 配置を重複生成しない |
| 退出と参加の競合 | 最後の参加端末の退出と新規参加・再接続が競合しても、使用中または継続が必要な割り当てを解除しない。古い終了処理で新しい状態を変更しない |
| 退出の対象 | 通常の退出は要求した参加端末だけに適用する。別の参加端末の終了には対象と権限を確認する |
| 明示的な終了 | 退出・除外・ルーム削除・通話時間上限を自動再接続で取り消さず、終了理由を通知する |
| 処理の完了 | 要求の受け付け、参加登録、WebRTC Transport の接続・通信停止、資源解放、E2EE の準備・更新を区別する。未確認の処理を完了として通知しない |
| 管理コマンド | `commandId` で重複を排除し、対象限定コマンドを対象 Session・Participant を持つインスタンスだけ実行する。結果イベントが不明でも完了と扱わない |
| 履歴と資源計上 | 入退出・除外・発行・購読と TURN・SFU・DataChannel の計上を対象・期間に対応付けて記録し、欠測をゼロとして扱わない |
| 接続情報の対応 | SDP、Answer、ICE 候補、ICE 候補の収集完了情報を、対象の参加端末・接続・交渉・ICE 世代へ適用する。別接続や終了済み世代の情報を混入させない |
| 再交渉と競合 | 同時 Offer、再交渉の重複・遅延・失敗を処理し、整合する状態へ収束する。SDP の内容だけで操作権限を増やさない |
| DTLS Association | フィンガープリント集合、交渉されたロール、tls-id の変更と互換性条件に従って再確立を判定する。新しい DTLS Association にも正当な交渉と接続相手の検証を要求する |
| ICE restart | DTLS Association の再確立とは独立に判定する。ICE 資格情報の変更だけで証明書・フィンガープリントの変更を許可しない |
| SFU 移行 | 新旧接続の交渉状態を区別する。旧接続の通知で新接続を上書きせず、準備失敗時の継続・切り戻しにも現在の権限と暗号条件を適用する |
| Signaling の一時切断 | 利用可能で権限・暗号条件を満たす WebRTC 通信を、Signaling 切断だけで終了・再作成しない |
| 切断中の権限失効 | D-Plane が失効を確認し、設定した期限内に対象通信を停止する。権限情報を確認できない場合も期限で停止し、再接続・再試行だけで期限を延長しない |
| 接続の引き継ぎ | 再認証と現在の権限確認を行う。並行する再接続で操作権限を一貫して決定し、引き継ぎ後の旧接続・処理中の旧要求で状態を変更しない |
| 状態同期 | 初回取得と再取得の両方で、取得中に起きた変更を取り込む。差分の履歴が失われた場合は現在の状態を取得し直し、重複・遅延通知で二重反映や巻き戻りを起こさない |
| 結果不明の操作 | 応答を受け取れなかった場合も、受け付け応答が届いて完了通知を確認できなかった場合も、再接続時にサーバーの状態と照合する。再送で発行・購読・接続・資源確保を重複させず、照合しても確定できなければ Browser SDK に結果不明を通知する |
| 再接続の期限 | 未認証の試行や未完了の同期だけで猶予を延長しない。猶予終了後の参加状態を遅延要求で復活させず、通話時間の起点や SFU の退役期限も変更しない |
| 読み取りと通知の認可 | 状態取得、差分同期、通知から、未許可のルーム・参加端末の接続情報、権限情報、鍵管理メッセージを取得できない |
| ブラウザー接続の保護 | HTTPS / WSS の接続先を検証し、平文へ切り替えない。未許可 Origin と、採用する認証方式に対する第三者サイトからの不正な接続・操作を拒否する |
| C-Plane / D-Plane の境界 | 採用した実行方式で、指示元・対象・権限・処理結果の対応を確認する。同一プロセスでも必要な検証を省略せず、別プロセス間の通信は相互認証して保護する |
| 不正入力と資源上限 | 不正な型・形式・長さ・値、過大な SDP・ICE 候補、低速送信、読み取りの遅い接続でも上限を超えない。過負荷時に検証を省略せず、展開・再構成後の量とエラー応答も計上する |
| E2EE と機密情報 | Signaling の復旧だけで E2EE の準備完了と扱わない。秘密鍵・復号鍵を Signaling に渡さず、認証情報・ICE の秘密情報・TURN 資格情報やメッセージ全文をログへ出力しない |

検証には、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)を適用する。
Signaling では、次を重点対象とする。

| 検証方法 | 重点対象 |
|---|---|
| TLA+ によるモデル検査 | 参加・退出・SFU 割り当て解除の競合、接続の引き継ぎ、権限失効と実行の競合、初期状態と変更通知の同期 |
| Fuzzing | メッセージと SDP・ICE 候補の入力検証、不正な型・長さ・値、分割入力、展開・再構成処理 |
| Property-based Testing | 参加・退出・再接続・再交渉の操作列、要求・通知の重複と順序逆転、状態同期、権限と資源計上の不変条件 |

モデル検査では、安全性に加え、通信や処理が回復する前提の下で、同期・引き継ぎ・終了処理が完了する活性も確認する。
成立に必要な前提と、検証範囲の制限を明示する。

モデル検査、Fuzzing、Property-based Testing の結果と、実際の Browser SDK・C-Plane・D-Plane を組み合わせた統合試験の結果を区別して記録する。
各手法の成功だけで、統合試験も成功したとは扱わない。

Chrome・Firefox・Safari と実際の Browser SDK を使い、参加、再交渉、ICE restart、再接続、SFU 移行を確認する。
ブラウザーで確認した条件と、検証用クライアントや障害注入で確認した条件を区別する。

結果には、ブラウザー・Browser SDK・サーバー・ライブラリのバージョン、実行方式、認証方式、通信条件、設定した期限・資源上限、検証範囲と観測結果を記録する。
認証方式や具体的な制限値は、本節では固定しない。
