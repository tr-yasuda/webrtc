# DataChannel 本文の E2EE

DataChannel 本文の暗号化・復号と配送先に応じた保護を定める。信頼モデル、鍵更新完了、旧鍵の保持、状態喪失からの復旧は [鍵管理仕様](key-management.md)に従う。配送と送達確認は [DataChannel 配送仕様](../datachannel/delivery.md)に従う。

## 前提

共通の前提は [共通仕様](../platform/overview.md#前提)に従う。

## 保護する情報と信頼モデル

暗号化の準備や鍵の検証に失敗した場合、保護対象の内容を平文へ切り替えて送信しない。

## DataChannel 本文の保護

送信元の参加端末でアプリケーションメッセージの本文を暗号化し、SFU は本文を復号せずに転送する。サーバーが転送に使う宛先や購読の識別情報は暗号化する本文と分け、参加端末と SFU 間では DTLS による保護も維持する。

### 宛先の決定と暗号化

メッセージごとに受信を許可された参加端末の範囲を定め、復号鍵の配布範囲を受信権限と一致させる。特定の端末だけが宛先なら、その本文を復号できる鍵を範囲外の端末に配布・共用しない。同じルームの参加端末であっても、メッセージごとの受信権限を適用する。

DataChannel の本文には、形式のバージョン、鍵識別子、Nonce の決定に必要な情報、暗号文、認証タグを含む形式を定める。
暗号処理には、既存実装による許可された AEAD を使用する。

メディアと DataChannel で暗号化用の鍵を共用しない。
送信元の参加端末ごとに鍵を分け、鍵の用途を区別して導出・配布する。
ほかの送信元の参加端末の鍵は、Browser SDK では復号用途に限定する。
この制限では、悪意ある正規参加端末による送信者の偽装を暗号学的に防げない。

暗号文を、対象ルーム・鍵状態・送信元の参加端末・論理チャネルに結び付けて認証する。
別のルームや論理チャネルのメッセージとして受け入れない。
論理チャネルは、接続ごとの SCTP ストリーム番号とは区別して識別する。

複数の論理チャネルからの並列送信、再接続、SFU 移行中の新旧接続での送信でも、別の暗号化処理に同じ鍵と Nonce の組を使わない。この条件を保証できなければ、その鍵での新規暗号化を停止する。

### 鍵更新が送信待ちのメッセージに重なった場合

参加・退出に伴う鍵更新と送受信の許可は、[鍵管理仕様の参加端末ごとの完了条件](key-management.md#鍵の配布参加退出鍵更新)に従う。
未送信のメッセージは、平文か暗号化済みかにかかわらず、実際の送信時点で鍵状態と送信先への配布権限を再確認する。更新が必要な状態では旧鍵での新規送信を停止する。旧鍵での新規送信が許可されない場合、現在の受信権限に適合する鍵で暗号化するか、送信を中止する。再暗号化でも、別の暗号化処理に同じ鍵と Nonce の組を使わない。

### 受信時の検証とアプリケーションへの引き渡し

受信側の参加端末は、暗号文とメッセージの識別情報を認証し、使用権限の確認に成功した本文だけをアプリケーションへ渡す。重複・リプレイの判定状態は、暗号文の認証に成功してから更新する。SFU 移行で同じメッセージを重複受信しても、アプリケーションへの引き渡しは一度に限る。認証に失敗した暗号文は破棄し、鍵の取得や復号に失敗した場合も平文には切り替えない。

配送方式で許容される順序逆転や欠落は受け入れ、欠落したメッセージを無期限に待たない。接続をまたぐ配送保証・順序保証・再送条件は [DataChannel 配送仕様](../datachannel/delivery.md#データ配送)に従う。相手アプリケーションへの送達は、参加端末と SFU 間の SCTP 配送とは別に確認する。送信できなかった結果と、送達を確認できない状態は Browser SDK から通知する。

メッセージ長と暗号化による増加分を含む送信サイズに上限を設ける。暗号化・復号待ち、未知の鍵を待つ暗号文、順序制御、重複・リプレイ判定の状態には、件数・総メモリ量・保持期間の上限を適用し、鍵の取得要求にも上限を設ける。

## 既存実装の利用条件

AEAD、ハッシュ、鍵導出、署名、公開鍵暗号、安全な乱数生成には、既存の暗号実装を利用する。
暗号アルゴリズムそのものを独自実装しない。

秘密鍵、復号鍵、平文を、ライブラリのログ、エラー報告、テレメトリーへ出力しない。
C-Plane・D-Plane へ鍵を送らずに利用できる構成とする。

対象の Chrome・Firefox・Safari で、実際のメディア処理と DataChannel に組み込んで動作を確認する。
ブラウザーごとに、E2EE に必要な API の対応状況と、実際に動作を確認したブラウザーバージョンを記録する。
SFrame のメディア処理への組み込みでは、必要な API が利用できることと、その API を用いて実際に暗号化・復号できることを分けて確認する。
API が利用できることだけで、E2EE の動作を確認済みとは扱わない。
必要な機能を利用できない環境では、非対応であることを Browser SDK から通知し、暗号化を無効にして接続を継続しない。

採用する実装、バージョン、設定、組み込み構成を記録する。
セキュリティ修正を追跡し、更新時には影響する相互接続性と安全性の条件を再確認する。
必要な保証を確認できない実装は採用しない。

## 受け入れ条件

採用する暗号実装・鍵管理方式を、Browser SDK と実際に組み合わせた構成で試験する。
正常な通信に加え、通知の欠落・遅延・重複・順序逆転、接続障害、状態喪失を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| メディアと DataChannel の保護 | 音声・カメラ映像・画面共有・DataChannel 本文を参加端末間で暗号化・復号できる。C-Plane・D-Plane に本文の平文や E2EE の秘密鍵・復号鍵を渡さない |
| 鍵の分離と配布範囲 | メディアと DataChannel の鍵を共用しない。特定の参加端末宛ての本文を、受信権限のない同一ルームの参加端末が、自分に配布された鍵や導出可能な秘密情報で復号できない |
| カウンター・Nonce | 複数の発行、Simulcast、複数の論理チャネル、並列処理、再接続、新旧 SFU への並行送信で、同じ鍵と Nonce による別の暗号化処理を行わない |
| 不正な暗号文とメタデータ | 改変された暗号文・認証タグ・認証対象メタデータを受け入れない。認証前の内容を再生やアプリケーションへ渡さず、不正入力によってリプレイ判定状態を進めない |
| 重複・順序逆転・配送確認 | 正当な順序逆転や配送方式上の欠落を処理し、同じメディア・メッセージを重複して再生・通知しない。SFU への SCTP 配送だけでは、相手アプリケーションへ送達済みと通知しない |
| 未送信メッセージと鍵更新 | 平文・暗号化済みの両方について送信時点の鍵状態と受信権限を確認する。旧鍵による新規送信が許可されなければ、適切な鍵で再暗号化するか送信を中止する |
| 資源制限 | 未知の鍵、不正入力、大量の待機メッセージ、並行する更新・復旧処理でも、ライブラリ内部を含む資源上限と処理期限を超えない |
| 非対応・失敗時の動作 | API 非対応、鍵の検証・取得・復旧失敗を Browser SDK から通知する。平文への切り替え、E2EE の無効化、検証条件の緩和によって通信を継続しない |
| ブラウザー相互接続 | Chrome・Firefox・Safari 間で、必要 API の利用可否と実際の暗号化・復号を別々に確認する。音声・映像・画面共有・DataChannel と鍵更新を、対象のブラウザー組み合わせで確認する |
| 標準処理と機密情報 | 対象処理が標準のテストベクトルと一致する。通常動作・異常処理のログ、エラー報告、テレメトリーに秘密鍵・復号鍵・本文の平文を出力しない |

試験結果には、ブラウザーとそのバージョン、必要 API の対応状況、採用ライブラリとバージョン、暗号スイート、鍵管理方式、設定した期限・資源上限を記録する。
未実施・非対応の条件を、確認済みの条件と区別する。

秘密保持の試験は、本仕様の信頼モデルと鍵漏洩時の前提に従って行う。
悪意ある Signaling による鍵の対応関係の偽装への耐性や、対称鍵を持つ正規参加端末に対する送信者本人性を、試験合格によって保証したとは扱わない。

既存実装の選定には、[鍵管理仕様の組み込み条件](key-management.md#既存実装の利用条件)も適用する。
