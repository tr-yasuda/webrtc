# SFrame によるメディア保護

SFrame による音声・映像の暗号化・復号を定める。信頼モデル、参加端末ごとの鍵更新完了、旧鍵の保持、状態喪失からの復旧は [鍵管理仕様](key-management.md)に従う。

## 前提

共通の前提は [共通仕様](../platform/overview.md#前提)に従う。

## 保護する情報と信頼モデル

暗号化の準備や鍵の検証に失敗した場合、保護対象の内容を平文へ切り替えて送信しない。

## SFrame による音声・映像の保護

音声・カメラ映像・画面共有を、参加端末で SFrame により暗号化する。
受信先の参加端末は、内容を認証・復号し、認証に成功したものだけをデコード・再生へ渡す。
参加端末と SFU 間の SRTP/SRTCP による保護も維持する。

SFrame の暗号化単位と、使用するコーデックへの適用方法を送信元と受信先の参加端末で一致させる。
SFU が転送に必要とするメタデータと、暗号化する内容を区別する。

送信者ごとに暗号化用の鍵を割り当てる。
同じ参加者の別の参加端末で、一つの送信鍵を共用しない。
各参加端末では、自分の送信用の鍵と、ほかの送信者からの受信専用の鍵を区別する。
受信専用は Browser SDK における使用制限とし、その鍵を Browser SDK の暗号化処理に使用することを許可しない。
SFrame は対称鍵暗号を使用するため、受信先の参加端末が保持する鍵も技術的には暗号文の生成に使用できる。
この使用制限では、送信者の偽装を暗号学的に防止できない。

鍵識別子（KID）と、対象ルーム・鍵状態・送信元の参加端末・使用を許可された発行との対応関係を管理する。
受信した KID や RTP の識別情報だけを根拠に、新しい鍵の対応関係を登録しない。

各暗号化処理で使用する KID とカウンター（CTR）の組を再利用しない。
同じ鍵を複数の発行や Simulcast のエンコーディングで使用する場合も、並列処理を含めて重複を防ぐ。
同じ鍵と Nonce による別の暗号化処理を許可しない。
再送には、すでに生成した暗号文を使用できる。
[RFC 9605 §4.1–4.4、§6.1.2、§9.1](https://www.rfc-editor.org/rfc/rfc9605.html#section-4.1)に従う。

再接続や SFU 移行だけを理由に、同じ鍵のカウンターを初期化しない。
旧接続と新接続で並行して送信する場合も、同じ鍵のカウンター値を暗号化処理間で重複させない。
カウンターの継続を保証できない場合は、その鍵による新規暗号化を停止し、新しい鍵状態を確認してから再開する。

暗号スイートと認証タグ長は、許可されたものを使用する。
カウンターの枯渇や、暗号方式ごとの鍵の使用上限に達する前に鍵を更新する。
更新できない場合は新規送信を停止する。

鍵更新は、[鍵管理仕様の参加端末ごとの完了条件](key-management.md#鍵の配布参加退出鍵更新)に従う。
映像では、更新後の鍵で復号・デコードを開始できるキーフレームを取得できるようにする。
未更新の受信先の参加端末に合わせて、旧鍵で新規送信しない。

未知の鍵による暗号文を待機させる場合は、件数・総バイト数・保持時間を制限する。
鍵の取得要求にも上限を設ける。
認証に失敗した暗号文は破棄し、平文として扱わない。

受信側でリプレイを検出し、同じ暗号文を繰り返し再生へ渡さない。
正当な順序逆転と再送を考慮し、判定状態にも資源上限を設ける。
SFU 移行による重複受信でも、この判定を維持する。

SFrame の追加認証データに含めるメタデータを定義する。
SFU が書き換える情報との整合性を保つ。
受信側は、認証が完了するまで、そのメタデータを認証済みの情報として利用しない。
復号準備のための使用は区別する。
[RFC 9605 §9.4](https://www.rfc-editor.org/rfc/rfc9605.html#section-9.4)に従う。

SFrame の認証成功だけで、悪意ある正規参加端末による送信者の偽装を防げるとは扱わない。
送信者別の鍵管理と、送信者本人による生成の証明を区別する。
将来、送信者本人による生成の証明を必要とする場合は、SFrame とは別の認証方式を検討する。
[RFC 9605 §7.2](https://www.rfc-editor.org/rfc/rfc9605.html#section-7.2)の制約を踏まえる。

## 既存実装の利用条件

AEAD、ハッシュ、鍵導出、署名、公開鍵暗号、安全な乱数生成には、既存の暗号実装を利用する。
暗号アルゴリズムそのものを独自実装しない。

秘密鍵、復号鍵、平文を、ライブラリのログ、エラー報告、テレメトリーへ出力しない。
C-Plane・D-Plane へ鍵を送らずに利用できる構成とする。

対象の Chrome・Firefox・Safari で、実際のメディア処理と DataChannel に組み込んで動作を確認する。
ブラウザーごとに、E2EE に必要な API の対応状況と、実際に動作を確認したブラウザーバージョンを記録する。
SFrame のメディア処理への組み込みでは、必要な API が利用できることと、その API を用いて実際に暗号化・復号できることを分けて確認する。
API が利用できることだけで、E2EE の動作を確認済みとは扱わない。
必要な機能を利用できない環境では、非対応であることを Browser SDK から通知し、暗号化を無効にして接続を継続しない。

標準のテストベクトルがある処理は、それとの一致を確認する。
SFrame には [RFC 9605 Appendix C](https://www.rfc-editor.org/rfc/rfc9605.html#appendix-C) のテストベクトルを用いる。
ベクトルとの一致とは別に、鍵管理や接続移行を含む安全性を確認する。

採用する実装、バージョン、設定、組み込み構成を記録する。
セキュリティ修正を追跡し、更新時には影響する相互接続性と安全性の条件を再確認する。
必要な保証を確認できない実装は採用しない。

## 受け入れ条件

採用する暗号実装・鍵管理方式を、Browser SDK と実際に組み合わせた構成で試験する。
正常な通信に加え、通知の欠落・遅延・重複・順序逆転、接続障害、状態喪失を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| メディアと DataChannel の保護 | 音声・カメラ映像・画面共有・DataChannel 本文を参加端末間で暗号化・復号できる。C-Plane・D-Plane に本文の平文や E2EE の秘密鍵・復号鍵を渡さない |
| カウンター・Nonce | 複数の発行、Simulcast、複数の論理チャネル、並列処理、再接続、新旧 SFU への並行送信で、同じ鍵と Nonce による別の暗号化処理を行わない |
| 鍵の使用上限 | カウンターや暗号方式の使用上限に達する前に更新する。更新失敗時は、上限を超えて暗号化せず新規送信を停止する |
| 不正な暗号文とメタデータ | 改変された暗号文・認証タグ・認証対象メタデータを受け入れない。認証前の内容を再生やアプリケーションへ渡さず、不正入力によってリプレイ判定状態を進めない |
| 資源制限 | 未知の鍵、不正入力、大量の待機メッセージ、並行する更新・復旧処理でも、ライブラリ内部を含む資源上限と処理期限を超えない |
| 非対応・失敗時の動作 | API 非対応、鍵の検証・取得・復旧失敗を Browser SDK から通知する。平文への切り替え、E2EE の無効化、検証条件の緩和によって通信を継続しない |
| ブラウザー相互接続 | Chrome・Firefox・Safari 間で、必要 API の利用可否と実際の暗号化・復号を別々に確認する。音声・映像・画面共有・DataChannel と鍵更新を、対象のブラウザー組み合わせで確認する |
| 標準処理と機密情報 | 対象処理が標準のテストベクトルと一致する。通常動作・異常処理のログ、エラー報告、テレメトリーに秘密鍵・復号鍵・本文の平文を出力しない |

試験結果には、ブラウザーとそのバージョン、必要 API の対応状況、採用ライブラリとバージョン、暗号スイート、鍵管理方式、設定した期限・資源上限を記録する。
未実施・非対応の条件を、確認済みの条件と区別する。

秘密保持の試験は、本仕様の信頼モデルと鍵漏洩時の前提に従って行う。
悪意ある Signaling による鍵の対応関係の偽装への耐性や、対称鍵を持つ正規参加端末に対する送信者本人性を、試験合格によって保証したとは扱わない。

既存実装の選定には、[鍵管理仕様の組み込み条件](key-management.md#既存実装の利用条件)も適用する。
