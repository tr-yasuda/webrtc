# E2EE の信頼モデルと鍵状態の管理

## 前提

共通の前提は [共通仕様](../platform/overview.md#前提)に従う。

- 音声・カメラ映像・画面共有は SFrame で暗号化する。
- DataChannel の本文も参加端末間で暗号化する。
- C-Plane・D-Plane に復号鍵を渡さない。
- 再接続・SFU 移行中も暗号化を維持する。
- 暗号アルゴリズムには既存実装を利用する。
- 初期の信頼モデルでは、参加権限の判定と参加端末・公開鍵の対応関係について Signaling サーバーを信頼する。
- 将来、Signaling とは独立した鍵の正当性確認方式を追加できるようにする。
- 参加・退出と鍵更新の反映を区別する。新しい参加端末が参加前の通信を復号できず、退出した参加端末が退出を反映した新しい鍵による通信を復号できないことを要件とする。
- 退出した参加端末がすでに取得した平文や鍵の消去までは保証しない。
- 鍵の漏洩後に安全性を回復できる条件は、鍵の配布・参加・退出・鍵更新の節で定める。
- 一時切断からの再接続後も、許可された鍵だけを使用できるようにする。
- SFrame の一つの暗号化用鍵を使用する送信者は一人とする。
- 送信者ごとの鍵の導出・割り当て、鍵識別子、カウンター、鍵更新の条件は、[メディア保護仕様](media.md#sframe-による音声映像の保護)で定める。
- 録画・外部サービスへの配信は今回の対象外とする。

## 用語

| 用語 | 意味 |
|---|---|
| 参加端末 | 共通仕様で定める、Browser SDK を使ってルームに参加するブラウザー側の主体 |
| E2EE | 送信する参加端末で暗号化し、受信する参加端末で復号する方式 |
| SFrame | 音声・映像のフレームを保護する RFC 9605 の方式 |
| 鍵更新 | 使用する暗号鍵を新しいものへ切り替えること |

## 利用場面

以下の A・B・C は、それぞれ別の参加端末とする。
A と B がルームで通話している。
C が途中参加し、参加を許可されたことを確認したうえで、参加後の通信に必要な鍵を取得する。
C は参加前の暗号化された通信を復号できない。

B が退出する。
A と C が、B の退出を反映した鍵更新を完了する。
その後の新しい鍵による通信を B は復号できない。
B がすでに取得した平文や鍵の消去は保証しない。

その後、SFU を新版へ移行する。
A と C は暗号化を維持して通話を続ける。

## 保護する情報と信頼モデル

音声・カメラ映像・画面共有の内容と、DataChannel の本文を参加端末間で暗号化する。
C-Plane・D-Plane に、参加端末の E2EE 用秘密鍵や、メディア・データの復号鍵を渡さない。
Signaling サーバーを鍵の対応関係の信頼元とする場合も、この条件を維持する。

参加者・発行・購読の識別情報、通信先、通信量など、制御と転送に必要な情報はサーバーが扱う。
これらの情報は E2EE の秘匿対象に含めない。

参加権限の判定と、参加端末の識別情報・公開鍵の対応関係について、Signaling サーバーを信頼する。
参加端末は、この信頼モデルに従って相手の鍵の正当性を確認する。

悪意ある Signaling サーバーが参加端末や公開鍵を偽って通知する攻撃への耐性は、今回の保証範囲に含めない。
HTTPS / WSS の使用だけで、この攻撃を防げるとは扱わない。
サーバーに E2EE の復号鍵を渡さないことは保証するが、悪意あるサーバーが鍵の対応関係を偽装して平文を取得することまで防げるとは保証しない。

正規の参加端末が取得した平文や鍵を外部へ提供することは防げない。
参加端末自体が侵害されている間の秘密保持も保証しない。

参加・退出に伴う鍵の切り替えと、鍵漏洩後に安全性を回復できる条件は、鍵の配布・参加・退出・鍵更新の節で定める。

暗号化の準備や鍵の検証に失敗した場合、保護対象の内容を平文へ切り替えて送信しない。

鍵の正当性確認の条件は、Signaling によるメッセージの配送と分けて定める。
将来、Signaling とは独立した確認方式を追加できるようにする。
独立した確認方式への移行が完了するまでは、その方式による安全性を保証しない。

## 参加端末の識別と鍵の正当性確認

ルーム ID・参加者 ID・参加端末・E2EE の鍵管理に使う公開鍵の対応関係を管理する。
参加端末は、個々の WebRTC 接続とは区別して識別する。
同じ参加者が複数の参加端末から接続する場合は、それぞれを別の参加端末として扱う。

Signaling サーバーは、認証した参加者と接続に対して、参加端末の登録と公開鍵の登録を許可する。
別の参加者や参加端末の公開鍵を、権限なく登録・変更することを許可しない。

参加端末は、鍵を使用する前に次を確認する。

- 鍵が対象ルームの参加を許可された参加端末に対応している。
- 公開鍵の形式・暗号条件が許可されたものである。
- 対象の参加端末が、公開鍵の用途に応じて必要な秘密鍵を所持していることを、採用する鍵管理方式に従って確認できる。
- 鍵が失効しておらず、対象の通信に使用できる。

初期の確認方式では、参加端末と公開鍵の対応関係を Signaling サーバーから取得する。
秘密鍵の所持確認は、採用する鍵管理方式に従って行う。

再接続や鍵の変更時も、必要な確認を行う。
参加者 ID が一致することだけを理由に、新しい公開鍵を以前と同じ鍵として扱わない。

鍵の更新・失効に関する情報が古い場合、既に確認した新しい鍵状態を過去の状態へ戻さない。
鍵状態の前後関係は、採用する鍵管理方式に従って判断する。
通知の到着順だけで新旧を判断せず、前後関係や整合性を確認できない更新をそのまま適用しない。
遅れて届いた失効情報を一律に無視せず、対象の鍵と適用条件を確認して処理する。

DTLS 証明書のフィンガープリント確認と、E2EE の公開鍵の正当性確認は別に扱う。
DTLS 接続が成立したことだけで、E2EE の鍵を検証済みとしない。

鍵の確認方式を識別できるようにする。
将来、独立した確認方式を要求する場合、その検証に失敗しても、Signaling を信頼する方式へ自動的に切り替えない。

## 鍵の配布・参加・退出・鍵更新

鍵の配布先は、対象の通信の復号を許可された参加端末に限定する。
配布時も、C-Plane・D-Plane に復号鍵を渡さない。

参加端末の追加・除外を鍵管理へ反映する。
同じ参加者の複数の参加端末も、個別に扱う。
WebRTC 接続を作り直したことだけを理由に、参加端末を追加・除外しない。

参加・退出の受け付けと、鍵状態への反映完了を区別する。

| 状況 | 鍵管理上の条件 |
|---|---|
| 新しい参加端末が参加する | 追加を反映した鍵状態で通信を開始する。参加前の通信を復号できる鍵は渡さない |
| 参加端末が退出・除外される | その参加端末を除外した鍵状態へ更新する。除外した参加端末に、新しい状態の復号鍵を渡さない |
| 鍵が漏洩した可能性がある | 侵害の解消または対象の参加端末の除外と、新しい秘密情報を用いた更新によって、安全性を回復する条件を定める |
| 参加端末が一時切断する | 再接続時に参加権限と鍵状態を確認し、許可された状態だけで復帰させる |

鍵更新の完了は、参加端末ごとに判定する。
各参加端末は、更新の正当性、参加端末の構成、鍵状態の整合性と反映を確認した後、その状態で許可された送受信を開始できる。
更新要求の送信や、Signaling による受け付けだけでは完了としない。
すべての参加端末による反映完了や確認応答は、ほかの参加端末の送受信を許可する条件としない。
切断中または更新に失敗した参加端末のために、更新済みの参加端末の通信を無期限に待機させない。
受信側に必要な鍵状態が未反映の場合、その受信側は復号できるまで待機する。
送信側は、その受信側に合わせて古い鍵で新規送信しない。

退出・除外後の秘密保持は、その変更を反映した鍵状態で暗号化した通信に対して保証する。
参加・退出の受け付け時点で、未更新の参加端末による通信まで保護されたとは扱わない。
更新が必要と確認した参加端末は、反映が完了するまで保護対象の新規送信を停止する。
更新後は新しい鍵状態で暗号化し、古い鍵での新規送信へ戻らない。

通知の欠落や一時切断により、更新が必要なことを確認できない場合も考慮する。
参加権限と鍵状態を再確認せずに新規送信を継続できる期間には、有限の上限を設ける。
再確認できないまま期限に達した参加端末は、新規送信を停止する。
更新期限や再確認期限を、再送や接続の作り直しだけで延長しない。
送信を停止した場合は、Browser SDK から状態を通知する。
復帰には、参加権限と使用を許可された鍵状態の再確認を必要とする。

並行する参加・退出や鍵更新について、参加端末が整合する更新順序を採用できるようにする。
再送や重複通知で同じ変更を二重に反映しない。
更新の欠落・分岐・不整合を検出した場合の復帰条件は、再接続・鍵状態を失った場合の節で定める。

鍵漏洩後の安全性を回復するには、攻撃者が新しい鍵状態を取得できなくなっている必要がある。
回復を保証する対象は、必要な更新を反映した参加端末が、新しい鍵状態で行う通信とする。
侵害が続いている参加端末を残したまま、鍵更新だけで安全性が回復したとは扱わない。

退出した参加端末に、過去の平文や鍵の消去を強制することはできない。
遅延した通信の復号に必要な旧鍵の保持条件は、再接続・SFU 移行の節で定める。
旧鍵を受信のために保持することを、その鍵による新規送信の許可としない。

## 再接続・SFU 移行・鍵状態を失った場合の扱い

WebRTC 接続の再確立と、E2EE の参加端末・鍵状態の継続を区別する。
接続先の SFU が変わったことだけを理由に、参加端末を変更したり、鍵状態を初期化したりしない。

再接続時は、参加権限、参加端末の識別、使用を許可された鍵状態を確認する。
接続が成立したことや、以前の鍵を保持していることだけでは、保護対象の送受信を再開しない。

鍵状態を継続する場合は、切断中に発生した参加・退出・鍵更新・失効を確認する。
更新の正当性と順序を検証し、必要な変更を反映する。
古い通知や保存状態を使って、確認済みの新しい鍵状態から過去の状態へ戻さない。

更新の欠落・分岐・不整合を解消できない場合は、影響する鍵状態による新規送信を停止する。
復旧処理は、その参加端末が使用を許可された状態への同期、または鍵管理方式に従った再参加によって行う。
ほかの正常な参加端末による通信を、その参加端末の復旧待ちにしない。

SFU 移行では、可能な場合は旧接続で通信を継続しながら、新接続を確立する。
新接続で必要な鍵状態と暗号化された通信の受信を確認してから切り替える。
旧 SFU の障害やネットワーク切断などで旧接続を維持できない場合は、通信の一時中断を許容する。
無停止での移行を必須条件とせず、E2EE の安全性と鍵状態の整合性を優先する。
両接続の暗号化処理でカウンターや Nonce の重複を防ぎ、受信側では接続をまたいで重複・リプレイを判定する。
切り替えでは音声を二重再生せず、同じ DataChannel メッセージを重複してアプリケーションへ渡さない。

移行中に鍵更新が必要になった場合も、通常の更新条件を維持する。
新接続の準備失敗を理由に、旧接続で失効した鍵や権限を使い続けない。
旧接続での通信継続や切り戻しは、その接続でも現在の送受信条件を満たす場合に限る。

鍵、カウンター、更新順序、リプレイ判定状態などを失った場合は、何を安全に継続できるかを確認する。
復旧後に過去の Nonce の再利用や、過去の暗号文の再受け入れが起きないことを、送受信の再開条件とする。
同じ鍵のカウンターを初期化して送信を再開しない。
受信側も、リプレイ判定状態を初期化しただけで、同じ鍵による過去の暗号文を再び受け入れない。

必要な状態を復元できない場合は、影響する送受信を停止し、新しい鍵状態を確立してから再開する。
新しい鍵状態への移行時も、過去の暗号文を新しい通信として受け入れない。
鍵識別子や接続の識別情報を変更しただけで、復旧条件を満たしたとは扱わない。
参加端末の識別に必要な秘密鍵を失った場合は、参加者 ID が一致することだけで以前の参加端末として復帰させない。
再登録と以前の参加端末の除外を、参加権限と鍵管理方式に従って処理する。

旧鍵を遅延受信のために保持する場合は、対象の鍵状態、受け入れる通信、保持期間、鍵数と総メモリ量の上限を定める。
期限は遅延パケットや再接続によって延長しない。
失効・除外に伴う受信制限を優先し、旧鍵を持っていることだけで受信を許可しない。

旧鍵の受信期間が終了した場合は、その鍵と不要になった関連状態を Browser SDK の管理対象から削除し、その鍵による暗号文を受け入れない。
遅延した通信を復号するために、削除済みの旧鍵を再取得しない。

復旧処理には、再試行回数・処理時間・保持資源の上限を設ける。
復旧できない場合は、影響する送受信を停止した状態と理由を Browser SDK から通知する。
平文への切り替えや、検証条件の緩和によって復旧しない。

## 既存実装の利用条件

AEAD、ハッシュ、鍵導出、署名、公開鍵暗号、安全な乱数生成には、既存の暗号実装を利用する。
暗号アルゴリズムそのものを独自実装しない。

SFrame と鍵管理の実装は、本仕様の条件を満たすことを確認して選定する。
MLS を採用するかは、引き続き未確定とする。

ライブラリ単体だけでなく、Browser SDK やアダプターを含む実際の組み込み構成で、次の条件を満たすことを確認する。

- 許可する暗号スイート・鍵形式・認証タグ長を限定できる。
- 参加端末と鍵の対応、秘密鍵の所持、失効、更新の正当性を、採用する鍵管理方式に従って確認できる。
- 送信者・用途・受信権限に応じて鍵を分離し、必要な範囲だけに配布できる。
- 並列処理、再接続、SFU 移行を含め、同じ鍵と Nonce の再利用を防げる。
- 鍵の使用上限と更新を管理し、更新できない場合に新規送信を停止できる。
- 状態の欠落・不整合・復元失敗を検出し、本仕様の復旧条件に従って送受信を制限できる。
- 認証に失敗した入力を、平文や検証済みの状態として扱わない。
- ライブラリ自身の制限または外部からの制御により、内部状態・バッファ・待機処理を含む資源上限を保証できる。

鍵管理方式が標準化されていることだけを理由に、本仕様の参加権限や復旧条件まで満たしたとは扱わない。
ライブラリが保証する範囲と、Browser SDK やアプリケーション側で保証する範囲を明確にする。

秘密鍵、復号鍵、平文を、ライブラリのログ、エラー報告、テレメトリーへ出力しない。
C-Plane・D-Plane へ鍵を送らずに利用できる構成とする。

不要になった鍵と関連状態を、定められた保持条件に従って削除できることを確認する。
実行環境によるコピーやメモリ管理の制約を確認する。
Browser SDK の管理対象から削除しても、参加端末内の全コピーの確実な消去は保証しない。

対象の Chrome・Firefox・Safari で、実際のメディア処理と DataChannel に組み込んで動作を確認する。
ブラウザーごとに、E2EE に必要な API の対応状況と、実際に動作を確認したブラウザーバージョンを記録する。
SFrame のメディア処理への組み込みでは、必要な API が利用できることと、その API を用いて実際に暗号化・復号できることを分けて確認する。
API が利用できることだけで、E2EE の動作を確認済みとは扱わない。
必要な機能を利用できない環境では、非対応であることを Browser SDK から通知し、暗号化を無効にして接続を継続しない。

採用する実装、バージョン、設定、組み込み構成を記録する。
セキュリティ修正を追跡し、更新時には影響する相互接続性と安全性の条件を再確認する。
必要な保証を確認できない実装は採用しない。

## 受け入れ条件

採用する暗号実装・鍵管理方式を、Browser SDK と実際に組み合わせた構成で試験する。
正常な通信に加え、通知の欠落・遅延・重複・順序逆転、接続障害、状態喪失を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| メディアと DataChannel の保護 | 音声・カメラ映像・画面共有・DataChannel 本文を参加端末間で暗号化・復号できる。C-Plane・D-Plane に本文の平文や E2EE の秘密鍵・復号鍵を渡さない |
| 参加端末と公開鍵の検証 | 未許可の参加端末、不正な鍵形式、必要な秘密鍵の所持を確認できない鍵、失効した鍵を使用しない。DTLS 接続の成立だけで E2EE の検証を省略しない |
| 複数の参加端末 | 同じ参加者の別の参加端末を個別に登録・除外できる。参加端末間で送信鍵を共用しない |
| 途中参加 | 新規参加端末は、参加前に取得した暗号文を、参加後に配布された鍵で復号できない |
| 退出・除外 | 除外された参加端末が保持していた鍵と取得済みの情報を使っても、除外を反映した新しい鍵状態による通信を復号できない |
| 参加端末ごとの更新完了 | 正常な参加端末は、切断中・更新失敗の参加端末の応答を待たず、新しい鍵状態で通信できる。未反映の参加端末に合わせた旧鍵での新規送信を行わない |
| 更新通知の欠落と期限 | 更新通知とは独立した鍵状態の有効期限または再確認の仕組みを設ける。通知が届かない参加端末も、期限内に使用可能な鍵状態を確認できなければ新規送信を停止する。期限の延長は、使用可能な鍵状態の正当な確認が成立した場合に限る。単なる再接続や通知の再送では延長しない。更新の必要性を確認した参加端末は、反映まで新規送信を停止する |
| 更新の並行処理 | 並行する参加・退出・鍵更新、遅延・重複通知で変更を二重反映せず、新しい状態を過去へ戻さない。欠落・分岐・不整合を検出し、安全な復帰条件を満たすまで影響する送信を停止する |
| 遅延した失効通知 | 到着順だけで失効情報を無視せず、対象の鍵と適用条件を確認して使用制限を反映する |
| 鍵漏洩後の回復 | 侵害の解消または対象の参加端末の除外後、新しい秘密情報による更新を反映した通信を、漏洩済みの鍵と情報から復号できない |
| カウンター・Nonce | 複数の発行、Simulcast、複数の論理チャネル、並列処理、再接続、新旧 SFU への並行送信で、同じ鍵と Nonce による別の暗号化処理を行わない |
| 不正な暗号文とメタデータ | 改変された暗号文・認証タグ・認証対象メタデータを受け入れない。認証前の内容を再生やアプリケーションへ渡さず、不正入力によってリプレイ判定状態を進めない |
| SFU 移行 | 旧接続を維持できる場合は並行して新接続を準備する。維持できない場合は中断を許容し、安全性と整合性を確認して復帰する。移行と鍵更新が重なっても、失効した鍵や権限で継続・切り戻しをしない |
| 状態喪失からの復旧 | 鍵・カウンター・更新順序・リプレイ判定状態を失わせても、過去の Nonce の再利用や過去の暗号文の再受け入れが起きない。必要な状態を復元できなければ、新しい鍵状態を確立してから再開する |
| 旧鍵の保持終了 | 設定した期限・資源上限に従って旧鍵を削除する。遅延通信や再接続で期限を延長せず、削除後は旧鍵の再取得や旧暗号文の受け入れを行わない |
| 資源制限 | 未知の鍵、不正入力、大量の待機メッセージ、並行する更新・復旧処理でも、ライブラリ内部を含む資源上限と処理期限を超えない |
| 非対応・失敗時の動作 | API 非対応、鍵の検証・取得・復旧失敗を Browser SDK から通知する。平文への切り替え、E2EE の無効化、検証条件の緩和によって通信を継続しない |
| ブラウザー相互接続 | Chrome・Firefox・Safari 間で、必要 API の利用可否と実際の暗号化・復号を別々に確認する。音声・映像・画面共有・DataChannel と鍵更新を、対象のブラウザー組み合わせで確認する |
| 標準処理と機密情報 | 対象処理が標準のテストベクトルと一致する。通常動作・異常処理のログ、エラー報告、テレメトリーに秘密鍵・復号鍵・本文の平文を出力しない |

試験結果には、ブラウザーとそのバージョン、必要 API の対応状況、採用ライブラリとバージョン、暗号スイート、鍵管理方式、設定した期限・資源上限を記録する。
未実施・非対応の条件を、確認済みの条件と区別する。

秘密保持の試験は、本仕様の信頼モデルと鍵漏洩時の前提に従って行う。
悪意ある Signaling による鍵の対応関係の偽装への耐性や、対称鍵を持つ正規参加端末に対する送信者本人性を、試験合格によって保証したとは扱わない。
