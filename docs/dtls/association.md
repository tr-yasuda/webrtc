# DTLS Association の確立・維持

STUN、TURN、ICE / WebRTC Transport で利用する DTLS の条件を定める。
共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
管理状態の件数・総量・寿命は、[共通の資源管理](../platform/resources.md#資源管理)に従う。

## 対応バージョン

DTLS 1.2 と DTLS 1.3 に対応し、DTLS 1.0 は使用しない。正常なバージョン交渉では、双方が対応する最新のバージョンを選ぶ。双方が 1.3 に対応していれば 1.3、共通の対応バージョンが 1.2 のみなら 1.2 を選び、共通の対応バージョンがなければ接続を失敗として扱う。

DTLS 1.3 での接続失敗を理由に、提示する対応バージョンを制限したり、暗号・証明書の検証条件を緩めたりして、DTLS 1.2 で再試行してはならない。DTLS を要求する接続では、失敗時に平文通信へ切り替えない。

## 暗号条件と接続相手の検証

DTLS のバージョンと用途ごとに、許可する暗号スイート、鍵・署名方式、検証方法を定める。
ライブラリの対応方式のうち、許可した方式だけを使用する。
許可された条件で接続できない場合は、接続を拒否する。

接続相手の検証方法は、用途ごとに定める。

| 用途 | 検証の責務 |
|---|---|
| STUN / TURN の TLS・DTLS 接続 | サーバーが適切な証明書を提示し、クライアントが信頼・有効性・接続先名を検証する |
| WebRTC Transport | Signaling で受け取ったフィンガープリントと、実際の DTLS 証明書を照合する |

証明書・公開鍵・フィンガープリントの検証に失敗した接続は受け入れない。
必要な検証が完了するまでは、保護対象のアプリケーション処理を開始しない。

証明書や鍵の更新は、用途ごとの許可条件に従う。
正規の更新と、許可されていない差し替えを区別する。

ここで定める使用上限は、DTLS レコードを保護する鍵を対象とする。
SRTP/SRTCP の鍵・暗号方式・使用上限は、[ICE / WebRTC Transport](../transport/secure-transport.md#暗号化通信の確立維持)で定める。

鍵の使用量は、暗号方式ごとの安全な使用上限に従って計数する。AEAD では、暗号化するレコード数と、認証に失敗したレコード数にそれぞれ上限を設ける。各バージョンで利用できる鍵更新または接続再確立を、上限に達する前に行う。

- DTLS 1.3 の送信側は、送信済みの KeyUpdate が ACK で確認されるまで、新しい送信鍵でのレコード送信も次の KeyUpdate の送信も待つ。KeyUpdate や ACK の損失・再送を見込み、鍵の使用上限に達する前に更新を完了できる時点で開始する。受信側は、新しい鍵で保護されたレコードを受信し、復号に成功するまで更新前の受信鍵を保持する。
- DTLS 1.2 では、用途ごとに定める再鍵交換または接続再確立を行う。DTLS 1.3 の KeyUpdate は適用しない。

更新・再確立が完了しないまま上限に達した場合は、その鍵による処理を停止する。同じ鍵を使い続けたまま計数値だけをリセットしない。

鍵の使用上限の管理は、ライブラリ自身または組み込み構成で実現する。
採用時に、上限の根拠、計数方法、更新・停止の動作を確認する。

## 接続確立と到達性確認

以下の条件は、サーバー側で DTLS 接続を受け付ける場合に適用する。

サーバーは、新規接続では原則として次の DTLS Cookie 交換を行い、相手がそのアドレスで応答を受け取れることを確認する。利用者の認証や TURN の利用許可は、各用途で扱う。

| バージョン | 到達性確認 |
|---|---|
| DTLS 1.2 | HelloVerifyRequest と DTLS Cookie 付き ClientHello |
| DTLS 1.3 | HelloRetryRequest と DTLS Cookie 拡張付き ClientHello |

DTLS Cookie は、相手の IP アドレスと対象のハンドシェイクに結び付ける。
UDP ポートも結び付けるかは、用途ごとの仕様で定める。
用途ごとの決定では、NAT rebinding、送信元ポートの偽装、ハンドシェイクの再送を含めて安全性と相互接続性を評価する。

サーバーは、DTLS Cookie の生成・検証に必要な情報を DTLS Cookie とサーバー共通の秘密情報から取得し、クライアントごとの保存状態に依存しない。

- 返された DTLS Cookie の改ざんと有効期限を検証する。
- DTLS 1.3 では、検証後に最初の ClientHello のハッシュと HelloRetryRequest の内容を復元できるようにする。その情報から RFC 9147 に従って Transcript を再構成し、その後のハンドシェイクに使用する。
- 生成に使う秘密情報は更新可能とし、旧世代を受け付ける期間と世代数に上限を設ける。

ICE によって同じ相手・経路で双方向の到達性を確認できていれば、用途の仕様に従って DTLS Cookie 交換を省略できる。確認記録が失われた場合や、確認済みの相手・経路と一致しない場合は、DTLS Cookie 交換を行う。

到達性を確認する前は、通常のハンドシェイク進行状態や接続ごとの再送タイマーを作成しない。
断片化した ClientHello の受信・再構成に必要な状態は別に管理し、相互接続性を保ちながら、保持する状態、メモリ量、保持期間を制限する。
DTLS Cookie 検証に必要な一時メモリ、断片再構成の状態、送受信量の計数情報にも、共通の資源管理要件を適用する。

DTLS 1.3 では、到達性確認前の送信量を次のように制限する。

- ローカルの待受アドレスと、相手の IP アドレス・ポートの組ごとに計数する。
- 送受信量は、UDP ペイロードのバイト数で計数する。
- 送信済みと送信予約済みの合計を、累積受信量の 3 倍以内に制限する。
- DTLS Cookie 応答、再送、Alert も送信量に含める。
- 並行処理でも、同じ送信予算を重複して取得しない。
- 計数情報の消失・削除によって、過去の受信量から送信予算を再生成しない。

到達性を確認できた場合は、接続数・処理量・メモリ量の上限を適用し、必要な枠を予約してから通常のハンドシェイク進行状態を確保する。DTLS 接続が確立した後も、用途ごとに必要な認証・権限確認を満たすまでは、保護対象のアプリケーション処理を開始しない。

## ハンドシェイク・断片再構成・再送の制限

次の資源に設定可能な上限を設ける。
接続単位・送信元単位・サーバー全体のうち、各資源に適用する範囲を定める。

| 資源 | 制限対象 |
|---|---|
| 進行中のハンドシェイク | 同時処理数、保持メモリ量、処理時間 |
| 断片再構成 | メッセージ長、同時再構成数、保持する断片管理情報、総バッファ量、保持時間 |
| 再送 | 再送用バッファ、タイマー数、再送回数、送信量 |
| 完了後の応答用状態 | 件数、保持メモリ量、保持時間 |

断片を受信したら、長さと範囲を検証してから再構成用の資源を確保する。
重複、順序逆転、重なりは各バージョンの仕様に従って処理し、同じ内容の再受信で保持量を増やしたり、別の接続やハンドシェイクの断片を混在させたりしない。
DTLS Cookie 検証前の ClientHello にも断片再構成の上限を適用し、その範囲内の正当な断片化メッセージを受信できることを相互接続試験で確認する。

進行中のハンドシェイクと未完了の断片再構成には、無通信時のタイムアウトに加え、保持開始からの期限を設ける。重複メッセージや追加の断片を受信しても、保持開始からの期限は延長しない。

再送する間隔と対象は DTLS 1.2 / 1.3 それぞれの仕様に従い、各再送にも送信予算と資源上限を適用する。
再送間隔の制御と処理全体の期限は別に管理する。
初期再送間隔、間隔の増加方法、再送回数、処理全体の期限は、各用途で RFC の推奨する再送間隔を考慮して決める。
遅延・損失・重複・順序逆転を含む相互接続試験で、上限内の正常な接続を不必要に失敗させないことを確認する。

DTLS 1.3 では、処理または保持したハンドシェイクレコードに限って ACK する。復号できないレコードと、ハンドシェイク以外のレコードは ACK しない。ACK 自体も別の Content Type で扱い、ACK の対象にしない。

ハンドシェイク完了後も、最後の送信が失われた場合に必要な応答用状態を保持する。

- DTLS 1.2：最後の一連のメッセージを送信した側は、少なくとも既定 MSL の 2 倍の期間、相手からの再送に応答できるようにする。
- DTLS 1.3：サーバーは同期間、クライアントの最終メッセージの再送に ACK を返せるようにする。

再送応答に必要な状態と、確立済み DTLS 接続の暗号状態は別に管理する。
再送応答用状態の保持期間によって、接続全体の寿命を制限しない。

再送応答用状態も資源上限に計上する。
必要な保持期間を短縮して空きを作らず、新規接続の受け入れを制限する。
再送を受けるたびに保持期限を延長しない。

上限や期限に達した場合は、追加の資源確保を停止し、各バージョンの仕様に従って対象の処理を中止またはメッセージを破棄する。
解放結果が不明な場合は、共通の資源管理要件に従う。

## 既存実装の利用条件

DTLS の暗号処理、レコード処理、ハンドシェイク、Transcript、ACK、再送には既存実装を利用する。

既存実装の選定では、次の条件を満たすことを確認する。

- DTLS 1.2 / 1.3 と、用途ごとに必要な機能に対応する。
- DTLS Cookie のステートレスな生成・検証と、DTLS 1.3 の Transcript 復元を、ライブラリまたはその組み込み構成によって実現できる。
- DTLS Cookie 検証前の状態確保が、本仕様の条件を満たす。
- 入出力、保持バッファ、タイマー、再送について、ライブラリ自身の制限または外部からの制御により、本仕様の資源上限と送信予算を保証できる。
- 接続の終了と資源の解放を確認できる。
- 暗号方式ごとの鍵の使用上限を、ライブラリまたはその組み込み構成によって管理できる。
- 各バージョンの鍵更新・接続再確立と、DTLS 1.3 の KeyUpdate・ACK の制約を満たせる。
- セキュリティ修正を追跡し、利用バージョンを更新できる。

対応機能の一覧だけで採用を判断しない。
本仕様の受け入れ条件を、実際に組み込む構成で満たすことを確認する。

ライブラリ内部で保持する状態・キャッシュ・バッファも、資源管理の対象とする。
内部資源の上限を把握するか、隔離された実行環境で上限を強制するなどの手段により、全体の上限を保証する。
接続当たりの内部資源量の上限が分からなければ、接続数を制限しても、内部資源の総量の上限は保証できない。
必要な保証や確認ができない実装は採用しない。

## 受け入れ条件

採用するライブラリを実際の組み込み構成で使用し、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| バージョン交渉 | 正常な交渉で双方が対応する最新バージョンを選択し、1.2 のみの相手とも接続できる。ハンドシェイク失敗後に対応バージョンや検証条件を緩めて再試行しない |
| 暗号条件・接続相手の検証 | 未許可の暗号スイートを拒否する。用途ごとの証明書・公開鍵・フィンガープリントの検証に失敗した接続を受け入れず、検証前に保護対象の処理を開始しない |
| 鍵の使用上限 | 暗号方式ごとの鍵の使用上限を管理し、上限を超えて処理を継続しない |
| KeyUpdate | KeyUpdate や ACK の損失・再送があっても、送信側は対象の KeyUpdate が ACK で確認されるまで、新しい送信鍵でのレコード送信と次の KeyUpdate の送信を待つ。別のメッセージへの ACK が先に届いても、この条件を守る。旧鍵が使用上限に達したら、その鍵での処理を止める。受信側は、新しい鍵での復号に成功するまで更新前の受信鍵を保持する |
| DTLS Cookie | 改ざん・期限切れ・対象外アドレスの DTLS Cookie を受理しない。生成・検証にクライアント別の保存状態を必要としない |
| Transcript | DTLS 1.3 の DTLS Cookie 交換後に Transcript を復元し、ハンドシェイクが成立する |
| アドレス変化 | NAT rebinding・ポート偽装・再送に対し、用途別に定めた DTLS Cookie と到達性確認の条件を守る |
| 断片再構成 | 正当な重複・順序逆転・内容が一致する断片の重なりを処理できる。内容が矛盾する断片は、各バージョンの仕様に従って処理する。過大な長さや大量の未完了メッセージでも資源上限を超えない |
| 送信予算 | 到達性確認前の累積送信量と送信予約量が、累積受信量の 3 倍を超えない。並行送信・再送・管理情報の削除でも制限を回避できない |
| ACK | 復号できないレコード、非ハンドシェイクレコード、処理も保持もしていないレコードを確認済みとして通知しない |
| 再送と期限 | 想定する遅延・損失条件で接続できる。重複や追加断片によって処理全体の期限を延長しない |
| 完了後の状態 | 必要な保持期間中は最終メッセージの再送に応答できる。応答用状態の保持終了によって、確立済み接続を終了しない |
| 資源の解放・回収 | タイムアウト、通知消失、途中失敗、隔離・再初期化について、共通の資源管理要件を満たす |

DTLS 1.2 / 1.3 は、それぞれ対応する接続相手で試験する。
ブラウザーとの相互接続は、対象ブラウザーと用途ごとに確認する。

ライブラリ内部の資源も、上限の保証根拠と実測結果を確認する。
隔離環境によって上限を強制する場合は、上限到達時の停止と資源回収も確認する。

試験結果には、ライブラリ・接続相手のバージョン、組み込み設定、通信条件、観測結果を記録する。
