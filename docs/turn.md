# TURN サーバー

共通の前提・用語・利用場面は [共通仕様](spec.md) に従う。
DTLS の条件は [共通 DTLS 仕様](dtls.md)に従う。

## 中継

TURN サーバーは、端末から SFU へ直接到達できない場合に、端末と SFU の通信を中継する。
メディアや DataChannel の本文を復号せずに転送する。

[RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html)に従い、クライアントと TURN サーバー間では、UDP、TCP、TLS-over-TCP、DTLS-over-UDP に対応する。
TURN サーバーと通信相手の間は UDP とする。

| クライアントと TURN 間 | TURN と通信相手の間 |
|---|---|
| UDP | UDP |
| TCP | UDP |
| TLS-over-TCP | UDP |
| DTLS-over-UDP | UDP |

クライアント側で TCP / TLS-over-TCP を使う場合も、通信相手への中継は UDP で行う。
通信相手との間で TCP 接続を確立する TCP Allocation（RFC 6062）は、今回の対象外とする。
[RFC 8656 §3.1](https://www.rfc-editor.org/rfc/rfc8656.html#section-3.1)に従う。

クライアント接続と中継アドレスは、IPv4・IPv6 に対応する。
クライアント接続のアドレスファミリーと、割り当てる中継アドレスのアドレスファミリーを区別して扱う。

既定の待受ポートは UDP・TCP が 3478、TLS-over-TCP・DTLS-over-UDP が 5349 とする。
待受ポートと、中継に使用するアドレス・ポート範囲は設定可能とする。
接続先を Client SDK に設定できるようにする。

中継資源は、認証と利用許可を確認した Allocate 要求によって確保する。
ルームの作成だけでは確保しない。

次の処理に対応する。

| 処理 | 内容 |
|---|---|
| Allocate | 中継アドレスと Allocation を確保する |
| Refresh | Allocation の有効期限を更新し、または削除する |
| CreatePermission | 通信相手の IP アドレスに対する Permission を作成・更新する |
| ChannelBind | TURN チャネル番号と通信相手の IP アドレス・ポートを対応付ける |
| Send Indication | クライアントから TURN サーバーへ渡したデータを、通信相手へ送信する |
| Data Indication | 通信相手から TURN サーバーが受信したデータを、クライアントへ渡す |
| ChannelData | Channel Binding を使用して、クライアントと通信相手の間で双方向にデータを転送する |

Allocation は、クライアントとサーバーの IP アドレス・ポート、および接続トランスポートの組に対応付ける。
別の接続から、既存の Allocation を無条件に引き継がせない。

Permission は通信相手の IP アドレス単位、Channel Binding は通信相手の IP アドレス・ポートとの対応として管理する。
両者を同じ状態として扱わない。

認証、利用可能な中継先、資源上限、有効期限、再送、解放の条件は、後続の節で定める。

## 認証・利用制限

### 利用認証

TURN による中継には、利用者認証と利用許可を必須とする。
未認証の利用を許可する運用モードは設けない。

クライアントの認証には、STUN の長期資格情報方式を使用する。
Allocate、Refresh、CreatePermission、ChannelBind の各 Request に、この方式の認証を適用する。
[RFC 8656 §5](https://www.rfc-editor.org/rfc/rfc8656.html#section-5)に従う。

C-Plane は、認証した参加端末の利用権限を確認して、期限付きの TURN 資格情報を発行する。
Browser SDK には必要な資格情報を渡し、資格情報を生成・検証するためのサーバー共通秘密情報は渡さない。

資格情報は、利用者と参加端末に対応付ける。
ユーザー名には、個人情報を直接含めない。
秘密情報には十分な推測耐性を持たせ、資格情報をログやエラー報告へ出力しない。

資格情報の有効期間と、認証方式としての「長期資格情報方式」を区別する。
この方式を使用する場合も、クライアントへ配布する資格情報には有効期限を設ける。

ここでいう NONCE は STUN / TURN の認証属性を指し、メディア・データ暗号化で使う Nonce とは区別する。
サーバーは、REALM、NONCE、メッセージ完全性、および資格情報の有効性を、採用する認証条件に従って検証する。
認証情報の不足、不正な資格情報、古い NONCE は、RFC 8489 の認証手順に従って処理する。
必要な認証が成立する前に、Allocation、Permission、Channel Binding、中継ポートを確保しない。

許可する認証アルゴリズムと互換性条件を定め、対象ブラウザーとの相互接続で確認する。
認証失敗を理由に、認証なしの処理へ切り替えない。

Allocation の作成時に、認証したユーザー名を所有者として記録する。
既存 Allocation に対する後続の認証済み Request でも、その所有者との一致を確認する。
別の資格情報で認証に成功したことだけを理由に、Allocation の更新・変更・削除を許可しない。
所有者が一致しない場合は、RFC 8656 に従って 441（Wrong Credentials）を返す。
[RFC 8656 §5](https://www.rfc-editor.org/rfc/rfc8656.html#section-5)に従う。

Send Indication / Data Indication と ChannelData に、Request と同じ長期資格情報方式の認証を要求しない。
データ転送では、対応する Allocation、Permission、必要な Channel Binding、および中継先の利用許可を確認する。
これらのデータ転送だけで、新しい Permission の作成や更新を行わない。
[RFC 8656 §3.3–3.4、§5](https://www.rfc-editor.org/rfc/rfc8656.html#section-3.3)に従う。

TLS / DTLS による接続保護と、TURN の利用者認証を区別する。
DTLS Cookie による到達性確認や、TLS / DTLS 接続の確立だけで、中継の利用を許可しない。

期限付き TURN 資格情報を再発行する場合も、既存 Allocation の所有者確認を緩めない。
同じユーザー名で資格情報を更新できる条件と、ユーザー名の変更などによって新しい Allocation を作成する条件は、「有効期限と解放条件」で定める。
資格情報の期限切れ・失効が、新規 Allocation、既存 Allocation の Refresh、Permission・Channel Binding の更新、継続中のデータ転送へ与える影響も、同節で定める。

### 認証後の資源上限

認証済みの利用者にも、中継資源と処理量の上限を適用する。
上限は設定可能とし、少なくとも次を対象にする。

| 対象 | 制限する内容 |
|---|---|
| Allocation | 同時に保持する数 |
| Permission | 同時に保持する数 |
| Channel Binding | 同時に保持する数 |
| 中継ポート | 使用中・予約中のポート数 |
| 中継帯域 | クライアントから通信相手、および通信相手からクライアントへの転送量 |
| 制御処理 | Allocate、Refresh、CreatePermission、ChannelBind などの処理量 |
| 内部資源 | 接続、処理待ち要求、タイマー、管理表、受信・送信バッファの件数と総メモリ量 |

Allocation 内の上限、参加端末・利用者ごとの合計上限、TURN サーバー全体の上限を、対象資源に応じて適用する。
Allocation 数だけを制限して、各 Allocation 内の状態を無制限に保持しない。

利用者・参加端末の集計は、資格情報を発行した C-Plane の対応関係に基づく。
資格情報の再発行、ユーザー名の変更、接続先アドレスやトランスポートの変更によって、同じ利用者に適用する上限を回避できないようにする。
この集計上の対応付けを、Allocation の所有者確認を緩める理由にはしない。

RFC 8656 の 486（Allocation Quota Reached）は、要求を認証したユーザー名で新しい Allocation を作成できないことを示す。
そのユーザー名に適用する Allocation 上限の判定に、C-Plane が対応付けた利用者・参加端末の共有枠を含める。
同じ利用者・参加端末に属する複数のユーザー名は、その共有枠を消費する。
共有枠の上限に達した場合も、要求を認証したユーザー名での追加作成を拒否し、486 を返す。
この対応はプラットフォームの割り当てポリシーとし、RFC が利用者・参加端末という集計単位を定義しているとは扱わない。

複数の Worker で処理する場合も、同じ上限の適用範囲に属する資源を合計する。
Worker ごとの上限だけを根拠に、利用者・サーバー全体の上限を保証したとは扱わない。
Worker をまたいで予約・確保・解放が並行する場合も、全体の上限を超えないことを保証する。
具体的な実装方式は限定せず、[共通の資源管理](spec.md#資源管理)の予約・計上・照合・回収の条件を適用する。

資源の予約・確保・解放・照合は、共通の資源管理に従う。
並列要求でも上限を超えないよう、予約済み・解放待ち・結果不明の枠も計上する。

Permission や Channel Binding の更新では、新規作成と既存状態の更新を区別する。
同じ状態の更新や Request の再送によって、不要な資源確保や件数の二重計上を行わない。
更新と再送にも、制御処理の上限を適用する。

一つの Request が複数の資源を必要とする場合は、必要な枠を確認してから処理する。
部分的な確保後に失敗した場合も、確認できていない資源を解放済みとして扱わない。

認証済み Request が資源上限によって実行できない場合は、メソッドと原因に応じたエラーを返す。

| 条件 | 応答 |
|---|---|
| 認証ユーザー名に適用する Allocation 数の上限（対応する利用者・参加端末の共有枠を含む） | 486（Allocation Quota Reached） |
| 中継アドレス・ポートなどの容量不足 | 508（Insufficient Capacity） |
| CreatePermission / ChannelBind を容量不足で実行できない場合 | 508（Insufficient Capacity） |

エラー処理は [RFC 8656 §7.2、§10.2、§12.2](https://www.rfc-editor.org/rfc/rfc8656.html#section-7.2)に従う。
応答自体にも、処理量と送信量の制限を適用する。

中継帯域には、方向ごとの上限を適用する。
計測点、計上するバイトの範囲、計測期間、許容する一時的な超過量を明示する。
Send Indication / Data Indication と ChannelData のどちらを使っても、帯域制限を回避できないようにする。

帯域上限を超える転送データは破棄する。
制限を守るためにデータを無制限にキューへ蓄積しない。
キューを使用する場合は、件数・総バイト数・保持時間を制限する。
[RFC 8656 §5](https://www.rfc-editor.org/rfc/rfc8656.html#section-5)に従う。

中継データの帯域制限と、制御応答・TLS / DTLS 処理を含むサーバー全体の資源制限を分けて管理する。
中継帯域の上限だけで、ネットワーク使用量や暗号処理量の総量を保証したとは扱わない。

### 有効期限と解放条件

TURN 資格情報の有効期限、Allocation の有効期限、Permission の有効期限、Channel Binding の有効期限を別に管理する。
一つの更新を、ほかのすべての期限の更新として扱わない。

TURN の状態の寿命と更新は、次に従う。

| 状態 | 寿命と更新 |
|---|---|
| Allocation | 既定の寿命は600秒とし、Allocate / Refresh の処理で RFC に従って決定する。応答の LIFETIME に実際の寿命を返す |
| Permission | 寿命は300秒とする。CreatePermission または ChannelBind によって作成・更新する |
| Channel Binding | 寿命は600秒とする。同じ対応に対する ChannelBind によって更新する |

これらの寿命と更新は [RFC 8656 §6–9、§12](https://www.rfc-editor.org/rfc/rfc8656.html#section-6)に従う。
Allocation の最大寿命を含む設定は、RFC の条件を満たす範囲で定める。

データの送受信だけで、Allocation、Permission、Channel Binding の期限を更新しない。
Refresh で Permission や Channel Binding の期限を更新せず、CreatePermission で Channel Binding の期限を更新しない。

資格情報の期限を延長する場合は、C-Plane が現在の利用権限を再確認する。
単なる通信の継続、再接続、NONCE の更新では、資格情報の期限を延長しない。

既存 Allocation を維持した資格情報の期限延長は、採用する資格情報方式で安全に実現できる場合に限る。
その場合も、次の条件をすべて満たす必要がある。

- 認証ユーザー名、REALM、認証に用いる秘密情報を維持できる。
- C-Plane と TURN サーバーが、同じ資格情報に対する有効期限の更新を正当に確認できる。
- 資格情報がまだ有効で、失効しておらず、現在の利用権限を満たしている。

有効期限をユーザー名に含める方式など、同じユーザー名・秘密情報のまま安全に延長できない場合は、新しい資格情報で新しい Allocation を作成する。

資格情報の期限延長だけで、Allocation やその内部状態の期限を延長しない。
クライアントは、引き続き必要な Refresh、CreatePermission、ChannelBind を行う。

ユーザー名や認証に用いる秘密情報を変更する場合、または上記の条件で期限を延長できない場合は、新しい資格情報で新しい Allocation を作成する。
既存 Allocation の所有者を付け替えたり、441（Wrong Credentials）を回避するために所有者確認を省略したりしない。

新しい Allocation が必要な場合は、可能なら既存経路を維持しながら新しい中継経路を準備する。
新旧両方の資源を利用者・参加端末の上限に計上し、移行中であることだけを理由に上限を超えない。
既存経路を維持できない場合は、一時中断を許容する。

資格情報の期限切れと明示的な失効は、次のように扱う。

| 状況 | 新規作成・更新 | 既存のデータ転送 |
|---|---|---|
| 資格情報の期限切れ | 新規 Allocate、既存 Allocation の Refresh、Permission・Channel Binding の作成・更新を許可しない | 既存 Allocation と転送方式ごとの状態・権限が有効な間だけ許可する。期限切れによって追加の猶予期間を設けない |
| 資格情報または利用権限の明示的な失効 | 対象範囲の新規作成・更新を許可しない | 失効の反映後は停止し、対象資源を解放する |

このプラットフォームでは、通常の資格情報の期限切れだけでは既存 Allocation を即座に削除せず、上記の条件で転送を許可する。
これはプラットフォームの方針であり、RFC の必須動作ではない。

期限切れ後の転送可否は、転送方向と Send Indication / Data Indication・ChannelData ごとの RFC の条件に従って判定する。
Permission と Channel Binding の期限切れは、それぞれに判定する。

失効の対象となる資格情報・利用者・参加端末と Allocation の対応を識別する。
失効情報の伝達・反映には有限の期限を設け、その期限内に利用許可を確認できなければ対象の転送を停止する。
遅延した期限延長通知によって、失効済みの資格情報を再び有効にしない。

Allocation の期限切れ、認証済みの LIFETIME が0の Refresh、または管理上の失効によって中継を終了する。
関連する Permission・Channel Binding・中継ソケットなどを解放する。
複数アドレスファミリーの資源を持つ場合は、削除対象と残す対象を区別する。

期限切れや削除の後も、解放を確認するまでは資源枠に計上する。
解放結果が不明な場合の照合・隔離・回収は、[共通の資源管理](spec.md#資源管理)に従う。

Browser SDK は、資格情報の更新や新しい経路の準備が必要な状態と、失敗・転送停止の理由をアプリケーションへ通知する。
資格情報を更新できない場合も、認証条件を緩めて中継を継続しない。

## 自作範囲・既存実装の利用

TURN のプロトコル処理と中継処理は Rust で実装する。
Rust の実行方式は、Wasm、Native Addon、独立 Worker を選択肢として残し、この節では固定しない。
Rust で実装しても、独立プロセスでの実行は必須としない。
C-Plane / D-Plane の論理的な責務の分離と、Rust の実行方式は区別し、実行プロセスの分離を必須としない。

| 自作する部分 | 内容 |
|---|---|
| TURN メッセージの処理 | Allocate、Refresh、CreatePermission、ChannelBind、Send Indication / Data Indication、ChannelData の解析・検証・生成 |
| 認証と利用許可の判定 | 資格情報、メッセージ完全性、Allocation の所有者、中継先の許可条件の確認 |
| 中継状態の管理 | Allocation、Permission、Channel Binding と、それぞれの期限・更新・失効の管理 |
| データの中継 | クライアント側トランスポートと通信相手側の UDP 間の転送、接続上のメッセージ境界の処理 |
| 資源と処理量の制限 | 枠の予約・計上、Worker 間の上限保証、方向別の帯域制限、バッファ・処理量の制限 |
| 再送と障害時の処理 | Request 再送時の整合性、部分的な失敗、結果不明の資源の照合・回収 |

これらの処理は自作し、完成済みの TURN サーバーや TURN プロトコル実装には委ねない。

STUN 形式のメッセージには、[STUN サーバー](stun.md#自作範囲既存実装の利用)で自作する共通の読み書き・検証処理を利用する。
ChannelData は STUN メッセージと区別して処理する。
認証順序、再送、状態変更などの TURN 固有の条件は、TURN 側で適用する。

ソケット入出力、非同期実行、タイマー、バッファ管理には、Rust の標準ライブラリや汎用ライブラリを利用できる。

ハッシュ、HMAC、鍵導出、暗号学的な乱数生成、TLS / DTLS、証明書処理には、既存の暗号実装を利用する。
暗号アルゴリズムそのものを独自実装しない。
STUN の規定に従う認証入力の組み立てと、その検証結果に基づく利用許可の判定は、自作するプロトコル処理が担う。

資格情報の発行と利用者・参加端末の権限管理は、TypeScript の C-Plane が担う。
Rust の TURN サーバーは、信頼できる対応関係と認証条件に基づいて検証し、既存 Allocation の所有者確認と資源上限を適用する。

TLS / DTLS ライブラリの内部状態・バッファ・タイマーも、全体の資源管理に含める。
ライブラリ自身の制限または組み込み側の制御によって、本仕様の上限を保証する。
DTLS の利用条件は、[共通 DTLS 仕様](dtls.md#既存実装の利用条件)に従う。

採用する既存実装のバージョン、設定、依存する機能を記録する。
機能への対応だけで採用を判断せず、実際の組み込み構成で相互接続性、資源上限、障害時の動作を確認する。
セキュリティ修正を追跡し、更新できる構成とする。

実装と検証には、[実装・検証の共通方針](spec.md#実装検証の共通方針)を適用する。
TURN 固有の検証対象と確認する結果は、「受け入れ条件」で定める。

## セキュリティ

認証、Allocation の所有者確認、期限切れ・失効、認証後の資源上限は、「認証・利用制限」に従う。
認証に成功したことだけで、任意の中継先や無制限の資源利用を許可しない。

STUN 形式のメッセージには、共通の解析・検証と RFC の処理順序を適用する。
ChannelData は別の形式として、TURN チャネル番号、長さ、パディング、対応する Allocation と Channel Binding を検証する。
不正な入力で範囲外アクセスや過大な資源確保を発生させない。

TURN の利用用途を、ブラウザー用と SFU 用に分ける。
用途は、認証した利用主体、対象の Allocation、C-Plane が認可した接続に対応付ける。
クライアントの自己申告や TURN 資格情報の所持だけで、別用途の中継許可を取得させない。

ブラウザー用の中継先は、C-Plane が管理する SFU の通信先のうち、利用を許可されたものに限定する。
SFU 用では、C-Plane が認可した WebRTC 接続・ICE 世代と、その接続の ICE 候補に基づく中継許可を使用する。
SFU 用であることだけを理由に、任意の外部ホストへの中継を許可しない。

許可情報には、対象の IP アドレス、UDP ポートまたはポート範囲、適用範囲、有効期限を含める。
SFU 用では、接続・ICE 世代・Allocation と、ICE 接続確認用または通常の転送用という許可範囲も識別する。
具体的な許可情報の表現と同期方式は固定しない。
Signaling で通知された ICE 候補やクライアントが要求した通信先を、そのまま通常の転送許可として登録しない。
接続の認可だけで任意の宛先を ICE 候補として許可せず、ICE 候補のアドレス・ポートに運用上の許可条件も適用する。

Relayed Candidate を使う ICE 接続確認の前に、認証済みの CreatePermission によって対象 IP アドレスの TURN Permission を作成できるようにする。
この段階では、C-Plane が認可した接続・ICE 候補に対する、ICE 接続確認専用の暫定的な許可を使う。
まだ成功していない ICE の認証・到達性確認を、Permission 作成の前提として要求しない。
[RFC 8445 §7.2.1](https://www.rfc-editor.org/rfc/rfc8445.html#section-7.2.1)に従い、プラットフォームの暫定的な許可と TURN Permission の作成を区別する。

暫定的な許可では、送信する確認用パケットを、信頼する ICE エージェントが対象接続・ICE 世代について生成・承認した内容に限定する。
TURN は、信頼する ICE エージェントとの内部の連携によって、送信内容、宛先、方向、対象トランザクション、許可期間との対応を確認できることを必要とする。
TURN クライアントの自己申告、パケット内の識別情報、STUN の形式への一致だけを、生成・承認の根拠としない。
アプリケーションが任意の本文を確認用パケットとして承認させる経路を設けない。

暫定的な許可で受信した確認用パケットは、対象接続の ICE エージェントの検証処理にだけ渡す。
通常のメディア・DataChannel・アプリケーション向けの転送経路へ渡さない。
既存の Send Indication / Data Indication や ChannelData を利用する場合も、内部でこの用途の分離を維持し、メッセージ形式の切り替えで通常の転送許可を迂回できないようにする。

TURN が保証する条件は、用途・接続・Allocation との対応、暫定的な許可の範囲、送信内容の承認との一致、および適用する中継制限とする。
ICE エージェントは、対象世代の資格情報による認証、要求・応答とトランザクション・送受信アドレスの照合、到達性確認と ICE 状態遷移を検証する。
STUN の形式検証、Permission の存在、確認要求の受信だけで、これらの検証が成功したとは扱わない。
通常の転送用の許可へ移行するには、信頼する ICE エージェントによる検証結果と、C-Plane の接続認可との対応を確認する。
その後も、ICE の経路利用条件と WebRTC Transport の認証・暗号条件を満たさない通信を開始しない。

暫定的な許可には、宛先の範囲・件数、通信量、同時処理数、保持時間の上限を設け、既存の資源・帯域・失効条件も適用する。
確認の失敗や期限切れだけで通常の転送を許可せず、許可範囲を自動的に広げない。

Peer-Reflexive Candidate と正当な経路変更は、信頼する ICE エージェントが対象接続・ICE 世代に対応付けて扱う。
Signaling で事前通知されていないことだけで拒否せず、新しい送信元を観測したことだけで許可しない。
学習した ICE 候補について必要な接続認可との対応と暫定的な許可を確認し、Permission の作成・更新を行ってから、その経路で必要な ICE 接続確認を行う。
未許可の IP アドレスからのパケットが TURN Permission によって破棄される場合は、既に確認を受け付けられる経路、または追加の ICE 候補交換と認可によって確認経路を準備する。
対象アドレスの Permission と確認用経路を準備できなければ、その経路は利用不可として扱い、Permission を迂回した転送や任意宛先への許可は行わない。

用途ごとに許可された IP アドレス・ポートとの一致は、中継先の利用許可の判定とする。
IP アドレス・ポートの一致だけでは、通信相手を暗号学的に認証できない。
TURN は許可された通信先への中継を制限し、通信相手の認証とメディアの保護は、[ICE / WebRTC Transport](transport.md)の仕様に従う。

Permission は IP アドレス単位で管理する。
CreatePermission では対象 IP アドレスの許可を確認し、属性のポート値を Permission の制限として扱わない。
ポートを含む制限は、ChannelBind と実際のデータ転送で確認する。

Send Indication と ChannelData のどちらでも、中継先の制限を回避できないようにする。
通信相手から受信するデータにも、転送方向に応じた Permission・Channel Binding の条件と、用途ごとに許可された通信先との対応を適用する。
Permission が存在する IP アドレスでも、プラットフォームの許可対象外のポートや用途へ転送しない。

許可されていない中継先への CreatePermission / ChannelBind は、403（Forbidden）で拒否する。
許可されていない転送データは、応答せず破棄する。
中継先の制限は [RFC 8656 §10.2、§11.2、§12.2、§21.1.4](https://www.rfc-editor.org/rfc/rfc8656.html#section-21.1.4)を踏まえて適用する。

SFU 移行中は、利用を許可した新旧 SFU の通信先を扱えるようにする。
移行完了や許可の失効後に、古い通信先への転送を無期限に継続しない。
許可情報の更新・失効は、資格情報や利用権限の失効と同様に、有限の期限内に反映する。

用途ごとの通信先がプライベートアドレスの場合も、許可情報との一致を確認する。
プライベートアドレスであることだけで許可せず、同じホスト上の管理用ポートなど、許可されていない通信先への転送を防ぐ。

TURN の待受先をメディアの通信先として誤って許可しない。
TURN の中継アドレスは、認可された接続の正当な Relayed Candidate である場合に限って扱い、用途に応じた ICE 接続確認と転送許可を必要とする。
TURN 間の転送ループを生じさせず、帯域制限だけをループ防止の根拠としない。

NONCE には有効期限を設け、改ざんや対象外の利用を検証する。
NONCE の発行・検証、認証失敗への応答にも、処理量・送信量・保持状態の上限を適用する。

Allocation に保持する認証情報は、RFC に従う導出済みの認証鍵とし、パスワードを平文で保存しない。
導出済みの認証鍵も機密情報として保護する。
[RFC 8656 §6](https://www.rfc-editor.org/rfc/rfc8656.html#section-6)に従う。

TLS / DTLS 接続では、サーバーが接続先に対応する適切な証明書を提示する。
証明書の信頼・有効性・接続先名は、接続するクライアント側が検証する。
この検証は、WebRTC の SDP フィンガープリント照合とは別に扱う。

TLS / DTLS を使用する場合、制御応答、Data Indication、ChannelData を、対応する保護された接続または DTLS Association を通じて返す。
平文の UDP 応答や別のクライアントの接続へ切り替えない。

DTLS の到達性確認、ハンドシェイク、断片再構成、再送、送信予算は、[共通 DTLS 仕様](dtls.md)に従う。
到達性確認前、認証前、認証後のそれぞれに資源上限を適用する。

TURN 接続の TLS / DTLS だけでは、通信相手までの本文の保護を保証しない。
中継する WebRTC 通信と参加端末間の本文は、WebRTC Transport および E2EE の仕様に従って保護する。

## 受け入れ条件

IPv4・IPv6 と、クライアント接続の UDP・TCP・TLS-over-TCP・DTLS-over-UDP を組み合わせ、ブラウザー用・SFU 用それぞれの許可された通信先との UDP 中継を確認する。
次の条件を、実際の組み込み構成で検証する。

| 試験対象 | 確認する結果 |
|---|---|
| 基本的な中継 | Allocate、Refresh、CreatePermission、ChannelBind を処理できる。Send Indication はクライアントから通信相手へ、Data Indication は逆方向へ転送し、ChannelData は Channel Binding を使って双方向に転送する |
| トランスポートの分離 | クライアント接続が TCP / TLS でも、通信相手への中継は UDP とする。未対応の TCP Allocation を受け入れない |
| 認証 | 認証情報の不足、不正な資格情報、古い NONCE を規定どおり処理する。認証成立前に中継資源を確保せず、認証なしの処理へ切り替えない |
| Allocation の所有者 | 認証済みでも、作成時と異なるユーザー名による既存 Allocation の操作を許可しない。条件に従って 441 を返す |
| 資格情報の期限延長 | 採用する方式で安全に延長できる場合だけ、既存 Allocation を維持する。ユーザー名や秘密情報の変更が必要な場合は、新しい Allocation を作成する。所有者確認を緩めない |
| 資格情報の期限切れ | 新規 Allocate、Refresh、Permission・Channel Binding の作成・更新を拒否する。既存の転送は、プラットフォーム方針と各状態・方向別の転送条件に従い、追加の猶予を設けず終了する |
| 明示的な失効 | 資格情報・利用権限・中継先許可の失効を設定期限内に反映し、対象の転送を停止する。失効対象の Allocation は資源を解放し、遅延した延長通知で復活させない |
| 状態ごとの寿命 | Allocation、Permission、Channel Binding の期限を独立に管理する。Refresh、CreatePermission、ChannelBind が更新する対象を区別し、データ転送だけでは期限を延長しない |
| Permission と転送条件 | Permission を IP 単位で扱い、属性のポート値を Permission の制限にしない。Permission と Channel Binding の期限が異なる場合も、各転送方向・方式の RFC の条件に従って判定する |
| 中継先の制限 | ブラウザー用は C-Plane が許可した SFU に限定する。SFU 用は認可された接続・ICE 世代と用途ごとの中継許可に限定する。同じ IP の未許可ポート、管理用ポート、任意の外部ホストへ転送しない。Send Indication と ChannelData の切り替えで制限を回避できない |
| 用途の認可 | クライアントの自己申告や TURN 資格情報の所持だけで SFU 用の許可を取得できない。別接続・別 Allocation・旧 ICE 世代の許可や検証結果を流用できない |
| ICE 接続確認前の Permission | C-Plane が認可した接続・ICE 候補に対し、到達性確認前に認証済みの CreatePermission を実行できる。IP 単位の Permission が存在しても、確認用の許可を通常の転送許可として扱わない |
| 暫定的な許可とデータの分離 | 送信は信頼する ICE エージェントが生成・承認した確認用パケットに限定する。STUN 形式に似せた本文、未承認の属性・内容、別トランザクションのパケットを送信できない。受信は ICE の検証処理にだけ渡し、通常の転送経路へ渡さない。形式・TURN チャネルの切り替えでも迂回できない |
| ICE の認証と通常の転送許可 | 不正な完全性情報、対象外の資格情報、未対応のトランザクション、不一致の送受信アドレスでは、通常の転送許可へ移行しない。Permission や形式検証の成功だけで認証・到達性確認を完了扱いしない |
| Peer-Reflexive Candidate と経路変更 | 事前通知されていない正当な ICE 候補を対象接続・ICE 世代に対応付け、必要な認可・Permission と確認用経路を準備して検証できる。未許可 IP では追加の ICE 候補交換などを用い、準備できなければ利用不可とする。単なる送信元変更や古い検証結果で通常の転送を許可しない |
| SFU 移行 | 許可された新旧 SFU を扱い、許可終了後の旧宛先へ無期限に転送しない。新旧 Allocation の両方を資源上限に計上する |
| 中継先許可と相手認証 | IP・ポートの一致だけで、通信相手を暗号学的に認証済みと扱わない。WebRTC Transport の相手認証とメディア保護を省略しない |
| 転送ループ | TURN の待受先への不正な中継や TURN 間の転送ループを発生させない。正当な Relayed Candidate は用途ごとの認可・確認条件で扱い、中継アドレスであることだけで一律に許可・拒否しない |
| Request の再送 | UDP / DTLS-over-UDP の同一トランザクションの再送で、RFC に従う状態・応答の整合性を維持する。Allocation の重複作成や、Permission・Channel Binding の二重計上を起こさず、処理量・応答帯域制限も回避できない |
| 資格情報と集計単位 | 資格情報の再発行やユーザー名・接続経路の変更後も、C-Plane が対応付けた利用者・参加端末の共有枠に合算する。共有枠の上限を、認証ユーザー名へ適用する Allocation 上限として判定する |
| Worker 間の並行処理 | 複数 Worker で予約・確保・解放が並行しても、利用者・参加端末・サーバー全体の上限を超えない。空き枠1に対する同時要求を含めて確認する |
| 容量不足の応答 | Allocation 上限は 486、容量不足による Allocate / CreatePermission / ChannelBind の失敗は条件に従って 508 を返す。応答にも処理量・送信量の制限を適用する |
| 方向別の帯域制限 | 両方向で設定した上限を守る。Send Indication / Data Indication と ChannelData で制限を回避できず、超過データを破棄する。キューを無制限に増やさない |
| 不正入力と内部資源 | 不正な属性長、ChannelData の長さ・番号・パディング、分割受信、大量の接続や低速送信でも、範囲外アクセスや資源上限超過を起こさない |
| 結果不明と回収 | 確保・解放の通知消失、重複、遅延、管理記録の喪失でも、過少計上や二重返却を起こさない。隔離資源は所有関係と解放を確認して回収し、古い通知で再利用後の資源を変更しない |
| 終了と解放 | Allocation の期限切れ、認証済みの寿命0の Refresh、管理上の失効で対象の中継を終了する。アドレスファミリー別の削除対象を区別し、解放確認までは資源枠へ計上する |
| TLS / DTLS | 制御応答・Data Indication・ChannelData を、対応する保護された接続または DTLS Association で返す。平文への切り替えや別クライアントへの混入を起こさず、共通 DTLS の受け入れ条件を満たす |
| 機密情報と通知 | Allocation にパスワードを平文保存しない。資格情報・認証鍵・本文をログへ出力しない。更新・経路準備の必要性、失敗・転送停止の理由を Browser SDK から通知する |

検証方法の選定と結果の扱いは、[実装・検証の共通方針](spec.md#実装検証の共通方針)に従う。
TURN では、次を重点対象とする。

| 検証方法 | 重点対象 |
|---|---|
| TLA+ によるモデル検査 | Worker 間の資源予約・確保・解放、結果不明からの回収、所有者確認、資格情報の更新・失効と転送停止の競合 |
| Fuzzing | STUN / ChannelData の解析、長さ・境界・パディング、不正な認証属性、接続上の分割・連続入力 |
| Property-based Testing | 予約・使用・解放の計上、状態ごとの期限、再送・重複・順序逆転を含む操作列、中継先制限 |
| 形式的な証明の評価 | 資源計数や帯域予算の不変条件、境界計算などについて、Lean 4・Verus・Aeneas などの適合性を評価する |

Lean 4・Verus・Aeneas は選定候補とし、適合性の評価結果と、実際に完了した形式検証の結果を区別する。
検証できなかった範囲や未完了の検証を、証明済みとして扱わない。

モデル検査では、上限を超えないことに加え、必要な通知や照合が進み、資源の解放を確認できる前提の下で、回収処理が完了することも検証対象とする。
回復不能な障害を、仮定によって隠して成功扱いしない。

対象ブラウザーの対応状況に応じて相互接続を確認する。
ブラウザーが利用しないトランスポートや条件は、検証用クライアントで確認し、その範囲を区別する。

試験結果には、実行方式、サーバー・ブラウザー・ライブラリのバージョン、通信条件、資格情報方式、期限、資源上限、帯域の計数条件、検証範囲と観測結果を記録する。
具体的な制限値は本節では固定しない。
