# SFU の配置・移行・退役

ルームへの SFU 割り当てと解除、計画的な移行・退役、障害時の再配置を定める。ルーム自体の寿命は [ルーム仕様](../platform/rooms.md)、参加・退出との並行処理は [Signaling 仕様](../signaling/session.md)に従う。

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## SFU のスケール

計画的な更新は、次の順で進める。

1. C-Plane は、新版の SFU が受け入れ可能になったことを確認してから、旧 SFU を drain 状態とする。その時点で退役期限を必ず設定し、Browser SDK へ移行予定と退役期限を通知する。drain 中は旧 SFU への新しいルームの割り当てを止め、担当中のルームの通話・途中参加・再接続は継続する。
2. 旧 SFU 上で通話を続けながら、移行先への接続と発行・購読を準備する。準備中は新旧 SFU に接続する参加者間で会話を継続できるようにし、両方の転送に必要な需要を [品質制御仕様](quality.md#需要の集約から停止再開まで)に従って集約する。参加者 ID と発行・購読の識別子は、移行の前後で維持する。
3. Browser SDK は、新しい接続で受信・再生を確認してから再生先を切り替える。切り替え中も同じ音声を二重に再生せず、移行を通常の退出・再参加としてアプリケーションに通知しない。
4. 切り替えが完了したことを確認してから旧接続を解放する。旧 SFU は担当 Room がなくなり、容量予約もなくなった後、idle timeout を経て停止できる。

退役期限は drain の開始を起点とし、初期値を 30 分とする。運用側で変更できるが、途中参加・再接続・移行の再試行では延長しない。退役期限とルームごとの通話時間の上限は別々に管理し、期限到達前の予告は[共通仕様の時間設定](../platform/rooms.md#ルーム参加者権限)に従う。

### 準備失敗・退役期限到達・障害時の復旧

切り替え前に準備が失敗した場合、旧 SFU を利用でき、かつ退役期限に達していなければ、旧接続で通話を継続しながら移行を再試行する。退役期限までに移行できなかった場合は、中断を伴う自動再接続に切り替える。旧 SFU が突然故障した場合も、自動再接続で復旧を試みる。

移行時の同時接続数と送信品質の制御は、通信資源と参加端末の負荷を含めて受け入れ条件で定める。
移行時に許容する音声・映像の中断時間は、受け入れ条件で定める。
DataChannel の切り替えに伴う未配送データ・順序・重複の扱いは、[データ配送](../datachannel/delivery.md#データ配送)で定める。

## Worker の構成とライフサイクル

プロセスモデルの正本は [D-Plane のプロセスモデルと IPC 境界](../platform/dplane.md)にあり、本節は SFU の配置に必要な条件だけを定める。

SFU は、Node host が UDS で制御する独立した Rust Worker プロセスとして実行する。Node host は Worker の OS 上の親プロセスではなく、プロセスの生存期間は supervisor（systemd など）が管理する。Node host の再起動で Worker を終了させない。

実行形態、IPC 契約、再起動時の照合は [D-Plane のプロセスモデルと IPC 境界](../platform/dplane.md)に従う。Worker のプロセス寿命と Room の実行時状態は分けて扱う。

1 つの Worker は複数の Room を収容する。Room ごとにプロセスを作らず、Room の実行時状態である Router を作成・閉鎖する。

### Worker プロセスの起動・停止

- Worker は必要時に起動し、Room 0 かつ容量予約 0 になってから 30 秒の idle timeout で停止する。idle timeout 中の新しい Room 割り当ては停止をキャンセルする。
- Worker 数は 0 まで縮退できる。停止状態に入った Worker には新しい Room を割り当てず、必要なら別 Worker を起動する。

### Room と Router の閉鎖

- 最後の参加者が退出した Room は、明示退出なら処理中操作と資源解放を確認して Router を閉じる。異常切断なら 30 秒の再接続猶予を置き、復帰しなければ閉じる。
- C-Plane の Room と履歴は保持し、再参加時は新しい Router を作成する。

### 容量と再起動

Worker の容量は CPU・帯域・参加者数の上限で管理し、実使用量と予約量の合計で空きを判定する。Room 作成、参加者受入、Transport、Produce、Consume の予約を同じ台帳に計上し、並行する操作へ同じ空き容量を二重に割り当てない。C-Plane から Node host への Room 割り当ては、Node host の予約成功で確定する。容量が不足する場合は、別 Worker、別 Host、拒否の順に扱う。

再起動時の扱いは、次のように分ける。

- Node host: 生存 Worker のスナップショットとイベント境界から制御を引き継ぐ。
- Worker: 失われた Router と Transport を復元せず、影響する Room を C-Plane が再配置する。
- Signaling: 永続化された割り当てと Worker の状態を照合し、孤児を確定してから閉じる。

## 自作範囲・既存実装の利用

SFU のメディア転送と品質制御の中核処理は Rust で実装する。
アプリケーションからの操作、認可、配置・移行の制御は TypeScript の C-Plane が担う。

SFU 移行との連携では、発行・購読の引き継ぎ、移行中の需要の集約、切り替え結果の確認を自作する。

既存の SFU 製品や完成済みのメディア転送エンジンに、これらの中核処理を委ねない。

汎用的な入出力、非同期実行、時刻管理、メモリ管理、計測には既存ライブラリを利用できる。
バイト列や数値の読み書きへの利用は、自作する RTP/RTCP の解析・検証・状態管理を置き換えない範囲とする。
メディア本文のデコード・再エンコードは行わない。

C-Plane と D-Plane は論理的に分離し、SFU は Node host が制御する独立した Rust Worker プロセスとして実行する。複数 Room の収容、容量予約、idle と orphan の状態遷移は [D-Plane のプロセスモデルと IPC 境界](../platform/dplane.md)に従う。

採用する既存実装のバージョン、設定、依存する機能を記録する。
実装と検証は、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)に従う。

## セキュリティ

SFU は、C-Plane が認可したルーム・参加端末・接続・発行・購読の対応に従って転送する。
WebRTC Transport の認証に成功したことだけで、発行・購読の権限を取得したとは扱わない。
パケット中の SSRC、MID、RID などの識別情報だけで、別の発行や購読へ対応付け直さない。

発行・購読、エンコーディング・レイヤーの対応、パケット処理量、転送帯域、再送用データ、キュー、タイマー、通知待ち状態に、共通の資源管理要件を適用する。
並行する操作や SFU 移行中の資源にも上限を適用する。
確保・解放の結果が不明な場合は、[共通の資源管理](../platform/resources.md)に従って照合・隔離・安全な回収を行う。

移行先で転送を許可する前に、現在の参加・発行・購読権限と、新しい WebRTC Transport の利用条件を確認する。旧 SFU の割り当てや過去の認可結果だけでは、この確認を満たさない。移行中や切り替え後に旧 SFU の遅延した処理が届いても、新しい接続や購読状態の変更・解放には適用しない。

ログ・計測・エラー通知には、認証情報、暗号鍵、メディア本文、パケット全体を出力しない。
ルーム・参加端末・発行・購読の識別情報や通信状況は、必要な範囲だけ記録し、アクセス制御と保持期限を適用する。

## 受け入れ条件

実際の Browser SDK、Signaling、SFU、WebRTC Transport、STUN / TURN を組み合わせて検証する。
通常動作に加え、損失・遅延・重複・順序逆転、購読変更、権限失効、接続切断、SFU 障害を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 資源上限と回収 | 並行する発行・購読・再送・移行でも予約を含む上限を超えない。結果不明や遅延通知による二重計上・誤解放を防ぎ、隔離した資源を安全に回収できる |
| Worker の起動・停止 | Room 0 かつ予約 0 で 30 秒後に停止し、新規 Room で停止をキャンセルする。Worker 数を 0 にでき、停止後のプロセスが残らない |
| Room の閉鎖 | 明示退出は処理完了後に閉じ、異常切断は 30 秒の猶予後に閉じる。再接続で閉鎖をキャンセルし、C-Plane の Room を消さない |
| 容量予約 | 空き枠 1 に対する同時 Room 作成で確保が 1 件だけになる。予約中の Worker を idle で停止しない |
| 再起動時の復旧 | Node host 再起動ではメディアが継続し、Worker 再起動では影響 Room が再配置され、Signaling 再起動では孤児を確定してから閉じる |
| 計画的な SFU 移行 | 新旧 SFU 間で必要な需要を維持し、現在の権限と新しい WebRTC Transport を確認して切り替える。識別情報を維持し、二重再生や古い処理による新状態の破壊を起こさない |
| 障害・退役期限 | 旧接続を維持できない場合は一時中断を許容して復旧する。再試行で退役期限を延長せず、期限到達時の自動再接続を確認する |
| ログ・通知 | 認証情報、暗号鍵、メディア本文、パケット全体を出力しない。識別情報・通信状況の記録にアクセス制御と保持期限を適用する |

性能試験は、[共通の収容人数・品質の基準条件](../platform/verification.md#収容人数品質受け入れ条件)に従う。
100 人の収容性能は、同時発行数、購読数、解像度、フレームレート、品質などの基準負荷を固定して評価する。
比較する試験間で負荷条件を変えず、条件の異なる試験結果を同じ基準による性能比較として扱わない。
100 人を目標とし、到達しない場合も同じ基準負荷で収容できた人数と制約を記録する。
測定の完了と性能目標の達成は区別して記録し、100 人に到達しなかった場合は、測定を完了しても性能目標は未達として扱う。
需要に応じた停止・再開については、適用前後の送信ビットレートと送信元の参加端末の CPU 使用量、停止・再開の所要時間、再開後のデコード開始時間を測定する。

SFU 移行では、定常時に加え、新旧接続が重なる間の接続数、送信品質、参加端末・サーバーの CPU・メモリ・帯域を測定する。
音声・映像の中断時間と、退役期限での再接続結果を記録する。
性能・復旧時間の合否基準は、対応条件ごとに試験前に定め、実測結果と合わせて記録する。
安全性の要件は、性能目標の達成を理由に緩和しない。

Chrome・Firefox・Safari 間で相互接続を確認する。
必要な API の利用可否と、実際の転送・停止・再開・復号・デコードの成功を分けて記録する。
結果には、ブラウザー・Browser SDK・サーバーのバージョン、Worker の構成とプロセス数、idle・orphan の設定、コーデック、Simulcast・SVC、E2EE、ネットワーク、設定した期限・資源上限を含める。

検証方法と結果の扱いは、[SFU 共通の検証条件](forwarding.md#共通の検証方法と結果の記録)に従う。
