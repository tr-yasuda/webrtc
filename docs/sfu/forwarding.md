# SFU の発行・購読とメディア転送

発行・購読の管理と、RTP/RTCP の対応付け・書き換え・再送・転送停止を定める。転送品質は [品質制御](quality.md)、配置と移行は [配置仕様](placement.md)で定める。

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## 音声・映像・画面共有の転送

SFU は、参加端末が発行した音声・カメラ映像・画面共有を、購読関係に従って転送する。
これらを独立した発行として扱い、開始・停止・購読変更を個別に行えるようにする。

同じルームの全参加端末が、マイクとカメラを同時に有効にできるようにする。
実際の転送対象と品質は、購読設定、利用権限、参加端末・ネットワーク・サーバーの容量に従って決定する。
収容人数と品質は、共通仕様の基準条件で検証する。

SFU は、ルーム・参加者・参加端末・発行の識別情報と、対象接続で交渉した SSRC、MID、RID、Payload Type などの対応を管理する。パケットを受け取ると、WebRTC Transport で認証・検証されたものだけをこの対応に従って対象の発行へ取り込む。パケット中の識別情報だけで新たな発行や転送先を登録することはなく、転送先は現在の購読関係と権限から、同じルームの許可された参加端末に絞る。

SFU は、受信した SRTP/SRTCP を WebRTC Transport で認証・復号した後も、内部の SFrame の暗号文を復号・再暗号化せずに転送する。転送判断には、交渉した RTP ヘッダー拡張など、SFU が参照できる情報を使う。必要な情報が暗号化されていて判断できなくても、復号鍵を要求して補わない。

購読先へ送る SSRC、Payload Type、RTP シーケンス番号、RTP タイムスタンプ、ヘッダー拡張を変更する場合は、その接続の交渉結果と RTP/RTCP の状態に合わせ、音声・映像の同期に必要な時刻情報との整合性を維持する。書き換えに必要な情報と E2EE で変更を禁止する情報を区別し、SFrame の暗号文と追加認証データに含めた情報を、受信先の参加端末が認証できる状態で維持する。[E2EE・鍵管理](../e2ee/media.md#sframe-による音声映像の保護)に従う。

SRTP/SRTCP の保護単位は、参加端末と SFU 間の WebRTC Transport とする。各購読先へ送信する際は、その WebRTC Transport の鍵・SSRC・パケット番号などに従って SRTP/SRTCP を暗号化・認証する。暗号状態の条件は、[WebRTC Transport](../transport/secure-transport.md#暗号化通信の確立維持)に従う。

送信元と受信先の参加端末が利用できるコーデック、RTP Payload Format、ヘッダー拡張、フィードバック方式を交渉し、共通する条件で転送する。
SFU によるメディア本文のデコード・再エンコードによるコーデック変換は、今回の対象外とする。
互換性がない場合は、その購読を成立させず Browser SDK に理由を通知する。

RTCP は、参加端末と SFU 間の受信状態、損失、再送、キーフレーム要求、帯域・輻輳制御に必要な情報として処理する。
受信側の要求を、その参加端末が購読する発行と送信経路へ対応付ける。
書き換えた SSRC や RTP シーケンス番号に対する要求を、別の発行や元の番号へ誤って適用しない。
[RFC 8834](https://www.rfc-editor.org/rfc/rfc8834.html)に従って、対応する機能を交渉する。

再送時は、交渉した方式と保持中のデータに応じて処理する。

- 生成済みの SRTP 暗号文を再送する場合は、同じ WebRTC Transport であることと、暗号文に対応する鍵・SSRC・パケット番号などの保護条件と保護対象の内容が維持されていることを確認する。
- RTX などで新しい RTP パケットを生成する場合や、保護対象のヘッダー・内容を変更する場合は、対象の WebRTC Transport の状態に従って新たに暗号化・認証する。RTX などで元の SFrame 暗号文を利用する場合も、外側の SRTP 保護の鍵と IV の組は再利用しない。

再送用データには件数・総バイト数・保持時間の上限を設ける。再送で映像を復旧できない場合は必要に応じてキーフレームを要求する。同じ発行に対する複数購読先からのキーフレーム要求などは不要な重複を抑え、要求と再送の両方に処理量と帯域の上限を適用する。

SFU は、購読先ごとに送信量、送信待ちデータ、損失と輻輳の状態を管理する。遅い購読先のために、ほかの購読先や発行元の処理が無期限に待たないよう、各キューに有限の上限を設け、遅延が蓄積した場合はメディアの依存関係を考慮して転送量を減らす。

発行が終了した場合や、購読が解除された場合、権限が失効した場合、WebRTC Transport の利用条件を失った場合は、対象の転送を停止する。停止条件は処理中・送信待ち・再送待ちのデータにも適用し、遅延した通知や再送要求で転送を復活させない。送信への引き渡しと停止が競合する場合は、[セキュリティ](#セキュリティ)の確定順序に従う。

受信対象、転送品質、Simulcast・SVC を利用する場合の選択・切り替え条件は、[品質制御仕様](quality.md#受信対象の選択)で定める。

## 受信対象の選択

参加端末は、受信する音声・カメラ映像・画面共有の発行を選択できる。
購読する発行の選択と、その発行から転送する品質の選択を分けて扱う。

購読の追加・変更・解除は、C-Plane が現在の権限と対象発行を確認して受け付ける。
SFU は、確定した購読関係に従って転送する。
品質の自動調整によって、購読していない発行を追加しない。

## 自作範囲・既存実装の利用

SFU のメディア転送と品質制御の中核処理は Rust で実装する。
アプリケーションからの操作、認可、配置・移行の制御は TypeScript の C-Plane が担う。

発行・購読と参加端末を対応付け、転送対象を決定し、変更・終了を反映する処理を自作する。
RTP/RTCP の転送では、パケット・フィードバックの対応付け、ヘッダーの書き換え、転送先ごとの状態管理を行う。

再送対象の保持、NACK・RTX の処理、キーフレーム要求の集約・重複抑制も自作する。
キュー・保持データの制限と、並行する変更の処理も自作する。
権限失効時に転送を停止し、資源を解放する処理も含める。

既存の SFU 製品や完成済みのメディア転送エンジンに、これらの中核処理を委ねない。

ICE、DTLS、SRTP/SRTCP は、[ICE 仕様](../transport/ice.md)と[暗号化通信仕様](../transport/secure-transport.md)に従う共通処理を利用する。
SFU に同じプロトコル処理や暗号状態を重複実装しない。
SFU は、転送先の SSRC、RTP シーケンス番号、RTP タイムスタンプ、RTX などの RTP 情報を決定する。
WebRTC Transport は、その結果に基づいて、対象接続の SRTP/SRTCP の暗号状態、ROC、パケットインデックス、リプレイ判定を管理する。
SFU による書き換え、レイヤー切り替え、再送が WebRTC Transport の暗号状態と矛盾せず、鍵と IV の一意性を維持することを保証する。
同じ RTP パケットの再送と、RTX などによって新しい RTP パケットを生成する場合を区別する。
既存の SRTP 暗号文を再送する場合は、保護済みの内容と、その暗号文に対応する鍵・SSRC・パケット番号などの保護条件を維持する。
RTX や書き換えによって新たに暗号化する場合は、WebRTC Transport が鍵と IV の再利用を防ぎ、同じ鍵・IV で異なる内容を暗号化しない。

汎用的な入出力、非同期実行、時刻管理、メモリ管理、計測には既存ライブラリを利用できる。
バイト列や数値の読み書きへの利用は、自作する RTP/RTCP の解析・検証・状態管理を置き換えない範囲とする。
メディア本文のデコード・再エンコードは行わない。

C-Plane と D-Plane の分離は論理的な責務の分離とし、別プロセスでの実行を必須としない。
Rust の実行方式は Wasm、Native Addon、独立 Worker を選択肢として残し、後続の技術選定で決定する。

採用する既存実装のバージョン、設定、依存する機能を記録する。
実装と検証は、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)に従う。

## セキュリティ

SFU は、C-Plane が認可したルーム・参加端末・接続・発行・購読の対応に従って転送する。
WebRTC Transport の認証に成功したことだけで、発行・購読の権限を取得したとは扱わない。
パケット中の SSRC、MID、RID などの識別情報だけで、別の発行や購読へ対応付け直さない。

権限失効と、必要な権限情報を確認できない場合の停止条件は、Signaling・WebRTC Transport の仕様に従う。
Signaling の切断中も適用する。
処理中・送信待ち・再送待ちのデータにも停止条件を適用し、遅延した操作や通知によって転送を再開しない。

SFU は、各パケットが送信待ちキューを出た後、実際の送信処理へ引き渡す直前に、現在の購読と転送権限から送信開始の可否を確定する。転送処理の開始時や中間キューへの登録時に認可済みでも、この判定を行う。可否の確定後も実際の引き渡しまで待機させる場合は、引き渡し時に判定し直す。再送にも同じ条件を適用する。

同じ転送状態に対しては、送信開始の可否と購読解除・権限失効の確定に一貫した順序を設ける。解除・失効の確定が先なら、古い認可で新たな送信処理を開始しない。解除・失効より前に実際の送信処理へ引き渡したパケットは、到着や受信の取り消しを保証しない。同期方法は未確定とし、競合時の順序と停止条件は共通の状態遷移・資源管理の検証方針に従って検証する。

WebRTC Transport による認証後も、RTP/RTCP の長さ、形式、交渉結果、対象発行・購読との対応を検証する。
認証済みの参加端末から受信した場合も、内容を検証する。
不正なヘッダー拡張、依存関係、フィードバックによって、別の発行の状態を変更したり、保持状態を無制限に生成したりしない。

NACK、キーフレーム要求、受信品質・帯域の報告は、送信元が購読する発行と対象経路に対応付ける。
要求の頻度、再送量、送信元への通知量に上限を設ける。
一つの購読先からの過剰な要求によって、ほかの購読先の通信や発行元の処理を無制限に消費しない。

発行・購読、エンコーディング・レイヤーの対応、パケット処理量、転送帯域、再送用データ、キュー、タイマー、通知待ち状態に、共通の資源管理要件を適用する。
並行する操作や SFU 移行中の資源にも上限を適用する。
確保・解放の結果が不明な場合は、[共通の資源管理](../platform/resources.md)に従って照合・隔離・安全な回収を行う。

SFrame の復号鍵は SFU に渡さず、E2EE の保護を省略・解除して転送を成立させない。
SRTP/SRTCP の認証成功を、内部の SFrame 暗号文の正当性や、送信者本人による生成の証明とは扱わない。
SFrame の認証・復号と送信者に関する保証は、E2EE 仕様に従って参加端末側で扱う。

ログ・計測・エラー通知には、認証情報、暗号鍵、メディア本文、パケット全体を出力しない。
ルーム・参加端末・発行・購読の識別情報や通信状況は、必要な範囲だけ記録し、アクセス制御と保持期限を適用する。

## 受け入れ条件

実際の Browser SDK、Signaling、SFU、WebRTC Transport、STUN / TURN を組み合わせて検証する。
通常動作に加え、損失・遅延・重複・順序逆転、購読変更、権限失効、接続切断、SFU 障害を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 発行・購読 | 音声・カメラ映像・画面共有を独立して発行・購読できる。未購読・未許可の参加端末や別ルームへ転送しない |
| RTP/RTCP の対応 | SSRC、MID、RID、Payload Type と発行・購読の対応を維持する。書き換え後のフィードバックを正しい発行へ適用し、音声・映像の同期を維持する |
| 暗号保護 | SFrame 暗号文と必要な認証情報を維持し、受信先の参加端末で認証・復号できる。転送先ごとに SRTP/SRTCP を保護し、SFU に E2EE 復号鍵を渡さない |
| 再送と暗号状態 | 同じ保護済みパケットの再送と、RTX・書き換えによる新しい暗号化を区別する。レイヤー切り替え、番号の周回、SSRC の変更でも WebRTC Transport の ROC・パケットインデックスと矛盾せず、鍵と IV の一意性を維持する |
| NACK・キーフレーム要求 | 対象発行へ正しく対応付ける。要求の重複・集中を抑制し、処理量・再送量・保持時間の上限を超えない |
| 解除・失効と送信の競合 | キュー待機中・送信直前・再送中に解除や失効を発生させる。規定した確定順序に従い、解除・失効の確定後に古い認可で新たな送信処理を開始しない |
| 認証済みの不正入力 | 不正な RTP/RTCP、ヘッダー拡張、依存情報、フィードバックでも、別発行の状態変更、範囲外アクセス、無制限な状態生成を起こさない |
| 資源上限と回収 | 並行する発行・購読・再送・移行でも予約を含む上限を超えない。結果不明や遅延通知による二重計上・誤解放を防ぎ、隔離した資源を安全に回収できる |
| ログ・通知 | 認証情報、暗号鍵、メディア本文、パケット全体を出力しない。識別情報・通信状況の記録にアクセス制御と保持期限を適用する |

性能試験は、[共通の収容人数・品質の基準条件](../platform/verification.md#収容人数品質受け入れ条件)に従う。
100 人の収容性能は、同時発行数、購読数、解像度、フレームレート、品質などの基準負荷を固定して評価する。
比較する試験間で負荷条件を変えず、条件の異なる試験結果を同じ基準による性能比較として扱わない。
100 人を目標とし、到達しない場合も同じ基準負荷で収容できた人数と制約を記録する。
測定の完了と性能目標の達成は区別して記録し、100 人に到達しなかった場合は、測定を完了しても性能目標は未達として扱う。
需要に応じた停止・再開については、適用前後の送信ビットレートと送信元の参加端末の CPU 使用量、停止・再開の所要時間、再開後のデコード開始時間を測定する。

### 共通の検証方法と結果の記録

検証には、共通の実装・検証方針を適用する。

| 検証方法 | 重点対象 |
|---|---|
| TLA+ によるモデル検査 | 発行・購読の状態遷移、解除・失効と送信開始の競合、需要の集約、停止・再開、SFU 移行、資源の予約・解放 |
| Fuzzing | RTP/RTCP、ヘッダー拡張、依存情報、フィードバック、制御通知の解析・入力検証 |
| Property-based Testing | 書き換えと再送の対応、レイヤー切り替え、需要変更・通知の操作列、暗号状態との整合、資源計上 |
| 形式的な証明の評価 | 番号の対応・周回、需要集約、資源上限などの不変条件について、Lean 4・Verus・Aeneas の適合性を評価する |

モデル検査では、安全性に加え、必要な通信・処理・障害回復の前提の下で、停止・再開・移行・回収が完了する活性を検証する。
モデル検査、形式的な証明、Fuzzing、テスト、静的解析、実際の構成による統合試験の結果を区別する。
選定候補の評価や未検証の範囲を、証明済みとして扱わない。
