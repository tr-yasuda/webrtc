# SFU の品質制御とエンコーディングの停止・再開

購読関係に基づく品質選択、帯域配分、送信エンコーディングの停止・再開を定める。パケットの転送と送信時の認可は [転送仕様](forwarding.md)に従う。

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md) に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## 受信対象の選択

参加端末は、受信する音声・カメラ映像・画面共有の発行を選択できる。
購読する発行の選択と、その発行から転送する品質の選択を分けて扱う。

購読の追加・変更・解除は、C-Plane が現在の権限と対象発行を確認して受け付ける。
SFU は、確定した購読関係に従って転送する。
品質の自動調整によって、購読していない発行を追加しない。

購読ごとに、受信を希望する品質、許容する最大解像度・フレームレート、優先度を指定できるようにする。
具体的な API と値の表現は [Browser SDK 仕様](../client-sdk/browser.md)で定める。
指定した希望品質を、常に提供できる保証とはしない。

転送品質は、次の条件を合わせて決定する。

| 条件 | 判断に使う内容 |
|---|---|
| 発行側 | 実際に送信しているエンコーディング・レイヤーと、その依存関係 |
| 受信側 | 交渉したコーデック・機能、受信上限、参加端末から通知された受信条件 |
| 通信経路 | 推定帯域、損失、遅延、送信キューと輻輳の状態 |
| 購読設定 | 希望品質、上限、優先度 |
| 資源と権限 | 参加端末・ルーム・サーバーの上限と現在の利用許可 |

受信先の参加端末への経路で共有する帯域を、購読全体で配分する。
発行ごとに帯域全体を利用可能と見積もり、合計送信量が上限を超えることを防ぐ。
再送や制御通信に必要な送信量も考慮する。

帯域不足時は、既定では音声の継続を優先し、映像の品質低下や一時停止によって送信量を減らす。
画面共有・カメラ映像などの配分は、購読の優先度に従う。
アプリケーションが優先度を変更しても、権限・資源上限・WebRTC Transport の送信条件を超えない。

### エンコーディングとレイヤーの選択

Simulcast では、同じ発行に属する交渉済みのエンコーディングから、購読先ごとに転送対象を選ぶ。
別の発行として重複登録せず、切り替え時も発行・購読の識別情報を維持する。
[RFC 8853](https://www.rfc-editor.org/rfc/rfc8853.html)に従う。

SVC では、交渉した方式と、SFU が参照できる依存関係の情報に基づいて転送レイヤーを選ぶ。
選択したレイヤーの復号・デコードに必要な依存先を維持し、任意のパケット間引きだけで品質を変更しない。

E2EE と SVC を組み合わせる場合は、送信側が選択的に転送できる単位で SFrame 暗号文を構成する。
暗号文の途中を削除して、認証できないフレームを生成しない。
[RFC 9605 §6.1.3](https://www.rfc-editor.org/rfc/rfc9605.html#section-6.1.3)に従う。

### 需要の集約から停止・再開まで

エンコーディングは送信側が生成する符号化メディアを指し、レイヤーは品質や依存関係に応じて選択する階層を指す。
以下の停止・再開はエンコーディングの制御を指し、レイヤーの選択とは分けて扱う。
通常の転送レイヤー選択やビットレート制御とは別に、購読需要に応じて送信側のエンコーディングを動的に停止・再開できるようにする。
SFU は、現在の権限・購読設定・帯域配分に基づき、すべての購読先で必要なエンコーディングと依存レイヤーの需要を集約する。
切り替え準備中・再開待ちの需要も含め、一部の購読先が必要としているエンコーディングを、ほかの購読先の都合で停止しない。
停止中のエンコーディングへの新たな需要も判定し、現在受信しているパケットの有無だけで需要を判断しない。

どの購読先も必要としていないことを確認したエンコーディングについて、SFU は Signaling を通じて送信元の Browser SDK に停止を通知する。
新たな購読や品質変更で必要になった場合は、再開を通知する。
通知は、認可された送信元の参加端末・発行・交渉済みエンコーディングに対応付け、送信元の Browser SDK が適用する。
Browser SDK は、適用した状態、適用失敗、制御への非対応を通知し、SFU は要求した状態と実際の送信状態を区別する。
エンコーディングの停止によって発行・購読・キャプチャーデバイスを終了せず、発行・購読の識別情報を維持する。

停止・再開の判断と通知には更新の順序を識別できる情報を持たせ、遅延・重複した通知や古い適用結果で、現在の需要に基づく状態を上書きしない。
停止処理中に需要が生じた場合も、進行中の適用結果を照合し、最新の必要状態へ収束させる。
再接続や SFU 移行で需要情報を一時的に取得できなくても、需要がないとは判断しない。
移行中は旧・新 SFU の転送に必要な需要を集約し、一方の停止判断によって他方に必要な送信を停止しない。

短時間の需要変動で停止・再開を繰り返さないよう、停止までの待機条件と切り替え頻度の制限を設ける。
新たな需要への再開を停止用の待機条件で不必要に遅らせず、再開待ちの期限と失敗時の通知を定める。
通知・適用待ちの状態やキューには共通の資源上限を適用する。

再開時は、実際の送信再開と、必要なキーフレーム・依存関係などのデコード可能な条件を確認してから転送する。
現在の権限・WebRTC Transport・E2EE の条件を満たし、停止・再開によって鍵・カウンターを不正に初期化したり、Nonce を再利用したりしない。
再開待ちの購読先が、ほかの購読先への正常な転送を妨げない。

この機能は Simulcast・SVC と組み合わせ、送信側で実際に独立制御できる単位に適用する。
SVC の転送レイヤーを選択できても、送信側で各レイヤーを独立して停止できるとは限らない。
ストリーム全体しか停止できない構成では、いずれかの購読先に必要なレイヤーやその依存先の需要が残る間は、全体を停止しない。

Chrome・Firefox・Safari について、エンコーディングの停止・再開に必要な API の利用可否と、実際の送信停止・再開および受信側でのデコード成功を分けて確認する。
確認したブラウザーバージョン、コーデック、Simulcast・SVC の構成、E2EE の条件を記録する。
WebRTC API を利用する場合は、[W3C WebRTC のエンコーディング制御](https://www.w3.org/TR/webrtc/#dom-rtcrtpencodingparameters-active)に従い、交渉済みの構成と制約を維持する。
独立した停止・再開に対応しない環境では、その制約を Browser SDK から通知し、利用可能な既存の品質制御を適用する。
停止を要求しただけで送信資源が削減されたとは扱わず、非対応を理由に E2EE を無効化したり、SFU の再エンコードで補ったりしない。

### 制御できない場合と品質切り替え

Simulcast・SVC の利用可否は、ブラウザー、コーデック、交渉した機能、E2EE の組み込み条件ごとに確認する。
利用できない場合も、SFU が単一エンコーディングから任意の解像度やビットレートを生成できるとは扱わない。
利用可能な手段は、送信元の参加端末へのビットレート調整要求、コーデックの依存関係を維持できる範囲での転送量削減、映像転送の一時停止とする。
送信側が実際に品質を変更できるかどうかは、コーデックとブラウザーの対応状況に従って確認する。
調整要求の送信だけで、送信品質が変更されたとは扱わない。
SFU で復号・再エンコードして補わない。

エンコーディングやレイヤーの切り替えでは、必要なキーフレームや切り替え可能な境界を確認する。
切り替え先をデコードできる条件が整う前に、依存関係を破壊する転送を行わない。
キーフレーム要求には、[転送仕様の重複抑制と制限](forwarding.md#音声映像画面共有の転送)を適用する。

帯域や損失の短時間の変動で、品質を過度に往復させない。
品質を上げる条件と下げる条件、切り替え待ちの期限を定める。
待機中もキューと保持状態を無制限に増やさない。

購読設定の変更、発行の終了、権限失効、品質切り替えが並行した場合も、現在の購読と発行に対応する結果だけを適用する。
古い切り替え結果で、解除済みの購読を再開しない。

Browser SDK には、希望品質と実際の転送品質、品質制限・一時停止・復帰の状態と理由を通知する。
帯域調整で一時停止しても、購読の解除や参加端末の退出は行わない。
転送再開時にも、現在の権限と接続・鍵状態を確認する。

購読数、同時に転送するエンコーディング・レイヤー数、画面共有数には設定可能な上限を設ける。
並行する購読変更でも上限を超えない。
共通仕様の「他の9人のカメラ映像を購読する」という条件は性能測定の基準であり、製品の固定上限として扱わない。

## 自作範囲・既存実装の利用

SFU のメディア転送と品質制御の中核処理は Rust で実装する。
アプリケーションからの操作、認可、配置・移行の制御は TypeScript の C-Plane が担う。

品質制御では、帯域推定、購読間の帯域配分、Simulcast・SVC の選択と切り替えを自作する。
需要に応じた停止・再開では、購読需要と依存関係を集約し、送信元の Browser SDK へ通知する処理と、適用結果を現在の状態と照合する処理を自作する。

既存の SFU 製品や完成済みのメディア転送エンジンに、これらの中核処理を委ねない。

SFrame 暗号文の生成・復号と E2EE の鍵管理は、参加端末側で行う。
送信エンコーディングの停止・再開は、送信元の Browser SDK がブラウザーの機能を使って適用する。
SFU は、要求の通知と実際の適用完了を区別する。

汎用的な入出力、非同期実行、時刻管理、メモリ管理、計測には既存ライブラリを利用できる。
バイト列や数値の読み書きへの利用は、自作する RTP/RTCP の解析・検証・状態管理を置き換えない範囲とする。
メディア本文のデコード・再エンコードは行わない。

C-Plane と D-Plane の分離は論理的な責務の分離とし、別プロセスでの実行を必須としない。
Rust の実行方式は Wasm、Native Addon、独立 Worker を選択肢として残し、後続の技術選定で決定する。

採用する既存実装のバージョン、設定、依存する機能を記録する。
実装と検証は、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)に従う。

## セキュリティ

SFU は、C-Plane が認可したルーム・参加端末・接続・発行・購読の対応に従って転送する。
WebRTC Transport の認証に成功したことだけで、発行・購読の権限を取得したとは扱わない。
パケット中の SSRC、MID、RID などの識別情報だけで、別の発行や購読へ対応付け直さない。

権限失効と、必要な権限情報を確認できない場合の停止条件は、Signaling・WebRTC Transport の仕様に従う。
Signaling の切断中も適用する。
処理中・送信待ち・再送待ちのデータにも停止条件を適用し、遅延した操作や通知によって転送を再開しない。

各パケットについて、送信待ちキューを経た後、実際の送信処理へ引き渡す直前に、現在の購読と転送権限に基づいて送信開始の可否を確定する。
中間キューへの登録や、転送処理の開始時に行った認可だけを、この確定とは扱わない。
同じ転送状態に対する送信開始の可否の確定と、購読解除・権限失効の確定には、一貫した順序を設ける。
購読解除・権限失効の確定が先行した場合は、古い認可結果に基づく新たな送信処理を開始しない。
送信開始を確定した後も実際の引き渡しまで待機させる場合は、引き渡し時にこの判定をやり直し、古い送信許可を持ち越さない。
解除・失効の確定前に実際の送信処理へ引き渡し済みのパケットは、到着や受信を取り消せるとは保証しない。
再送にも同じ条件を適用する。
同期方法は未確定とする。
競合時の順序と停止条件は、共通の状態遷移・資源管理の検証方針に従って検証する。

エンコーディングの停止・再開は、認可された購読関係から集約した需要に基づいて決定する。
購読する参加端末から、送信元の参加端末に対する任意の停止・再開指示を直接適用しない。
通知と適用結果は対象の発行・エンコーディング・更新順序に対応付け、古い結果で現在の必要状態を上書きしない。

発行・購読、エンコーディング・レイヤーの対応、パケット処理量、転送帯域、再送用データ、キュー、タイマー、通知待ち状態に、共通の資源管理要件を適用する。
並行する操作や SFU 移行中の資源にも上限を適用する。
確保・解放の結果が不明な場合は、[共通の資源管理](../platform/resources.md)に従って照合・隔離・安全な回収を行う。

ログ・計測・エラー通知には、認証情報、暗号鍵、メディア本文、パケット全体を出力しない。
ルーム・参加端末・発行・購読の識別情報や通信状況は、必要な範囲だけ記録し、アクセス制御と保持期限を適用する。

## 受け入れ条件

実際の Browser SDK、Signaling、SFU、WebRTC Transport、STUN / TURN を組み合わせて検証する。
通常動作に加え、損失・遅延・重複・順序逆転、購読変更、権限失効、接続切断、SFU 障害を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 購読と品質の分離 | 品質調整で未購読の発行を追加しない。希望品質、実際の品質、制限・停止・復帰の理由を Browser SDK に通知する |
| 帯域配分 | 受信先の参加端末の購読全体で帯域を配分し、再送・制御通信も計上する。帯域不足時は既定で音声を優先し、遅い購読先がほかの通信を無期限に妨げない |
| Simulcast・SVC | 交渉済みの構成から選択し、必要な依存関係を維持する。切り替え先をデコードできる状態から転送し、頻繁な品質の往復を抑制する |
| 需要の集約 | 全購読先と切り替え準備中の需要を集約する。一部の購読先が必要とするエンコーディングや依存レイヤーを停止しない |
| エンコーディングの停止・再開 | 需要がなくなれば送信元の Browser SDK を通じて停止し、新たな需要で再開する。通知だけで成功とせず、実際の送信停止・再開と受信側のデコードを確認する |
| 停止・再開の競合 | 処理中の需要変更、通知・適用結果の欠落・遅延・重複・順序逆転でも、古い状態へ戻らない。必要な通信が回復する前提で最新の必要状態へ収束し、待機期限では失敗を通知する |
| 制御できない構成 | SVC の独立停止可否を実際の制御単位で判断する。非対応時は制約を通知し、既存の品質制御を適用する。任意の解像度生成や E2EE の解除で補わない |
| 解除・失効と送信の競合 | キュー待機中・送信直前・再送中に解除や失効を発生させる。規定した確定順序に従い、解除・失効の確定後に古い認可で新たな送信処理を開始しない |
| 資源上限と回収 | 並行する発行・購読・再送・移行でも予約を含む上限を超えない。結果不明や遅延通知による二重計上・誤解放を防ぎ、隔離した資源を安全に回収できる |
| ログ・通知 | 認証情報、暗号鍵、メディア本文、パケット全体を出力しない。識別情報・通信状況の記録にアクセス制御と保持期限を適用する |

性能試験は、[共通の収容人数・品質の基準条件](../platform/verification.md#収容人数品質受け入れ条件)に従う。
100 人の収容性能は、同時発行数、購読数、解像度、フレームレート、品質などの基準負荷を固定して評価する。
比較する試験間で負荷条件を変えず、条件の異なる試験結果を同じ基準による性能比較として扱わない。
100 人を目標とし、到達しない場合も同じ基準負荷で収容できた人数と制約を記録する。
測定の完了と性能目標の達成は区別して記録し、100 人に到達しなかった場合は、測定を完了しても性能目標は未達として扱う。
需要に応じた停止・再開については、適用前後の送信ビットレートと送信元の参加端末の CPU 使用量、停止・再開の所要時間、再開後のデコード開始時間を測定する。

Chrome・Firefox・Safari 間で相互接続を確認する。
必要な API の利用可否と、実際の転送・停止・再開・復号・デコードの成功を分けて記録する。
結果には、ブラウザー・Browser SDK・サーバーのバージョン、Rust の実行方式、コーデック、Simulcast・SVC、E2EE、ネットワーク、設定した期限・資源上限を含める。

検証方法と結果の扱いは、[SFU 共通の検証条件](forwarding.md#共通の検証方法と結果の記録)に従う。
