# 資格情報の発行・検証・更新・失効

参加 JWT と用途別資格情報について、発行から受け入れ・更新・失効までを定める。参加 JWT は顧客アプリサーバーが署名し、Signaling が検証する。権限の管理と失効の反映期限は [認可仕様](authorization.md)に従う。

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md)に従う。
各プロトコルの認証・状態管理は、それぞれのコンポーネント仕様に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## 利用場面

参加から退出までの流れは、[認証・認可の利用場面](authorization.md#利用場面)を参照する。
参加 JWT は HS256 署名付き JWT とする。Management UI のログインには IDaaS の OpenID Connect を使う。TURN・ICE・DTLS・内部サービスの資格情報は、それぞれの用途に応じた方式を使う。

## 参加 JWT の発行・更新・失効

参加 JWT は、Browser SDK が対象ルームへの参加や許可された操作に使用するアクセストークンとする。
TURN、ICE、内部サービス、管理操作の資格情報として無条件に流用しない。

### 顧客アプリサーバーが署名して Browser SDK へ渡すまで

顧客アプリサーバーは、自社の認証基盤で利用者を確認し、Management で払い出した ApplicationSigningKey を使って参加 JWT に署名する。プラットフォームは利用者認証を代行せず、参加 JWT の発行窓口にならない。

参加 JWT の header と claim は、次の形式とする。

| 位置 | claim | 値と確認内容 |
|---|---|---|
| header | `alg` | `HS256`。他の値を受け入れない |
| header | `typ` | `JWT` |
| header | `kid` | ApplicationSigningKey の識別子。Signaling はこの値で有効鍵を選ぶ |
| payload | `iss` | Application ID |
| payload | `aud` | `webrtc.v1` |
| payload | `sub` | ExternalUser 識別子 |
| payload | `iat` / `exp` | 発行時刻と有効期限。`exp` は最大 24 時間までとする |
| payload | `jti` | 省略可能。監査・重複排除に使う場合だけ含める |
| payload | `project` | 対象 Project 識別子 |
| payload | `room` | 対象 Room 識別子 |
| payload | `grants` | 許可する操作のオブジェクト |

参加 JWT の TTL は 5 分程度を推奨する。`exp` が発行時刻から 24 時間を超える参加 JWT は、Signaling が受け入れない。SDK の発行ヘルパーが既定値を持つ場合は 5 分程度とし、顧客アプリケーションは用途に応じてさらに短い値へ変更できる。

`sub` は監査・利用量・Room 内の識別に使うため、不要な個人情報や表示名を含めない。顧客アプリケーションが管理する安定した ExternalUser 識別子を使う。

`grants` には、次の用途別キーを使用する。

| キー | 許可する操作 |
|---|---|
| `room.create` | 未作成 Room を最初の参加時に作成する |
| `room.join` | 対象 Room へ参加する |
| `media.publish` | 自分の音声・カメラ映像・画面共有を発行する |
| `media.subscribe` | 同じ Room で発行済みの音声・映像を購読する |
| `data.send` | 同じ Room の DataChannel へデータを送信する |

将来は `recording`・`transcription` など、追加機能ごとに新しい grant を定義して拡張する。Signaling は未知の grant と未サポートの grant を黙って無視せず、参加要求を拒否する。`grants` の値は真偽値以外を受け入れない。

発行するトークンには、直接格納するか、検証時に取得できる情報として、次を対応付ける。

| 情報 | 確認する内容 |
|---|---|
| 発行元・利用先・用途 | 信頼する Application が、対象サービスでの参加・操作用に発行したものか |
| 対象利用者・参加者 | 誰の参加・操作に使用できるか |
| 対象ルーム・操作範囲 | どのルームで、何を許可できるか |
| 有効期間 | いつから、いつまで受け入れられるか |
| 識別・管理情報 | 更新・失効・監査で対象のトークンや発行関係を識別できるか |

発行時に参加端末を指定する場合は、トークンと対象端末の対応も検証する。参加処理で端末を登録する場合、既存の別の参加端末の引き継ぎには [Signaling の再接続条件](../signaling/session.md#再接続)を適用し、トークンや参加端末識別情報の所持だけでは許可しない。

Signaling は署名に加え、`kid` で選んだ有効鍵、`iss`・`aud`・`project`・`room`・`grants`・`exp` と、現在の Room・Session・失効状態を確認する。鍵が失効済みの場合、新しい参加 JWT を受け入れない。ApplicationSigningKey の秘密値は暗号学的に安全な乱数で生成し、最低 256 bit を確保する。

Browser SDK への受け渡しは、保護された通信と、認証した利用者との対応を確認できる方法で行う。
URL、ログ、エラー報告、公開状態、開発者向けデバッグ機能へ露出させない。
ブラウザーの WebSocket API の制約を考慮し、Signaling 接続の認証方法と合わせて選定する。

### 更新・期限切れ・失効

顧客アプリサーバーは、参加 JWT を再発行するときに利用者の現在の状態を確認し、その時点で許可する範囲だけを `grants` に記載して再度署名する。更新用の長期資格情報を Browser SDK に保持させることは必須としない。失効した ApplicationSigningKey での再署名は、新しい参加 JWT として受け入れない。

更新後は、新旧のトークンを併用できる条件と期間に上限を設ける。更新前の参加端末、通話時間の起点、SFU の退役期限を引き継ぐ。トークンの更新だけでは、利用権限、権限の再確認期限、プロトコル状態の寿命を延長しない。各期限の扱いは [認可仕様](authorization.md#有効期限権限変更失効の反映)に従う。

トークンが期限切れの場合、そのトークンによる新しい参加・操作の認証には使用しない。
既存の通信を継続できるかは、現在の利用権限、権限情報の有効性、WebRTC Transport・E2EE の条件に基づいて判断する。
トークンの更新に失敗したことだけで直ちに退出させるとは限らないが、必要な権限を期限内に確認できなければ、既存仕様に従って対象の操作・通信を停止する。

失効時は、Application・ApplicationSigningKey・Room・Session・Participant のどれが対象かを特定し、既存通信の利用権限を含むかを確認する。初期提供では `jti` 単位の個別トークン失効を提供しない。`jti` は監査・重複排除のためにだけ使う。

- ApplicationSigningKey が対象なら、Signaling の鍵キャッシュを無効化し、その鍵による新しい参加 JWT を拒否する。既存接続は自動終了しない。
- Room・Session・Participant が対象なら、Management の強制切断・Room 削除コマンドに従って、Signaling と D-Plane が対象通信を停止する。

いずれの場合も、旧トークン、発行・更新結果、遅延した通知で反映済みの失効を取り消さない。

### 並行処理と結果不明への対応

顧客アプリサーバーによる参加 JWT の再署名と ApplicationSigningKey の失効が並行する場合は、Signaling が鍵状態で確定順序を判断する。失効が反映済みなら、その鍵で署名した新しい参加 JWT を受け入れない。失効前に有効だった既存 Session は、強制切断を別に行わない限り自動終了しない。

発行・更新の応答が失われた場合は、同じ要求の再試行で権限や有効期間が意図せず拡大しないようにする。結果不明の扱い、再試行、発行記録の保持には、それぞれ期限と資源上限を設ける。

監査には、ApplicationSigningKey の作成・ローテーション・失効と、強制切断・Room 削除の要求元、対象、結果を確認するために必要な情報を記録する。
トークン本体、署名鍵、更新用の秘密情報は記録しない。

## 用途別の資格情報と検証条件

資格情報は用途ごとに、発行する側、受け入れる側、許可できる操作、検証条件を定める。
同じ発行元や暗号方式を使っていても、別用途の資格情報を無条件に受け入れない。

| 用途 | 受け入れる側 | 確認する範囲 |
|---|---|---|
| 外部認証の情報 | Management UI の IDaaS 連携処理 | 設定済みの連携先、対象利用者、認証結果の有効性 |
| 外部アプリケーションの資格情報 | Management API | 要求元、扱える利用者・資源・操作、委任範囲 |
| 参加 JWT | Signaling の参加・操作の受け付け | 対象利用者・ルーム・操作、有効期間、失効、現在の利用権限 |
| TURN 資格情報 | TURN サーバー | プロトコル認証、資格情報の有効性、Allocation の所有者、用途別の利用許可 |
| ICE 資格情報 | 対象接続の ICE エージェント | 接続・ICE 世代、ICE 接続確認の認証と要求・応答の対応 |
| 内部サービスの資格情報 | 指示や状態通知を受け付ける内部コンポーネント | サービスの識別、指示できる対象・操作、資格情報の有効性 |
| 管理操作の資格情報 | Management API | 管理主体、操作対象、管理権限、有効期間と失効 |

参加者の資格情報を持っていることだけで、管理操作や内部サービスの指示を許可しない。
外部アプリケーションの資格情報を持っていることだけで、任意の利用者として参加させない。
管理操作の認証方式と内部サービスの認証方式も、それぞれの用途に応じて選定する。

各用途について、次の検証条件を定める。

| 条件 | 検証する内容 |
|---|---|
| 発行元と真正性 | 用途に応じて、信頼する発行元や、認可された接続で生成・共有した資格情報との対応を確認し、不正な情報を受け入れないか |
| 利用先と用途 | このコンポーネントが、この処理で受け入れてよい資格情報か |
| 対象の対応 | 利用者・サービス、ルーム、参加端末、接続などが処理対象と一致するか |
| 操作範囲 | 要求された操作が、資格情報の範囲と現在の権限の両方に含まれるか |
| 有効期間と失効 | 利用可能な期間内であり、反映済みの失効に該当しないか |
| 再利用条件 | 別接続への流用、再送、更新、再接続で使用できる条件を満たすか |

共通の検証条件は、用途ごとに適切な認証・検証手順へ対応付ける。
すべての資格情報に、同じ発行元検証や署名検証を要求しない。
参加 JWT や外部アプリケーションの資格情報は、採用する発行・検証方式に従う。
ICE のように接続ごとに生成・共有する資格情報は、認可された接続・ICE 世代との対応と、プロトコルの認証手順によって確認する。

これらの情報を、すべての資格情報へ同じ形式で格納することは要求しない。
直接含まれる情報、サーバー側の記録、認可済みの接続状態などを組み合わせて確認できるようにする。
TURN・ICE・DTLS のメッセージ形式、認証・相手検証の手順、状態管理の条件は、既存の各プロトコル仕様を維持する。

受け入れる用途は、受け付けるサービス・機能と信頼する設定に基づいて決定する。
資格情報自身が申告した用途・発行元・検証方式だけで、受け入れ条件を変更しない。
ある用途の検証に失敗した資格情報を、別用途として自動的に試し直して受け入れない。

資格情報の検証と、Signaling が管理する権限情報の確認を分ける。
各コンポーネントは、有効期限内の権限情報を利用でき、毎回 Signaling へ問い合わせる必要はない。
ただし、対象コンポーネントに反映済みの失効や接続の引き継ぎを、古い情報で覆さない。
必要な情報を期限内に確認できない場合は、既存仕様に従って対象の処理・通信を停止する。

トークン単体の失効、通信権限の失効、プロトコル状態の期限切れを区別する。
既存接続への影響は、参加 JWT・TURN・WebRTC Transport など、それぞれの確定済み条件に従う。
資格情報が更新されたことだけで、別用途の資格情報や通信状態の期限を更新しない。

単独 STUN Binding によるアドレス確認は、資格情報を要求しない既存方針を維持する。
この例外を、ICE 接続確認や TURN の利用認証へ適用しない。
DTLS の証明書検証と E2EE の鍵確認も、参加 JWT や利用権限の確認の代わりにはしない。

資格情報は必要な相手にだけ渡す。
Browser SDK には利用に必要な参加 JWT や TURN 資格情報を渡せるが、サーバー側の署名鍵、TURN の共通秘密情報、内部サービス用の資格情報は渡さない。
D-Plane が利用者の資格情報そのものを受け取る必要があるか、検証済みの権限情報を受け取るかは、後続の設計で決定する。
どちらの場合も、指示元・対象・操作・有効期限の確認を省略しない。

## プロトコル資格情報との連携

Signaling は、プロトコルの利用を許可する主体・接続・用途を確認する。
各プロトコルの処理は、その許可と、プロトコル固有の認証・状態管理の両方を適用する。
共通のトークン形式で、TURN・ICE・DTLS の手順を置き換えない。

| 対象 | プラットフォーム側の責務 | プロトコル側の責務 |
|---|---|---|
| 単独 STUN Binding | 公開条件と資源制限を管理する | 認証不要の Binding を既存仕様に従って処理する |
| TURN | 資格情報の発行、利用者・参加端末との対応、用途・中継先の許可を管理する | 長期資格情報方式の認証、Allocation の所有者確認、Permission・Channel Binding と転送条件を適用する |
| ICE | 対象接続・参加端末・交渉との対応を管理し、必要な接続情報を交換する | 資格情報の生成・使用、ICE 接続確認、ICE 世代と経路の状態を管理する |
| DTLS | 認可された接続と、交換する証明書フィンガープリントなどの対応を管理する | 用途に応じた相手検証、ハンドシェイク、鍵確立・使用上限を適用する |

TURN 資格情報は、Signaling が現在の利用権限を確認して発行する。
ブラウザー用と SFU 自身の TURN 利用を区別し、資格情報の所持だけで別用途の許可を取得できないようにする。
生成・検証に必要な情報を TURN 側へ安全に配布する。
共通秘密情報を使用する方式を採用する場合も、それを Browser SDK へ渡さない。

TURN 資格情報の更新・失効は、既存 Allocation と利用者・参加端末の対応を維持して処理する。
ユーザー名や認証に用いる秘密情報が変わる場合の新しい Allocation の作成、通常の資格情報期限切れ後の転送、明示的な失効による停止は、[TURN Allocation 仕様](../turn/allocation.md)に従う。
参加 JWT の更新だけで、TURN 資格情報や Allocation を更新しない。

ICE 資格情報は、ブラウザー側ではブラウザーの ICE エージェント、SFU 側では自作する ICE エージェントが生成・管理する。
Signaling は、認可された接続と交渉に対応付けて交換する。
参加 JWT や TURN パスワードを、ICE の秘密情報として流用しない。
ICE restart では新しい世代の資格情報を使用し、旧世代の要求・応答を新世代の認証結果として扱わない。

ICE の認証成功、経路の到達性、Consent Freshness、プラットフォームの利用権限を区別する。
ICE 接続確認に成功しても、未許可の発行・購読・データ通信を開始しない。
利用権限が失効した場合、ICE 資格情報や経路が有効なままでも、既存仕様の期限内に対象通信を停止する。

STUN / TURN の TLS・DTLS では、サーバーが適切な証明書を提示し、接続するクライアントが信頼・有効性・接続先名を検証する。
WebRTC Transport の DTLS では、対象接続の正当な交渉で受け取ったフィンガープリントと実際の証明書を照合する。
これらの用途を混同せず、参加 JWT の検証を証明書検証の代わりにしない。

DTLS Association の継続・再確立、証明書情報の変更、ICE restart との関係は、Signaling・WebRTC Transport 仕様に従う。
トークン更新や ICE 資格情報の変更だけで、証明書・フィンガープリントの変更を許可しない。
DTLS・SRTP/SRTCP の鍵と、参加端末間の E2EE の鍵は、それぞれの仕様に従って管理する。

再接続・SFU 移行では、新旧の資格情報、接続、ICE 世代、Allocation、権限情報の対応を維持する。
新しい接続先へ切り替えたことだけで権限を広げず、旧接続の資格情報や遅延通知で新しい接続を操作させない。
移行中に新旧の資源を同時に確保する場合も、共通の資源上限を適用する。

ApplicationSigningKey の配布・キャッシュ無効化は [Management 仕様](../platform/management.md#applicationsigningkey)に従う。TURN・ICE・DTLS の資格情報は、それぞれの仕様に従う。配布・更新・失効情報の伝達に失敗した場合は、用途ごとの有効期限と停止条件に従い、再試行だけで期限を延長しない。

## 署名・検証と鍵の管理

参加 JWT の署名・検証には HS256 を使う。TURN・ICE・DTLS・内部サービスの認証方法は、それぞれの用途に応じて選定する。
すべての資格情報に署名付きトークンを要求しない。
署名、MAC、参照先への照会、プロトコル固有の認証など、採用した方式で必要な検証を行う。

署名・MAC・ハッシュ・暗号学的な乱数生成には、既存の安全な実装を利用する。
暗号アルゴリズムを独自実装しない。
利用を許可するアルゴリズム、鍵形式、鍵の強度と用途を設定し、入力された資格情報の指定だけで変更しない。

署名や MAC の検証に成功しても、それだけで操作を許可しない。
発行元・利用先・用途・対象・有効期間・失効と現在の権限は、「用途別の資格情報と検証条件」に従って確認する。
署名は改ざんを検出するために使い、資格情報の内容の秘匿は保証しない。

鍵の管理では、次を区別する。

| 対象 | 管理する内容 |
|---|---|
| 発行用の鍵・秘密情報 | 使用できる発行処理、用途、保管先、アクセス権限、使用期間 |
| 検証用の鍵・情報 | 信頼する発行元、利用用途、取得元、更新条件、受け入れ期間 |
| 鍵の識別情報 | 対象の発行元・用途・鍵を取り違えずに選ぶための対応 |
| 更新・失効の記録 | 新旧の切り替え、受け入れ終了、漏洩時の対象と処理結果 |

発行用の秘密情報にアクセスできる処理を限定する。
Browser SDK・React SDK に、サーバー側の署名鍵や TURN の共通秘密情報を渡さない。
ApplicationSigningKey の秘密値は顧客アプリサーバーと Management・Signaling の必要範囲だけに配布する。Management は Cloud KMS で暗号化した `secret_ciphertext` を保存し、DB に平文を保存しない。作成権限のある Owner / Admin は、作成直後の応答だけで秘密値を一度受け取る。通常の取得・再表示では返さない。

Signaling は、JWT header の `kid` を設定済み ApplicationSigningKey に対応付けて検証鍵を選ぶ。
資格情報に含まれる鍵の識別子や URL だけを根拠に、任意の鍵・接続先を信頼しない。
不明な鍵を受け取った場合も、未検証の鍵で受け入れたり、検証を省略したりしない。
鍵取得の再試行には、処理量・待機時間・保持状態の上限を設ける。

通常の鍵更新では、新しい ApplicationSigningKey を追加し、顧客アプリサーバーが新しい `kid` へ切り替えた後に旧鍵を失効する。ローテーション中は新旧鍵を併用し、失効済み鍵による新しい参加 JWT は拒否する。
旧鍵を受け入れる場合も、資格情報自体の期限・失効・現在の権限を確認する。
鍵の更新や検証鍵の再取得によって、資格情報の有効期限を延長しない。

鍵の漏洩や不正使用が疑われる場合は、通常の更新と区別して扱う。対象鍵を直ちに失効し、Signaling の鍵キャッシュを無効化して新しい参加 JWT を拒否する。
鍵の失効と既存 Session の強制切断は別操作とする。必要な場合は ProjectUser が Participant / Session 単位で強制切断する。
対象範囲と反映期限を定め、古い検証鍵の保持だけで受け入れを継続しない。
既存通信を停止するかは、失効対象と現在の権限に従って判断する。
正規利用者が復帰する場合は、既存の認証・認可要件に従って認証と現在の権限を確認し、漏洩した鍵に依存しない新しい資格情報を発行する。
拒否した資格情報の所持だけで再発行を許可せず、旧資格情報や遅延した更新結果を再び有効にしない。

鍵や検証情報を取得できない場合は、確認済み情報を利用できる期限と用途ごとの停止条件に従う。
検証できない新しい資格情報を受け入れない。
再接続・再試行・再起動だけで、鍵の受け入れ期間や権限情報の期限を延長しない。
状態を復元する場合も、受け入れ停止済みの鍵を古い記録から再び有効にしない。

参照型トークンを採用する場合は、参照値に必要な推測耐性を確保し、照会先の認証と通信保護を行う。
照会結果にも、利用先・用途・対象・期限・失効の検証と、有効期限を守った保持を適用する。
トークンの形式が参照型であることだけで、現在の権限や即時の失効反映を保証したとは扱わない。

TURN・ICE・DTLS・E2EE の鍵・秘密情報は、各仕様の生成・配布・更新・削除条件に従う。
参加 JWT の署名鍵を更新しただけで、これらの鍵やプロトコル状態を更新したとは扱わない。

ApplicationSigningKey の秘密値、トークン本体を、ログ・監査・診断・エラー報告に出力しない。
不要になった鍵と関連状態は、定めた保持条件に従って削除する。
鍵の保管には Cloud KMS、Signaling への配布にはサービス間認証を行った Management 内部鍵配布 API、キャッシュ無効化には Pub/Sub コマンドバスを使用する。ローテーション期間、キャッシュ保持期間、漏洩時の具体的な手順は、運用条件を確認して定める。

## 方式選定

ルーム参加用のアクセストークンには、参加 JWT を使用し、独自のトークン形式は作らない。
JWT の発行・解析・署名検証には、既存ライブラリを利用する。
TURN・ICE・DTLS・内部サービスなど、ほかの用途の資格情報まで JWT に統一することは要求しない。

| 選定する項目 | 比較する候補・条件 |
|---|---|
| 参加 JWT の署名方式 | HS256 を採用する。許可する `alg` は `HS256` に固定し、JWT 内の指定だけで検証設定を変更しない |
| 検証方法 | JWT の署名・claim 検証、有効鍵キャッシュ、失効済み鍵の反映、Room・Session・失効状態の確認 |
| 更新方法 | 顧客アプリサーバーによる再発行。Browser SDK に更新用の長期資格情報を持たせない |
| 鍵管理 | Cloud KMS による暗号化保存、Management 内部鍵配布 API、Pub/Sub によるキャッシュ無効化、ローテーションと失効 |

JWT の検証時に必要な情報と、発行後の権限変更・失効を確認する方法を合わせて評価する。
ほかの用途で参照型トークンを検討する場合は、照会先への依存、遅延、可用性、情報の保持期間と失効の反映期限を評価する。
トークン形式を選ぶ際も、オンライン照会の要否と失効を保証する方法は別に決める。

参加 JWT は、署名検証だけで操作を許可しない。
許可アルゴリズム、発行元、利用先、用途、対象、権限、有効期限、鍵の選択と検証規則を定め、現在の利用権限と失効状態も確認する。
同じ発行元の異なる用途の JWT を、相互に受け入れない規則を設ける。[RFC 8725 §3](https://www.rfc-editor.org/rfc/rfc8725.html#section-3)

参加 JWT には HS256 を採用する。HS256 の選定理由は、顧客アプリサーバーと Signaling だけで使う鍵を配布すればよい PaaS 契約、複数鍵を `kid` で選べるローテーション、JWT ライブラリの相互接続性にある。

Management UI の IDaaS 認証で OpenID Connect を利用する場合も、その ID token を参加 JWT として扱わない。参加 JWT は常に顧客アプリサーバーが ApplicationSigningKey で署名する。

Signaling の認証方式は、ブラウザーの WebSocket API で任意の認証ヘッダーを設定できない条件を満たす必要がある。
資格情報を URL・ログへ露出させず、認証前の接続・処理を制限し、認証した利用者と接続を対応付けられることを確認する。
HTTP Cookie などを利用する場合は、既存の第三者サイトからの不正な接続・操作への対策も維持する。

## 自作範囲・既存実装の利用

Management UI の OpenID Connect 連携、Signaling の参加 JWT 検証、Management の鍵・資格情報管理は TypeScript で実装する。
各プロトコルでの認証と権限の適用は、それぞれのコンポーネントが担う。
論理的な責務の分離と、実行プロセスの分離は同一視しない。

| 実装する部分 | 責務 |
|---|---|
| 参加 JWT の検証と鍵管理連携 | `kid` による鍵選択、HS256 検証、失効済み鍵の反映、Signaling への鍵配布 |
| 資格情報の検証への組み込み | 用途別の検証設定、対象との対応、現在の権限・失効状態の確認 |
| プロトコルとの連携 | TURN 資格情報の発行、接続・用途との対応、各コンポーネントへの権限伝達 |
| 鍵管理との連携 | 発行・検証に使う鍵の選択、更新、受け入れ停止、漏洩時の復旧 |
| 監査と資源管理 | 必要な操作記録、処理量・保持状態の制限、結果不明からの照合 |

Management は ApplicationSigningKey と Management API credential を管理し、Signaling は参加 JWT の検証と Room・Session 状態を管理する。
実際に資格情報を受け入れるコンポーネントは、その用途に必要な検証と認可を適用する。
すべてのコンポーネントが参加 JWT を直接検証することは要求しない。
D-Plane などは、既存仕様に従って Signaling から受け取った検証済みの権限情報を利用できる。
その場合も、指示元・対象・操作・有効期限・反映済みの失効との対応を確認する。
共通の検証処理は再利用し、各コンポーネントへ不必要に重複実装しない。

JWT の生成・解析・署名検証、暗号処理、安全な乱数生成には既存ライブラリを利用する。
JWT や暗号アルゴリズムを独自実装しない。
ライブラリが保証する検証と、アプリケーション側で指定・確認する発行元、利用先、用途、対象、期限、権限、失効を区別する。
解析や署名検証の成功だけで、操作を許可しない。

鍵の保管、永続化、サービス認証、メッセージ配送、時刻管理、入力検証には、既存のライブラリや基盤を利用できる。
既存基盤が提供する順序・永続性・期限・障害回復の保証と、プラットフォーム側で補う条件を確認する。
同じ要件を満たす場合は、独自実装や追加コンポーネントを必要以上に増やさない。

TURN・ICE・DTLS の認証処理は、各コンポーネントの仕様に従う。
Signaling に同じプロトコル処理を重複実装せず、利用許可・資格情報・処理結果を対応付ける。
Browser SDK・React SDK に、サーバー側の発行権限や秘密情報を持たせない。

既存実装の内部バッファ、キャッシュ、再試行、鍵取得、照会待ちも資源管理に含める。
ライブラリ自身の制限または組み込み側の制御により、必要な上限と期限を保証する。
失敗時に認証・認可を省略したり、期限切れの情報を使い続けたりする構成を採用しない。

採用する実装・基盤のバージョン、設定、依存機能、検証範囲を記録する。
セキュリティ修正を追跡し、更新時は影響する検証条件を再確認する。
実装と検証は、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)に従う。

## セキュリティ

認証、権限付与、資格情報の発行・更新・失効、管理操作、状態取得、通知購読に、それぞれ必要な認証・認可を適用する。
認証済みの利用者・アプリケーション・内部サービスでも、対象資源と操作範囲を確認する。
資格情報の発行や権限変更によって、要求元の委任範囲を超える権限を与えない。

参加 JWT は、許可した HS256 と `kid` が指す有効鍵だけで署名を検証する。
署名のない JWT、許可していないアルゴリズム、不正な署名を受け入れない。
発行元・利用先・用途・対象・権限・有効期限と、現在の利用権限・失効状態を確認する。
使用開始時刻が指定されている場合は、その条件も検証する。
JWT 内のアルゴリズムや鍵の指定だけで、検証側の設定を変更しない。

外部認証の情報、参加 JWT、更新用資格情報、管理用・内部サービス用の資格情報を、別用途として無条件に受け入れない。
資格情報の検証に失敗した場合、別用途として試し直したり、弱い検証条件へ切り替えたりしない。
TURN・ICE・DTLS には、各仕様の認証・検証条件を適用する。

外部入力は、形式・サイズ・値・対象・更新順序を実行時に検証する。
署名済みの情報でも、その発行元が対象の利用者・ルーム・操作を扱えることを確認する。
表示名、メールアドレス、参加者 ID、参加端末 ID の一致だけで、利用者や接続の引き継ぎを許可しない。

鍵取得や外部照会の接続先は、信頼する設定から選ぶ。
資格情報に含まれる URL や識別子を、そのまま任意の外部接続や鍵の取得に利用しない。
外部照会結果にも、対象、用途、期限、失効の条件を適用する。

資格情報の受け渡しと内部通信は、既存の通信保護要件に従う。
ブラウザーの WebSocket API の制約を理由に、資格情報を URL へ含めない。
ブラウザーが自動送信する資格情報を利用する場合は、第三者サイトからの不正な接続・操作を防ぐ。
Origin の確認だけで、利用者認証や操作権限の確認を済ませない。

更新・再発行・再接続では、要求元と対象の現在の権限を確認する。
盗用・失効した資格情報の所持だけで、新しい資格情報や別の参加端末の操作権限を取得させない。
再送や応答の消失を利用して、有効期間や権限を意図せず拡大させない。

鍵の漏洩時は、対象鍵の受け入れ停止、資格情報の失効、利用権限の変更を区別する。
必要な処理と正規利用者の復帰は、「署名・検証と鍵の管理」に従う。
復旧のために、漏洩した鍵や拒否済みの資格情報を再び信頼しない。

未認証要求、認証試行、資格情報の発行・更新、鍵取得、権限照会、失効通知、結果照合に、処理量・保持状態・待機時間の上限を設ける。
認証済みの要求にも適用し、再試行・重複要求や複数処理の並行実行で上限を回避させない。
過負荷時にも認証・認可を省略せず、失効期限を守るための処理を無制限の待機キューへ蓄積しない。

トークン本体、秘密鍵、共通秘密情報、更新用の秘密情報を、URL・ログ・監査・診断・エラー報告へ出力しない。
Browser SDK・React SDK にサーバー側の秘密情報を渡さず、Signaling・D-Plane に E2EE の秘密鍵・復号鍵を渡さない。
監査には、要求元、対象、操作、判断結果と、発行・適用・停止の対応を確認するために必要な情報だけを記録する。
監査・状態照会にはアクセス制御と保持期限を適用する。

## 受け入れ条件

外部認証との連携処理、Management、Browser SDK、Signaling、D-Plane を組み合わせて検証する。
通常動作に加え、不正要求、権限変更、通知の欠落・重複・順序逆転、通信分断、時計のずれ、再起動、SFU 移行を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 参加 JWT の署名 | HS256 と `kid` が指す有効鍵だけで検証する。署名なし、不正署名、他のアルゴリズム、失効済み・不明な鍵を拒否する |
| JWT の情報と期間 | 発行元・利用先・用途・対象・権限・有効期限を検証する。使用開始時刻がある場合はその条件も確認し、現在の利用権限・失効状態を適用する |
| JWT の `grants` | 既定の grant 以外と未サポートの grant を拒否する。grant の型・対象・権限の組み合わせが許可範囲を超えない |
| 資格情報の用途分離 | 外部認証・参加・更新・管理・内部サービス・TURN・ICE の情報を別用途として無条件に受け入れない |
| 更新・再発行 | 現在の権限を確認し、権限や期限を意図せず拡大しない。再試行や応答消失で重複処理や失効の取り消しを起こさない |
| トークンの期限切れ・単体失効 | 新しい認証を拒否する。既存接続の継続は、失効対象と現在の利用権限に従って判断する |
| 通常の鍵更新 | 新旧鍵の切り替えと受け入れ期間を守る。更新や再取得だけで資格情報の期限を延長しない |
| 鍵漏洩と復旧 | 対象鍵の発行・受け入れを停止し、影響する資格情報を無効化する。利用権限の変更は別に判断し、正規利用者は再認証・認可後に新しい資格情報で復帰できる |
| プロトコルとの連携 | STUN の認証不要範囲、TURN の認証・所有者確認・期限切れ方針、ICE 世代、DTLS 相手検証を維持する |
| 外部照会・鍵取得 | 信頼する接続先だけを利用する。入力中の URL・鍵指定で任意の取得先や検証条件へ切り替えない |
| ブラウザーでの認証 | 採用した方式が WebSocket API の制約を満たす。資格情報を URL に含めず、未認証処理を制限し、必要な第三者サイト対策を適用する |
| 資源上限・過負荷 | 未認証・認証済みの要求、並行処理、再試行でも上限を超えない。過負荷を理由に検証や失効期限を緩めない |
| 秘密情報と監査 | 資格情報・鍵・共通秘密情報をログ等へ露出させない。監査で要求・判断・適用・停止の対応を確認でき、アクセス制御と保持期限を守る |

Fuzzing では、JWT ライブラリへの入力と検証設定、アルゴリズム・鍵の選択、発行元・利用先・用途・対象・期限の確認、検証結果に基づく認可処理を対象にする。
外部入力・照会応答の解析、長さ・境界、不正な用途・対象・時刻も検証する。

JWT の解析・署名検証には既存ライブラリを使用し、その内部実装を独自に検証し直すことを一律には要求しない。
ライブラリへの入力、検証設定、アルゴリズム・鍵の選択、発行元・利用先・用途・対象・期限の確認、検証結果に基づく認可処理は、プラットフォームの検証対象とする。
既存ライブラリの検証に成功したことだけで、プラットフォーム全体の認証・認可が正しいとは判断しない。

採用した JWT ライブラリ・署名方式・鍵管理構成と、実際のブラウザー・内部サービスの構成で検証する。
参加 JWT 用として OAuth 2.0・OpenID Connect・更新用トークンを採用していない。Management UI の OpenID Connect は別用途として、Management 仕様の条件で検証する。
結果には、バージョン、設定、権限・委任条件、期限、時計・障害条件、負荷、検証範囲と観測結果を記録する。
秘密情報を記録へ含めない。

検証方法・認証全体の性能試験と結果の記録には、[認可仕様の共通検証条件](authorization.md#共通の検証方法と結果の記録)も適用する。
