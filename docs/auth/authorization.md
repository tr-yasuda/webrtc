# 外部認証との連携・認可・権限の失効

共通の前提・用語・利用場面は [共通仕様](../platform/overview.md)に従う。
各プロトコルの認証・状態管理は、それぞれのコンポーネント仕様に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](../e2ee/key-management.md)に従う。

## 前提

- 認証、操作の許可判断、資格情報の検証は、それぞれ担当する処理を分ける。別々のサーバープロセスで実行することは必須としない。
- Management UI のログインには IDaaS の OpenID Connect を利用する。パスワード認証、パスワード管理、アカウント登録をプラットフォーム内で自前実装しない。
- 顧客アプリケーションの利用者認証は、顧客アプリケーションとその認証基盤が行う。プラットフォームは通話利用者の認証を代行しない。
- 参加 JWT は顧客アプリサーバーが ApplicationSigningKey で署名し、Signaling が検証する。プラットフォームは参加 JWT の発行窓口にならない。
- Signaling は参加 JWT が許す対象・操作と、Room・Session・失効状態という現在のプラットフォーム状態の両方を確認する。参加者が Client SDK の操作で自分の権限を増やせることはない。
- ProjectUser の管理権限は、[Management の ProjectUser ロール](../platform/management.md#projectuser-の権限ロール)に従う。参加 JWT の `grants` と ProjectUser ロールを混用しない。
- 各コンポーネントは、資格情報が有効かどうかと、現在その操作を許可できるかを別々に確認する。認証や署名検証に成功したことだけで、操作・通信を無期限に許可しない。毎回 Signaling・Management へ問い合わせることは必須とせず、有効期限内の権限情報を利用できる。ただし、権限変更・失効を定められた期限内に反映し、期限内に必要な権限を確認できない場合は、既存仕様に従って対象の処理・通信を停止する。
- 用途ごとに、受け入れる資格情報の発行元、利用先、利用者・サービス、対象資源、操作、期限、検証条件を定める。別の用途で発行された資格情報を、無条件に受け入れない。
- トークンの有効期限、利用権限の有効期限、権限を再確認する期限、失効を反映する期限、各プロトコル状態の寿命を分けて管理する。一つを更新しただけで、ほかの期限を延長しない。
- Browser SDK に、サーバー側の署名鍵や TURN 資格情報の生成・検証に使う共通秘密情報を渡さない。E2EE の秘密鍵・復号鍵を Signaling・D-Plane に渡さない。
- 既存の認可、通信停止、資源管理、E2EE、各プロトコルの認証要件は変更しない。TURN 資格情報の通常の期限切れと明示的な失効は、既存の TURN 仕様に従って扱う。
- 参加 JWT は HS256 署名付き JWT とする。形式、claim、ApplicationSigningKey の管理は [資格情報仕様](credentials.md)に従う。TURN・ICE・DTLS・内部サービスの資格情報まで JWT に統一しない。

## 用語

参加者、参加端末、ルーム、発行、購読、C-Plane、D-Plane は、共通仕様の定義に従う。

| 用語 | 意味 |
|---|---|
| 外部アプリケーション | プラットフォームを利用し、許可された範囲で利用者の参加や操作を要求するアプリケーション |
| 外部認証基盤 | 外部アプリケーションのログインと利用者管理を行う既存の仕組み |
| ExternalUser | 顧客アプリケーションが参加 JWT の `sub` で指定する通話利用者。PaaS の Account や ProjectUser とは別物 |
| ApplicationSigningKey | 顧客アプリサーバーが参加 JWT に HS256 署名を行うための鍵 |
| 主体 | 認証や権限確認の対象となる利用者、アプリケーション、内部サービス |
| 認証 | 要求元が誰かを確認すること |
| 認可 | 現在の権限と対象の状態に基づき、要求された操作を許可するか判断すること |
| 委任範囲 | 顧客アプリサーバーが ExternalUser に参加 JWT の `grants` として与えられる範囲。プラットフォームは顧客アプリ内の利用者権限管理を代行しない |
| 権限情報 | 誰が、どの資源に、どの操作を行えるかと、その有効期限などを示す情報 |
| 資格情報 | 認証や利用許可の確認に使うトークン、TURN のユーザー名・パスワードなどの情報 |
| アクセストークン | 対象サービスに提示し、参加や操作の許可を受けるために使う資格情報 |
| 参加 JWT | Browser SDK がルームへの参加や許可された操作に使う、署名付き JWT 形式のアクセストークン |
| 発行元 | トークンや資格情報を発行する主体 |
| 利用先 | そのトークンや資格情報を受け入れるサービス・機能 |
| 失効 | 期限前であっても、対象の資格情報や権限を無効にする決定。各コンポーネントがその決定を反映し、操作を拒否したり通信を停止したりする処理とは区別する。決定と反映は必ずしも同時に完了しない |
| トークンの有効期限 | そのトークンを有効な資格情報として受け入れられる期限 |
| 利用権限の有効期限 | 対象の操作や通信を許可する期間の終わり |
| 権限の再確認期限 | 保持している権限情報だけで判断を続けられる期限。期限内に必要な確認ができなければ、対象の処理・通信を停止する |
| 失効の反映期限 | 失効を各コンポーネントの拒否・通信停止に反映する期限。起点と完了条件は後続の節で定める |
| プロトコル状態の寿命 | TURN Allocation、Permission、Channel Binding など、各プロトコルが保持する状態の存続期間 |

## 利用場面

利用者 A が、顧客アプリケーションから会議ルームへ参加し、通話中に管理操作が行われる場面を扱う。

1. A は、顧客アプリケーションが利用する認証基盤でログインする。プラットフォームはこのログインを代行しない。

2. 顧客アプリサーバーは、Management で払い出した ApplicationSigningKey を使って、A のルーム参加と操作権限を参加 JWT に記載して署名する。

3. Browser SDK は、取得した参加 JWT を Signaling に提示する。Signaling は署名、発行元、対象、権限、有効期限と現在の Room・Session・失効状態を確認し、A の参加端末を登録する。登録だけでは、メディアやデータの送受信を開始しない。

4. Browser SDK と SFU が接続を準備する。TURN が必要なら、Signaling は利用権限を確認して TURN 資格情報を発行する。参加 JWT、TURN 資格情報、ICE 資格情報は、それぞれの用途で使用する。Browser SDK にサーバー側の署名鍵や TURN の共通秘密情報は渡さない。

5. 必要な WebRTC Transport と E2EE の準備が整い、発行・購読の権限を確認できた通信から開始する。各コンポーネントは、有効期限内の権限情報を利用でき、毎回 Signaling へ問い合わせる必要はない。

6. 参加 JWT の再発行が必要になった場合は、顧客アプリサーバーが利用者の現在の状態を確認してから再度署名する。トークンを更新しただけで、既存 Session、TURN Allocation、WebRTC 接続の寿命をまとめて延長しない。

7. 通話中に、権限を持つ ProjectUser が A の参加端末を強制切断する。Management の受付と、Signaling・SFU による通信停止は、必ずしも同時ではない。強制切断コマンドの結果が確認できるまで完了とは扱わない。ほかの参加端末の通信は継続する。

8. 失効通知が届かない場合も、必要な権限を期限内に再確認できなければ、対象の処理・通信を停止する。再接続や通知の再送だけで期限を延長しない。

9. A が退出すると、その参加端末の通信を終了し、関連する資源を解放する。遅延した更新結果や通知によって、終了した通信を再開しない。

## 外部認証基盤との連携

Management UI のログインと顧客アプリケーションの利用者認証は、別々の信頼境界で扱う。プラットフォームはどちらのパスワード認証も自前実装しない。

| 対象 | 認証方式 | プラットフォームの責務 |
|---|---|---|
| Management UI | IDaaS の OpenID Connect | Account の認証結果を受け入れ、ProjectUser ロールで管理 API を認可する |
| 顧客アプリケーション | 顧客が選んだ認証基盤 | 顧客アプリサーバーが ExternalUser を確認し、ApplicationSigningKey で参加 JWT に署名する |

IDaaS との連携では、発行者、クライアント、スコープ、ID token の署名検証、有効期限、ログアウト・権限変更の反映条件を設定する。Management は IDaaS の認証成功だけでは ProjectUser 操作を許可せず、認証した Account が対象 Project のどのロールを持つかを確認する。

顧客アプリケーションの認証結果は、プラットフォームが直接検証しない。プラットフォームは、顧客アプリサーバーが署名した参加 JWT の `sub` を ExternalUser 識別子として扱う。表示名やメールアドレスだけが一致する場合、別の ExternalUser や既存参加者へ自動的に結び付けない。

顧客アプリケーションのロールやグループを参加 JWT の `grants` に使うかどうかは顧客が決める。どのような外部ロール名であっても、Management UI の ProjectUser ロールや TURN・ICE のプロトコル権限を自動的に付与しない。

外部認証の資格情報を、参加 JWT や TURN 資格情報として無条件に受け入れない。IDaaS・顧客認証基盤の秘密情報や、顧客アプリサーバーの資格情報を Browser SDK に渡さない。

### 外部側の変更・障害を受けた判断

顧客アプリケーションでログアウトや利用停止が起きても、プラットフォームがその変更を自動検知するとは限らない。既存接続を停止する必要がある場合は、顧客サーバーが Management API で Participant / Session 単位の強制切断を行う。ApplicationSigningKey を失効しても、それは新しい参加 JWT の拒否であり、既存接続の停止とは別操作とする。

Management の強制切断コマンドは、[Management と Signaling の通信](../platform/management.md#management-と-signaling-の通信)に従って結果を確認する。ApplicationSigningKey の失効は、Signaling の鍵キャッシュ無効化後に新しい参加 JWT 検証へ反映する。

連携先へ一時的に接続できない場合も、必要な確認を省略して新規認証や権限拡大を許可しない。
既存通信の継続は、有効な権限情報と既存仕様の再確認・停止条件に従う。
問い合わせの失敗や再試行だけで、情報の有効期限を延長しない。

外部から取得・保持する利用者情報は、識別と権限判断に必要な範囲に限定する。
認証情報や不要な個人情報を、ログ・通知へ出力しない。

## 認可の対象と判断

Signaling は、参加 JWT の `grants` が許す対象・操作と、Room・Session・失効状態という現在のプラットフォーム状態の両方を確認する。Management は、IDaaS で認証した Account の ProjectUser ロールに基づいて管理操作を認可する。
各コンポーネントは、確認済みの権限情報と現在の対象状態に基づいて操作・通信を許可する。
署名検証やログインに成功したこと、対象の識別情報を知っていることだけでは許可しない。

権限は、次の対象と操作を区別して管理する。

| 対象 | 区別する操作・範囲 |
|---|---|
| ルーム | 作成・削除・設定変更・状態取得・参加 |
| 参加者・参加端末 | 自分の参加端末の退出、別の参加端末の操作・除外、接続の引き継ぎ |
| 発行 | 音声・カメラ映像・画面共有の開始・変更・停止、操作できる発行元の参加端末 |
| 購読 | 購読の追加・変更・解除、受信できる発行 |
| DataChannel | 論理チャネルの作成・利用、送信・受信、許可された宛先 |
| 状態・通知 | 取得できる情報と、変更通知を受け取れる範囲 |
| TURN | 利用できる用途・接続・中継先 |
| 管理操作 | 操作できるルーム・参加端末・設定と、実行できる管理機能 |
| 内部サービス | 指示できるコンポーネント・接続・操作 |

ルームへの参加権限と、発行・購読・データ通信・管理操作の権限を分ける。
一つの操作が許可されていても、ほかの操作を自動的に許可しない。
参加 JWT の権限は `room.create`・`room.join`・`media.publish`・`media.subscribe`・`data.send` とし、管理権限は [Management の ProjectUser ロール](../platform/management.md#projectuser-の権限ロール)に従う。

参加者と参加端末を区別する。
自分の参加端末の操作権限だけで、同じ参加者の別の参加端末を操作・終了させない。
発行・購読・論理チャネルは、所有する参加端末、所属ルーム、現在の接続との対応を確認する。
別の参加端末の操作や接続の引き継ぎには、その対象を扱う権限を必要とする。

外部アプリケーションの委任範囲には、対象資源、対象利用者、許可する操作、付与できる権限、有効期間の制約を定める。
権限付与や資格情報の発行要求を受けた場合は、要求元がその対象と操作を扱えることを確認する。
要求された権限が委任範囲を超える場合は、超過した権限を付与・発行しない。
認証済みの外部アプリケーションでも、自身の委任範囲を変更できるとは扱わない。

トークンに権限が記載されていても、現在の権限を広げる根拠にはしない。
操作は、資格情報が許す用途・対象・操作と、現在の権限の両方を満たす場合に限って許可する。
資格情報の更新・再発行だけで、失効した権限を復活させない。

DataChannel の送信権限と受信権限を区別する。
送信者が指定した宛先は、送信を許可された範囲に含まれることを確認する。
ルームへの参加だけで、すべてのメッセージの受信・復号を許可しない。
受信権限と E2EE の鍵配布範囲は、E2EE 仕様に従って一致させる。

状態取得や通知購読にも、対象と情報ごとの権限を適用する。
変更操作を拒否するだけでなく、未許可のルームや参加端末の状態・接続情報・鍵管理メッセージを取得させない。
管理権限があることだけで、E2EE 本文や復号鍵を取得できるとは扱わない。

各コンポーネントは、検証済みで有効期限内の権限情報を利用できる。
毎回 Signaling へ問い合わせることは要求しない。
権限情報がどの利用者・サービス、資源、操作に対するものか確認し、異なる対象や古い接続の情報を流用しない。
権限変更・失効の反映期限と、確認不能時の停止条件は、後続の「有効期限・権限変更・失効の反映」で定める。

操作の受け付け後に、退出、権限失効、接続の引き継ぎ、SFU 移行が起きる場合も考慮する。
実行時には、その操作が現在も許可され、対象が同じであることを確認する。
この確認には、有効期限内の権限情報を利用でき、毎回 Signaling へ問い合わせる必要はない。
権限失効や接続の引き継ぎと操作が競合した場合は、既存仕様で定めた確定順序に従って許可・拒否を判断する。
古い権限情報が有効期限内でも、対象コンポーネントに反映済みの失効を無視して操作を許可しない。
通信停止と送信開始が競合する場合の判定は、SFU・SCTP / DataChannel 仕様に従う。
古い操作や通知によって、新しい接続・権限状態を変更しない。

権限があっても、資源上限、WebRTC Transport の送信同意・相手認証、E2EE の鍵条件を省略しない。
認可、プロトコル上の接続条件、暗号条件、資源の利用可能性を、それぞれ確認する。

## 有効期限・権限変更・失効の反映

有効期限と反映期限は、用途と対象ごとに管理する。

| 対象 | 期限に達した場合の扱い |
|---|---|
| トークン | そのトークンによる新しい認証を拒否する。既存接続への影響は、失効対象と現在の利用権限から判断する |
| 利用権限 | 対象の操作・通信を許可しない |
| 保持している権限情報 | 必要な再確認ができなければ、対象の処理・通信を停止する |
| 失効の反映 | 対象コンポーネントで拒否・通信停止を完了する |
| プロトコル状態 | TURN・ICE・DTLS など、各仕様の期限・更新・終了条件を適用する |

一つの情報を更新しても、ほかの期限を自動的に延長しない。
TURN 資格情報の通常の期限切れと既存 Allocation の継続条件は、TURN 仕様を維持する。

### 失効の決定から拒否・停止の確認まで

Signaling は、権限変更・失効の対象と適用する変更、および決定した時点を識別できるようにする。外部認証基盤での変更を受けて失効を決定する条件は [外部認証基盤との連携](#外部認証基盤との連携)で定め、反映期限は Signaling が失効を決定した時点から数える。

各コンポーネントは、失効対象に応じて期限内に拒否・停止を適用する。トークン単体が失効した場合は、そのトークンによる新しい認証を拒否する。参加端末や利用者の通信権限が失効した場合は、対象の新しい操作を拒否し、既存通信も停止する。失効対象外の通信は、必要な権限・接続・暗号条件を満たす限り継続できる。

対象コンポーネントで権限変更を適用し、必要な拒否・停止が行われたことを確認して、反映を完了とする。失効通知の送受信後も、反映結果が不明なら照合と必要な停止処理を行う。停止後の資源は、解放が確認されるまで [共通の資源管理](../platform/resources.md#資源管理)に従って計上する。

### 通知や再確認ができない場合

失効通知が届かない場合や Signaling と D-Plane 間の通信が途切れた場合も、保持する権限情報の有効期限と再確認により、失効の反映期限内に対象通信を停止する。確認済みの情報を使用できる期間には有限の上限を設け、その間は用途ごとの停止条件に従って既存通信を継続できる。操作ごとの Signaling への問い合わせは必須としない。

必要な確認ができないまま期限に達した場合は、対象の処理・通信を停止する。再接続、要求の再送、同じ通知の再受信だけでは期限を延長しない。

権限情報の期限を延長するには、その対象について使用可能な権限が継続していることを確認する。
古い情報が遅れて到着した時刻を起点に、有効期間を新しく数え直さない。
時計のずれ、処理の中断、再起動によって、期限を超えた情報を利用しない。
期限を安全に判断できない場合は、その情報による新しい許可や期限延長を行わない。

### 並行処理と復旧時の判断

権限変更の順序は、通知の到着順だけで判断しない。
対象の利用者・参加端末・資源と、変更前後の関係を確認する。
適用済みの失効や新しい接続・割り当てを、古い権限情報、更新結果、再試行で取り消さない。
失効後に権限を再付与する場合は、新しい正当な変更として確認する。

権限変更・失効と、資格情報の発行・更新・操作実行・送信開始が競合する場合は、既存仕様の確定順序に従う。
送信待ち・再送待ちのデータにも停止条件を適用する。
既に実際の送信処理へ引き渡したデータの到着や、受信済みの平文を取り消せるとは保証しない。

再起動・SFU 移行・担当変更後も、必要な失効情報と現在の権限を確認する。
状態を復元できない場合は、確認できていない処理・通信を再開しない。
失効記録の削除によって、古い資格情報や権限情報を再び有効として受け入れない。
記録の保持期間と回収条件は、古い情報が受け入れられる期間と合わせて定める。

反映期限、再確認間隔、権限情報の有効期間、記録の保持期間は、設定と試験で確認できるようにする。
値はこの段階では固定しない。
同期・通知・再確認・照合の方式も、後続の方式選定で決定する。
通知の欠落、分断、並行更新、再起動を含む条件で、期限内の拒否・停止と古い状態への復帰防止を検証する。

## 方式選定

認証連携、トークン形式、検証、更新、失効情報の伝達、サービス認証を分けて選定する。
一つの方式を採用したことだけで、ほかの方式まで決定したとは扱わない。
方式は用途ごとに選べる。

| 選定する項目 | 比較する候補・条件 |
|---|---|
| 外部認証との連携 | 外部アプリケーション経由の連携、認証基盤との直接連携、OAuth 2.0・OpenID Connect の利用範囲 |
| 失効情報の伝達 | 通知、定期的な再確認、その併用 |
| 権限情報の保持 | 保持する範囲、有効期間、再確認、再起動・移行時の復元条件 |

JWT はトークン形式、OAuth 2.0 は認可の仕組み、OpenID Connect は外部認証との連携に関わる選択として扱う。
これらを同じ目的の代替候補として比較しない。

外部認証との連携方式は、既存基盤の対応機能、外部アプリケーションの認証方法、委任範囲、利用者との対応、停止・失効情報を取得できる条件で評価する。
連携方式を採用しても、外部認証の成功だけでプラットフォームの操作権限を与えない。

ローカル検証では、署名などの検証と、現在の権限・失効の確認を区別する。
オンライン照会でも、結果を保持して利用する場合は、その間の権限変更を確認できない期間を評価する。
照会結果を保持して減らせる負荷と、古い情報を使う期間を、失効の反映期限と合わせて評価する。[RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)

失効の伝達方式は、通知が一切届かない場合も含めて評価する。
通信分断、時計のずれ、処理中断、再起動、SFU 移行でも、設定した反映期限内に対象の拒否・停止を完了できることを確認する。
保証に必要な時計誤差や処理遅延などの前提を明示し、その前提を確認できない場合の停止条件も定める。
通常どおり通知が届く場合の測定だけでは、期限の保証を確認済みとしない。

各候補は、セキュリティ要件、遅延・処理量、依存先の障害、運用負荷、鍵更新、相互接続性、検証・保守のしやすさで比較する。
実装・運用の複雑さとして、独自に実装する範囲、追加コンポーネントと依存関係、同期・復旧・鍵更新の手順、検証・監視の負担も比較する。
同じセキュリティ要件と機能要件を満たす場合は、独自実装や追加コンポーネントを必要以上に増やさず、理解・検証・保守しやすい方式を優先する。
必要な機能を削除したり、認証・認可の条件や失効の反映期限を緩めたりすることで候補を適合させない。

選定結果には、採用範囲、設定、依存する基盤、成立に必要な条件、確認結果、残る制約を記録する。
方式の選定、数学モデルの検証、実装、統合試験は、それぞれ完了した範囲を記録する。
未採用・未実装・未検証の範囲を、対応済みとして扱わない。
Management UI の OpenID Connect と参加 JWT の HS256 は確定とする。IDaaS の発行者・スコープ、ApplicationSigningKey の保持期間、権限再確認間隔、強制切断の反映期限、内部サービス認証の設定は、運用条件を確認して定める。

## 自作範囲・既存実装の利用

Management UI の OpenID Connect 連携、Signaling の参加 JWT 検証、Management の権限・鍵管理は TypeScript で実装する。
各プロトコルでの認証と権限の適用は、それぞれのコンポーネントが担う。
論理的な責務の分離と、実行プロセスの分離は同一視しない。

| 実装する部分 | 責務 |
|---|---|
| 外部認証との連携 | 顧客アプリケーションでの認証の信頼境界、ExternalUser 識別子の扱い |
| 認可 | Signaling による JWT・Room・Session 状態の確認と、Management による ProjectUser ロール確認 |
| 権限変更・失効の反映 | 更新順序、通知・再確認、期限管理、適用・停止結果の照合 |
| 監査と資源管理 | 必要な操作記録、処理量・保持状態の制限、結果不明からの照合 |

外部アプリケーションのログイン、パスワード管理、利用者登録・管理は、既存の認証基盤を利用する。
外部認証基盤の機能を、プラットフォーム内へ重複実装しない。
外部基盤が認証を行っても、プラットフォーム固有の権限と委任範囲の確認は省略しない。

Management UI の OpenID Connect では、標準のプロトコル処理に既存実装を利用する。
採用した実装の設定と、Account・ProjectUser・管理権限との対応は、プラットフォーム側で確認する。

鍵の保管、永続化、サービス認証、メッセージ配送、時刻管理、入力検証には、既存のライブラリや基盤を利用できる。
既存基盤が提供する順序・永続性・期限・障害回復の保証と、プラットフォーム側で補う条件を確認する。
同じ要件を満たす場合は、独自実装や追加コンポーネントを必要以上に増やさない。

既存実装の内部バッファ、キャッシュ、再試行、鍵取得、照会待ちも資源管理に含める。
ライブラリ自身の制限または組み込み側の制御により、必要な上限と期限を保証する。
失敗時に認証・認可を省略したり、期限切れの情報を使い続けたりする構成を採用しない。

採用する実装・基盤のバージョン、設定、依存機能、検証範囲を記録する。
セキュリティ修正を追跡し、更新時は影響する検証条件を再確認する。
実装と検証は、[実装・検証の共通方針](../platform/verification.md#実装検証の共通方針)に従う。

## セキュリティ

認証、権限付与、資格情報の発行・更新・失効、管理操作、状態取得、通知購読に、それぞれ必要な認証・認可を適用する。
認証済みの利用者・アプリケーション・内部サービスでも、対象資源と操作範囲を確認する。
資格情報の発行や権限変更によって、要求元の委任範囲を超える権限を与えない。

外部入力は、形式・サイズ・値・対象・更新順序を実行時に検証する。
署名済みの情報でも、その発行元が対象の利用者・ルーム・操作を扱えることを確認する。
表示名、メールアドレス、参加者 ID、参加端末 ID の一致だけで、利用者や接続の引き継ぎを許可しない。

失効、鍵の受け入れ停止、接続の引き継ぎが反映済みの場合は、古い資格情報や権限情報で覆さない。
通知の欠落・通信分断・時計のずれ・再起動時の扱いは、「有効期限・権限変更・失効の反映」に従う。
確認不能だけを理由に既存通信を一律に即時停止することは要求しないが、確認済み情報を利用できる期限を超えて継続しない。

未認証要求、認証試行、資格情報の発行・更新、鍵取得、権限照会、失効通知、結果照合に、処理量・保持状態・待機時間の上限を設ける。
認証済みの要求にも適用し、再試行・重複要求や複数処理の並行実行で上限を回避させない。
過負荷時にも認証・認可を省略せず、失効期限を守るための処理を無制限の待機キューへ蓄積しない。

## 受け入れ条件

外部認証との連携処理、Management、Browser SDK、Signaling、D-Plane を組み合わせて検証する。
通常動作に加え、不正要求、権限変更、通知の欠落・重複・順序逆転、通信分断、時計のずれ、再起動、SFU 移行を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 外部認証の受け入れ | 設定した連携先と検証条件に従う。認証成功だけで参加・操作を許可しない |
| 利用者の対応 | 異なる認証基盤の同一識別子、同じ表示名・メールアドレスを理由に、利用者を誤って統合・引き継ぎしない |
| 委任範囲 | 外部アプリケーションが扱える利用者・資源・操作・有効期間を確認し、その範囲を超える権限を付与・発行しない |
| 操作別の認可 | 参加・発行・購読・DataChannel・状態取得・通知・管理操作を個別に確認する。自分の参加端末の権限で別の参加端末を操作しない |
| 通信権限の失効 | 対象の操作・通信を反映期限内に停止する。対象外の許可された通信を不必要に終了しない |
| 失効と処理の競合 | 資格情報の発行・更新・操作実行・送信開始との確定順序を守る。有効期限内の古い情報でも、反映済みの失効を覆さない |
| 通知が一切届かない場合 | 保持情報の有効期間と再確認により、失効の反映期限内に対象通信を停止する。再接続・再試行で期限を延長しない |
| 時計・中断・再起動 | 時計のずれ、処理中断、再起動で期限を数え直さない。必要な状態を確認できなければ、新しい許可・延長・再開を行わない |
| 停止結果の確認 | 通知の送受信と、実際の適用・拒否・通信停止・資源解放を区別する。結果不明を完了と扱わない |
| SFU 移行・担当変更 | 新旧接続・資源と権限情報を区別する。古い資格情報・更新・完了通知で新しい状態を変更しない |
| 資源上限・過負荷 | 未認証・認証済みの要求、並行処理、再試行でも上限を超えない。過負荷を理由に検証や失効期限を緩めない |

ログアウトでは連携先の設定に従い、既存通話を必ず終了するとはしない。
アカウント停止・明示的な権限失効では、必要な操作・通信が期限内に停止することを確認する。

反映期限の測定は、Signaling の失効決定から、対象コンポーネントでの拒否・通信停止までを対象とする。
通常の通知経路だけでなく、通知の全欠落と再確認経路の障害を組み合わせて検証する。
時計誤差・処理遅延などの成立条件と、その条件を確認できない場合の停止結果を記録する。
通知の受信や停止要求の受け付けだけで、期限を満たしたとは判断しない。

### 共通の検証方法と結果の記録

性能試験は、認証・資格情報の発行・更新・照会の頻度、利用者数、権限情報の有効期間、失効対象数、障害条件を固定して比較する。
処理量、応答時間、失効反映時間、依存先への問い合わせ量、CPU・メモリ・保持状態を測定する。
過負荷時も同じ認証・認可・失効条件を維持する。
合否基準は試験前に定め、測定完了と目標達成を区別する。

検証には、共通の実装・検証方針を適用する。

| 検証方法 | 重点対象 |
|---|---|
| TLA+ によるモデル検査 | 委任範囲、資格情報の発行・更新・失効の競合、保持情報の期限、通知欠落、接続引き継ぎ、再起動と停止完了 |
| Property-based Testing | 権限変更と通知の操作列、期限判定、更新・再試行、対象の対応、失効後の復活防止、資源計上 |
| 形式的な証明の評価 | 委任範囲を超えない発行、権限の組み合わせ、期限計算、更新順序の不変条件について、Lean 4・Verus・Aeneas の適合性を評価する |

安全性に加え、必要な通信・処理・障害回復の前提の下で、更新・停止・照合・回収が完了する活性を検証する。
モデルの前提と実装・実行環境の対応を確認する。
方式の評価、モデル検査、形式検証、Fuzzing、静的解析、統合試験の結果と保証範囲を区別する。
