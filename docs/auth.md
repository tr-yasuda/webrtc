# 認証・認可・資格情報

共通の前提・用語・利用場面は [共通仕様](spec.md)に従う。
各プロトコルの認証・状態管理は、それぞれのコンポーネント仕様に従う。
参加端末間の暗号化と鍵管理は、[E2EE・鍵管理](e2ee.md)に従う。

## 前提

- 認証、操作の許可判断、トークン・資格情報の発行は、それぞれ担当する処理を分ける。別々のサーバープロセスで実行することは必須としない。
- 外部アプリケーションのログイン・利用者管理には、既存の認証基盤を利用する。今回のプラットフォームで独自に再実装しない。
- 外部認証の結果から、要求元が誰かを確認する。認証に成功しただけでは、ルームへの参加や操作を許可しない。
- 参加・発行・購読・データ送信・管理操作の許可は、C-Plane が管理する現在の権限に基づいて判断する。外部アプリケーションの要求や、トークンに記載された権限だけで、C-Plane が管理する権限を書き換えない。
- 外部アプリケーションが利用者に与えられる権限の範囲は、プラットフォームが信頼する管理主体または設定によって定める。外部アプリケーション自身が、その範囲を拡大することはできない。
- 資格情報を発行する際は、発行を要求する側の権限、外部アプリケーションに任せた範囲、対象利用者の現在の権限、要求された用途・対象・操作を確認する。いずれの範囲も超えない権限だけを発行する。
- 各コンポーネントは、資格情報が有効かどうかと、現在その操作を許可できるかを別々に確認する。認証や署名検証に成功したことだけで、操作・通信を無期限に許可しない。毎回 C-Plane へ問い合わせることは必須とせず、有効期限内の権限情報を利用できる。ただし、権限変更・失効を定められた期限内に反映し、期限内に必要な権限を確認できない場合は、既存仕様に従って対象の処理・通信を停止する。
- 用途ごとに、受け入れる資格情報の発行元、利用先、利用者・サービス、対象資源、操作、期限、検証条件を定める。別の用途で発行された資格情報を、無条件に受け入れない。
- トークンの有効期限、利用権限の有効期限、権限を再確認する期限、失効を反映する期限、各プロトコル状態の寿命を分けて管理する。一つを更新しただけで、ほかの期限を延長しない。
- Browser SDK に、サーバー側の署名鍵や TURN 資格情報の生成・検証に使う共通秘密情報を渡さない。E2EE の秘密鍵・復号鍵を C-Plane・D-Plane に渡さない。
- 既存の認可、通信停止、資源管理、E2EE、各プロトコルの認証要件は変更しない。TURN 資格情報の通常の期限切れと明示的な失効は、既存の TURN 仕様に従って扱う。
- 参加 JWT は署名付きとする。署名アルゴリズム、OAuth 2.0、OpenID Connect、更新・検証方式、失効情報の同期方式は、要件とトレードオフを整理してから選定する。ほかの用途の資格情報まで JWT に統一することは要求しない。

## 用語

参加者、参加端末、ルーム、発行、購読、C-Plane、D-Plane は、共通仕様の定義に従う。

| 用語 | 意味 |
|---|---|
| 外部アプリケーション | プラットフォームを利用し、許可された範囲で利用者の参加や操作を要求するアプリケーション |
| 外部認証基盤 | 外部アプリケーションのログインと利用者管理を行う既存の仕組み |
| 主体 | 認証や権限確認の対象となる利用者、アプリケーション、内部サービス |
| 認証 | 要求元が誰かを確認すること |
| 認可 | 現在の権限と対象の状態に基づき、要求された操作を許可するか判断すること |
| 委任範囲 | 外部アプリケーションが、利用者に権限を与えたり資格情報の発行を要求したりできる範囲 |
| 権限情報 | 誰が、どの資源に、どの操作を行えるかと、その有効期限などを示す情報 |
| 資格情報 | 認証や利用許可の確認に使うトークン、TURN のユーザー名・パスワードなどの情報 |
| アクセストークン | 対象サービスに提示し、参加や操作の許可を受けるために使う資格情報 |
| 参加 JWT | Browser SDK がルームへの参加や許可された操作に使う、署名付き JWT 形式のアクセストークン |
| 発行元 | トークンや資格情報を発行する主体 |
| 利用先 | そのトークンや資格情報を受け入れるサービス・機能 |
| 失効 | 期限前であっても、対象の資格情報や権限を無効にする決定。各コンポーネントがその決定を反映し、操作を拒否したり通信を停止したりする処理とは区別する。決定と反映は必ずしも同時に完了しない |
| トークンの有効期限 | そのトークンを有効な資格情報として受け入れられる期限 |
| 利用権限の有効期限 | 対象の操作や通信を許可する期間の終わり |
| 権限の再確認期限 | 保持している権限情報だけで判断を続けられる期限。期限内に必要な確認ができなければ、対象の処理・通信を停止する |
| 失効の反映期限 | 失効を各コンポーネントの拒否・通信停止に反映する期限。起点と完了条件は後続の節で定める |
| プロトコル状態の寿命 | TURN Allocation、Permission、Channel Binding など、各プロトコルが保持する状態の存続期間 |

## 利用場面

利用者 A が、外部アプリケーションから会議ルームへ参加し、通話中に権限が変更される場面を扱う。

1. A は、外部アプリケーションが利用する既存の認証基盤でログインする。

2. 外部アプリケーションは、A のルーム参加と、音声・映像の発行・購読に必要な資格情報の発行を要求する。C-Plane 側では、要求元の認証、委任範囲、A の現在の権限を確認する。許可された範囲に限って参加 JWT を発行する。

3. Browser SDK は、取得した参加 JWT を Signaling に提示する。Signaling はトークンの有効性と現在の参加権限を確認し、A の参加端末を登録する。登録だけでは、メディアやデータの送受信を開始しない。

4. Browser SDK と SFU が接続を準備する。TURN が必要なら、C-Plane は利用権限を確認して TURN 資格情報を発行する。参加 JWT、TURN 資格情報、ICE 資格情報は、それぞれの用途で使用する。Browser SDK にサーバー側の署名鍵や TURN の共通秘密情報は渡さない。

5. 必要な WebRTC Transport と E2EE の準備が整い、発行・購読の権限を確認できた通信から開始する。各コンポーネントは、有効期限内の権限情報を利用でき、毎回 C-Plane へ問い合わせる必要はない。

6. 参加 JWT の更新が必要になった場合は、現在の権限を再確認して発行する。トークンを更新しただけで、利用権限、権限の再確認期限、TURN Allocation などの寿命をまとめて延長しない。

7. 通話中に、権限を持つ管理者が A のカメラ映像の発行権限を失効させる。C-Plane による失効の決定と、SFU などの各コンポーネントによる通信停止は、必ずしも同時ではない。失効を決定した後、定められた反映期限内に対象の通信を停止する。停止後は、古いトークンや権限情報によってカメラ映像の発行を再開できない。失効の決定だけで通信停止まで完了したとは扱わない。ほかの権限が有効なら、音声や購読は継続する。

8. 失効通知が届かない場合も、必要な権限を期限内に再確認できなければ、対象の処理・通信を停止する。再接続や通知の再送だけで期限を延長しない。

9. A が退出すると、その参加端末の通信を終了し、関連する資源を解放する。遅延した更新結果や通知によって、終了した通信を再開しない。

参加 JWT は署名付きとする。外部認証との連携方式、更新手順、権限情報の伝達方式は固定しない。

## 外部認証基盤との連携

外部アプリケーションのログイン・利用者管理は、既存の認証基盤が行う。
プラットフォームは、設定した連携先から認証結果を受け入れ、ルームへの参加や操作に必要な権限を別に確認する。
利用者のパスワードを、プラットフォームが預かって認証する構成は要求しない。

連携先ごとに、次の条件を設定する。

| 項目 | 定める内容 |
|---|---|
| 信頼する相手 | 認証基盤、外部アプリケーション、発行元を識別する情報 |
| 検証方法 | 認証結果の真正性、有効期限、利用先、対象利用者を確認する方法 |
| 利用者の対応 | 外部の利用者識別子と、プラットフォームの参加者との対応 |
| 委任範囲 | 外部アプリケーションが扱えるルーム、資源、操作、権限付与・資格情報発行の範囲 |
| 変更・終了時の扱い | 連携設定の変更・無効化や、外部側の利用停止を反映する条件 |

Browser SDK から渡された発行元や接続先を、そのまま信頼する連携先として登録しない。
認証結果の検証に使う接続先・鍵は、信頼する設定に基づいて選ぶ。
具体的な連携方式と検証方式は、後続の方式選定で決定する。

外部の利用者は、認証基盤・発行元と、その中の利用者識別子を組み合わせて識別する。
異なる認証基盤の識別子が一致しても、同じ利用者とは扱わない。
表示名やメールアドレスの一致だけで、既存の参加者へ自動的に結び付けない。
連携先や識別子を変更する場合も、既存利用者を引き継ぐ根拠を確認する。

外部アプリケーション自身の認証と、そのアプリケーションが扱う利用者の認証結果を区別する。
資格情報の発行要求では、要求元がその利用者・ルーム・操作を扱えることを確認する。
利用者がログイン済みであることだけで、要求元の委任範囲を広げない。

外部のロールやグループを権限判断に利用する場合は、どの情報から、どのプラットフォーム権限を与えられるかを定める。
外部の「管理者」という名称だけで、プラットフォーム全体の管理権限を与えない。
権限の追加・変更は、C-Plane が委任範囲と対象を確認して反映する。
外部アプリケーションが申告した権限を、確認せず採用しない。

外部認証の資格情報を、ルーム参加用や TURN 用として無条件に受け入れない。
発行元が同じでも、用途と利用先に応じた検証を行う。
外部認証基盤の秘密情報や、外部アプリケーションのサーバー用資格情報を Browser SDK に渡さない。

外部側のログアウト、利用者の停止・削除、アプリケーションの利用停止について、どの参加・操作権限を失効させるかと、その変更をプラットフォームへ伝える条件を定める。
ログアウトだけで既存の通話を必ず終了させることは要求せず、連携先ごとに定めた条件に従う。
アカウント停止や明示的な権限失効では、定められた期限内に必要な操作・通信を停止する。
外部側での変更だけで、通信停止まで完了したとは扱わない。
変更を検知する条件、失効を決定する時点、各コンポーネントへの反映期限を区別する。

連携先へ一時的に接続できない場合も、必要な確認を省略して新規認証や権限拡大を許可しない。
既存通信の継続は、有効な権限情報と既存仕様の再確認・停止条件に従う。
問い合わせの失敗や再試行だけで、情報の有効期限を延長しない。

外部から取得・保持する利用者情報は、識別と権限判断に必要な範囲に限定する。
認証情報や不要な個人情報を、ログ・通知へ出力しない。

## 認可の対象と判断

C-Plane は、利用者・参加端末・外部アプリケーション・内部サービスに許可する資源と操作を管理する。
各コンポーネントは、その権限情報と現在の対象状態に基づいて操作・通信を許可する。
認証に成功したことや、対象の識別情報を知っていることだけでは許可しない。

権限は、次の対象と操作を区別して管理する。

| 対象 | 区別する操作・範囲 |
|---|---|
| ルーム | 作成・削除・設定変更・状態取得・参加 |
| 参加者・参加端末 | 自分の参加端末の退出、別の参加端末の操作・除外、接続の引き継ぎ |
| 発行 | 音声・カメラ映像・画面共有の開始・変更・停止、操作できる発行元の参加端末 |
| 購読 | 購読の追加・変更・解除、受信できる発行 |
| DataChannel | 論理チャネルの作成・利用、送信・受信、許可された宛先 |
| 状態・通知 | 取得できる情報と、変更通知を受け取れる範囲 |
| TURN | 利用できる用途・接続・中継先 |
| 管理操作 | 操作できるルーム・参加端末・設定と、実行できる管理機能 |
| 内部サービス | 指示できるコンポーネント・接続・操作 |

ルームへの参加権限と、発行・購読・データ通信・管理操作の権限を分ける。
一つの操作が許可されていても、ほかの操作を自動的に許可しない。
具体的な権限名やロールの構成は、この段階では固定しない。

参加者と参加端末を区別する。
自分の参加端末の操作権限だけで、同じ参加者の別の参加端末を操作・終了させない。
発行・購読・論理チャネルは、所有する参加端末、所属ルーム、現在の接続との対応を確認する。
別の参加端末の操作や接続の引き継ぎには、その対象を扱う権限を必要とする。

外部アプリケーションの委任範囲には、対象資源、対象利用者、許可する操作、付与できる権限、有効期間の制約を定める。
権限付与や資格情報の発行要求を受けた場合は、要求元がその対象と操作を扱えることを確認する。
要求された権限が委任範囲を超える場合は、超過した権限を付与・発行しない。
認証済みの外部アプリケーションでも、自身の委任範囲を変更できるとは扱わない。

トークンに権限が記載されていても、現在の権限を広げる根拠にはしない。
操作は、資格情報が許す用途・対象・操作と、現在の権限の両方を満たす場合に限って許可する。
資格情報の更新・再発行だけで、失効した権限を復活させない。

DataChannel の送信権限と受信権限を区別する。
送信者が指定した宛先は、送信を許可された範囲に含まれることを確認する。
ルームへの参加だけで、すべてのメッセージの受信・復号を許可しない。
受信権限と E2EE の鍵配布範囲は、E2EE 仕様に従って一致させる。

状態取得や通知購読にも、対象と情報ごとの権限を適用する。
変更操作を拒否するだけでなく、未許可のルームや参加端末の状態・接続情報・鍵管理メッセージを取得させない。
管理権限があることだけで、E2EE 本文や復号鍵を取得できるとは扱わない。

各コンポーネントは、検証済みで有効期限内の権限情報を利用できる。
毎回 C-Plane へ問い合わせることは要求しない。
権限情報がどの利用者・サービス、資源、操作に対するものか確認し、異なる対象や古い接続の情報を流用しない。
権限変更・失効の反映期限と、確認不能時の停止条件は、後続の「有効期限・権限変更・失効の反映」で定める。

操作の受け付け後に、退出、権限失効、接続の引き継ぎ、SFU 移行が起きる場合も考慮する。
実行時には、その操作が現在も許可され、対象が同じであることを確認する。
この確認には、有効期限内の権限情報を利用でき、毎回 C-Plane へ問い合わせる必要はない。
権限失効や接続の引き継ぎと操作が競合した場合は、既存仕様で定めた確定順序に従って許可・拒否を判断する。
古い権限情報が有効期限内でも、対象コンポーネントに反映済みの失効を無視して操作を許可しない。
通信停止と送信開始が競合する場合の判定は、SFU・SCTP / DataChannel 仕様に従う。
古い操作や通知によって、新しい接続・権限状態を変更しない。

権限があっても、資源上限、WebRTC Transport の送信同意・相手認証、E2EE の鍵条件を省略しない。
認可、プロトコル上の接続条件、暗号条件、資源の利用可能性を、それぞれ確認する。

## 参加 JWT の発行・更新・失効

参加 JWT は、Browser SDK が対象ルームへの参加や許可された操作に使用するアクセストークンとする。
TURN、ICE、内部サービス、管理操作の資格情報として無条件に流用しない。

発行処理では、発行要求元を認証し、対象利用者・ルーム・操作を扱う権限と委任範囲を確認する。
利用者の認証結果と現在の権限も確認する。
Browser SDK が申告した参加者・ルーム・権限を、そのまま採用しない。

発行するトークンには、直接格納するか、検証時に取得できる情報として、次を対応付ける。

| 情報 | 確認する内容 |
|---|---|
| 発行元・利用先・用途 | 信頼する発行元が、対象サービスでの参加・操作用に発行したものか |
| 対象利用者・参加者 | 誰の参加・操作に使用できるか |
| 対象ルーム・操作範囲 | どのルームで、何を許可できるか |
| 有効期間 | いつから、いつまで受け入れられるか |
| 識別・管理情報 | 更新・失効・監査で対象のトークンや発行関係を識別できるか |

対象の参加端末を発行時に指定する場合は、その対応も検証する。
参加処理で参加端末を登録する場合も、トークンや参加端末識別情報の所持だけで、既存の別の参加端末を引き継がせない。
接続の引き継ぎは Signaling 仕様に従う。

参加 JWT は署名付きとする。
署名アルゴリズム、格納する情報の具体的な表現、オンライン照会の利用などの検証方法は、この段階では固定しない。
JWT の署名検証に加え、発行元・利用先・用途・対象・権限・有効期限・失効と現在の利用権限を確認する。

Browser SDK への受け渡しは、保護された通信と、認証した利用者との対応を確認できる方法で行う。
URL、ログ、エラー報告、公開状態、開発者向けデバッグ機能へ露出させない。
ブラウザーの WebSocket API の制約を考慮し、Signaling 接続の認証方法と合わせて選定する。

更新時は、更新を要求する側の認証・権限と、対象利用者の現在の権限を再確認する。
更新可能な資格情報を持っていることだけで、権限の拡大や失効の取り消しを許可しない。
外部アプリケーションを通じた再発行と、専用の更新用資格情報を使う方式は、後続の方式選定で比較する。
Browser SDK に更新用の長期資格情報を保持させることは、この段階では要求しない。

更新後のトークンは、その時点で許可された範囲に限定する。
旧トークンと新トークンを併用できる条件と期間には上限を設ける。
更新しても、参加端末、通話時間の起点、SFU の退役期限を初期化しない。
利用権限、権限の再確認期限、プロトコル状態の寿命も、自動的には延長しない。

トークンが期限切れの場合、そのトークンによる新しい参加・操作の認証には使用しない。
既存の通信を継続できるかは、現在の利用権限、権限情報の有効性、WebRTC Transport・E2EE の条件に基づいて判断する。
トークンの更新に失敗したことだけで直ちに退出させるとは限らないが、必要な権限を期限内に確認できなければ、既存仕様に従って対象の操作・通信を停止する。

失効では、対象が個々のトークン、参加端末、利用者、ルーム、外部アプリケーションのどれかを識別する。
トークンだけを失効させる操作と、既存通信の利用権限まで失効させる操作を区別する。
トークンだけを失効させた場合は、その失効を定められた期限内に反映し、反映後はそのトークンによる新しい認証を拒否する。
既に認証済みの接続を終了するかどうかは、失効対象と現在の利用権限に基づいて判断し、トークン単体の失効だけで必ず終了するとはしない。
参加端末や利用者の通信権限そのものを失効させた場合は、既存仕様に従って対象の通信を停止する。
利用権限も失効させる場合は、関係するコンポーネントへ定められた期限内に反映し、対象の操作・通信を停止する。
反映済みの失効を、旧トークン、更新結果、遅延した通知で取り消さない。

参加 JWT の発行・更新と失効が並行する場合は、その処理の順序を確認する。
失効が先に確定している範囲について、古い確認結果から新しい有効な資格情報を発行しない。
発行後に失効が決定された場合は、その資格情報も対象範囲に従って失効を反映する。

参加 JWT の発行・更新の応答が失われた場合も、同じ要求の再試行で権限や有効期間を意図せず拡大しない。
結果不明の扱い、再試行、保持する発行記録には、期限と資源上限を設ける。

監査には、参加 JWT の発行・更新・失効の要求元、対象、許可範囲、結果を確認するために必要な情報を記録する。
トークン本体、署名鍵、更新用の秘密情報は記録しない。

## 用途別の資格情報と検証条件

資格情報は用途ごとに、発行する側、受け入れる側、許可できる操作、検証条件を定める。
同じ発行元や暗号方式を使っていても、別用途の資格情報を無条件に受け入れない。

| 用途 | 受け入れる側 | 確認する範囲 |
|---|---|---|
| 外部認証の情報 | C-Plane の外部認証連携処理 | 設定済みの連携先、対象利用者、認証結果の有効性 |
| 外部アプリケーションの資格情報 | 権限変更・資格情報発行などを受け付ける C-Plane | 要求元、扱える利用者・資源・操作、委任範囲 |
| 参加 JWT | C-Plane・Signaling の参加・操作の受け付け | 対象利用者・ルーム・操作、有効期間、失効、現在の利用権限 |
| TURN 資格情報 | TURN サーバー | プロトコル認証、資格情報の有効性、Allocation の所有者、用途別の利用許可 |
| ICE 資格情報 | 対象接続の ICE エージェント | 接続・ICE 世代、ICE 接続確認の認証と要求・応答の対応 |
| 内部サービスの資格情報 | 指示や状態通知を受け付ける内部コンポーネント | サービスの識別、指示できる対象・操作、資格情報の有効性 |
| 管理操作の資格情報 | 管理 API を提供する C-Plane | 管理主体、操作対象、管理権限、有効期間と失効 |

参加者の資格情報を持っていることだけで、管理操作や内部サービスの指示を許可しない。
外部アプリケーションの資格情報を持っていることだけで、任意の利用者として参加させない。
管理操作の認証方式と内部サービスの認証方式も、それぞれの用途に応じて選定する。

各用途について、次の検証条件を定める。

| 条件 | 検証する内容 |
|---|---|
| 発行元と真正性 | 用途に応じて、信頼する発行元や、認可された接続で生成・共有した資格情報との対応を確認し、不正な情報を受け入れないか |
| 利用先と用途 | このコンポーネントが、この処理で受け入れてよい資格情報か |
| 対象の対応 | 利用者・サービス、ルーム、参加端末、接続などが処理対象と一致するか |
| 操作範囲 | 要求された操作が、資格情報の範囲と現在の権限の両方に含まれるか |
| 有効期間と失効 | 利用可能な期間内であり、反映済みの失効に該当しないか |
| 再利用条件 | 別接続への流用、再送、更新、再接続で使用できる条件を満たすか |

共通の検証条件は、用途ごとに適切な認証・検証手順へ対応付ける。
すべての資格情報に、同じ発行元検証や署名検証を要求しない。
参加 JWT や外部アプリケーションの資格情報は、採用する発行・検証方式に従う。
ICE のように接続ごとに生成・共有する資格情報は、認可された接続・ICE 世代との対応と、プロトコルの認証手順によって確認する。

これらの情報を、すべての資格情報へ同じ形式で格納することは要求しない。
直接含まれる情報、サーバー側の記録、認可済みの接続状態などを組み合わせて確認できるようにする。
TURN・ICE・DTLS のメッセージ形式、認証・相手検証の手順、状態管理の条件は、既存の各プロトコル仕様を維持する。

受け入れる用途は、受け付けるサービス・機能と信頼する設定に基づいて決定する。
資格情報自身が申告した用途・発行元・検証方式だけで、受け入れ条件を変更しない。
ある用途の検証に失敗した資格情報を、別用途として自動的に試し直して受け入れない。

資格情報の検証と、C-Plane が管理する権限情報の確認を分ける。
各コンポーネントは、有効期限内の権限情報を利用でき、毎回 C-Plane へ問い合わせる必要はない。
ただし、対象コンポーネントに反映済みの失効や接続の引き継ぎを、古い情報で覆さない。
必要な情報を期限内に確認できない場合は、既存仕様に従って対象の処理・通信を停止する。

トークン単体の失効、通信権限の失効、プロトコル状態の期限切れを区別する。
既存接続への影響は、参加 JWT・TURN・WebRTC Transport など、それぞれの確定済み条件に従う。
資格情報が更新されたことだけで、別用途の資格情報や通信状態の期限を更新しない。

単独 STUN Binding によるアドレス確認は、資格情報を要求しない既存方針を維持する。
この例外を、ICE 接続確認や TURN の利用認証へ適用しない。
DTLS の証明書検証と E2EE の鍵確認も、参加 JWT や利用権限の確認の代わりにはしない。

資格情報は必要な相手にだけ渡す。
Browser SDK には利用に必要な参加 JWT や TURN 資格情報を渡せるが、サーバー側の署名鍵、TURN の共通秘密情報、内部サービス用の資格情報は渡さない。
D-Plane が利用者の資格情報そのものを受け取る必要があるか、検証済みの権限情報を受け取るかは、後続の設計で決定する。
どちらの場合も、指示元・対象・操作・有効期限の確認を省略しない。

## プロトコル資格情報との連携

C-Plane は、プロトコルの利用を許可する主体・接続・用途を確認する。
各プロトコルの処理は、その許可と、プロトコル固有の認証・状態管理の両方を適用する。
共通のトークン形式で、TURN・ICE・DTLS の手順を置き換えない。

| 対象 | プラットフォーム側の責務 | プロトコル側の責務 |
|---|---|---|
| 単独 STUN Binding | 公開条件と資源制限を管理する | 認証不要の Binding を既存仕様に従って処理する |
| TURN | 資格情報の発行、利用者・参加端末との対応、用途・中継先の許可を管理する | 長期資格情報方式の認証、Allocation の所有者確認、Permission・Channel Binding と転送条件を適用する |
| ICE | 対象接続・参加端末・交渉との対応を管理し、必要な接続情報を交換する | 資格情報の生成・使用、ICE 接続確認、ICE 世代と経路の状態を管理する |
| DTLS | 認可された接続と、交換する証明書フィンガープリントなどの対応を管理する | 用途に応じた相手検証、ハンドシェイク、鍵確立・使用上限を適用する |

TURN 資格情報は、C-Plane が現在の利用権限を確認して発行する。
ブラウザー用と SFU 自身の TURN 利用を区別し、資格情報の所持だけで別用途の許可を取得できないようにする。
生成・検証に必要な情報を TURN 側へ安全に配布する。
共通秘密情報を使用する方式を採用する場合も、それを Browser SDK へ渡さない。

TURN 資格情報の更新・失効は、既存 Allocation と利用者・参加端末の対応を維持して処理する。
ユーザー名や認証に用いる秘密情報が変わる場合の新しい Allocation の作成、通常の資格情報期限切れ後の転送、明示的な失効による停止は、TURN 仕様に従う。
参加 JWT の更新だけで、TURN 資格情報や Allocation を更新しない。

ICE 資格情報は、ブラウザー側ではブラウザーの ICE エージェント、SFU 側では自作する ICE エージェントが生成・管理する。
Signaling は、認可された接続と交渉に対応付けて交換する。
参加 JWT や TURN パスワードを、ICE の秘密情報として流用しない。
ICE restart では新しい世代の資格情報を使用し、旧世代の要求・応答を新世代の認証結果として扱わない。

ICE の認証成功、経路の到達性、Consent Freshness、プラットフォームの利用権限を区別する。
ICE 接続確認に成功しても、未許可の発行・購読・データ通信を開始しない。
利用権限が失効した場合、ICE 資格情報や経路が有効なままでも、既存仕様の期限内に対象通信を停止する。

STUN / TURN の TLS・DTLS では、サーバーが適切な証明書を提示し、接続するクライアントが信頼・有効性・接続先名を検証する。
WebRTC Transport の DTLS では、対象接続の正当な交渉で受け取ったフィンガープリントと実際の証明書を照合する。
これらの用途を混同せず、参加 JWT の検証を証明書検証の代わりにしない。

DTLS Association の継続・再確立、証明書情報の変更、ICE restart との関係は、Signaling・WebRTC Transport 仕様に従う。
トークン更新や ICE 資格情報の変更だけで、証明書・フィンガープリントの変更を許可しない。
DTLS・SRTP/SRTCP の鍵と、参加端末間の E2EE の鍵は、それぞれの仕様に従って管理する。

再接続・SFU 移行では、新旧の資格情報、接続、ICE 世代、Allocation、権限情報の対応を維持する。
新しい接続先へ切り替えたことだけで権限を広げず、旧接続の資格情報や遅延通知で新しい接続を操作させない。
移行中に新旧の資源を同時に確保する場合も、共通の資源上限を適用する。

資格情報の配布・更新・失効情報の伝達に失敗した場合は、用途ごとの有効期限と停止条件に従う。
再試行だけで期限を延長せず、確認できない情報を有効とみなして通信を継続しない。
具体的な配布・同期方式と Rust の実行方式は、この段階では固定しない。

## サービス認証と権限の伝達

C-Plane と D-Plane、および内部コンポーネント間では、要求・通知の送信元と、扱える対象・操作を確認する。
内部ネットワークから届いたことや、サービスの認証に成功したことだけで、すべての接続・資源の操作を許可しない。

サービスの識別と、そのサービスが利用者に代わって行う操作の認可を区別する。
利用者の参加 JWT を転送したことだけで、指示元サービスの確認を済ませない。
サービス自身に許可された操作でも、対象利用者・参加端末の権限が必要な処理では、その権限も確認する。

別プロセス間の通信は、既存の共通セキュリティ条件に従い、相互認証と通信の暗号化を行う。
相手の識別情報を、設定した信頼関係と許可範囲に照合する。
具体的なサービス認証方式は、後続の方式選定で決定する。

同一プロセス内でも、誰がどの対象を操作できるかと、処理結果がどの要求に対応するかを確認する。
同じプロセスで動作することを理由に、未許可の呼び出しや対象の取り違えを許可しない。
同一プロセス内の呼び出しに、ネットワーク通信や署名付きトークンの使用を一律に要求しない。
これらの検証は、別プロセスと同等の隔離や、同一プロセス内の任意のコード実行に対する保護を保証するものとは扱わない。
具体的な実行方式と分離方法は、後続の技術選定で判断する。

C-Plane から D-Plane へ渡す権限情報は、次の内容を確認できるようにする。

| 情報 | 確認する内容 |
|---|---|
| 指示元 | どのサービスが指示し、その対象・操作を扱う権限があるか |
| 対象 | ルーム、参加端末、接続、発行・購読、Allocation など、どの資源に適用するか |
| 許可範囲 | 利用できる操作、用途、中継先などの制約 |
| 有効性 | いつまで利用でき、いつまでに再確認が必要か |
| 更新の対応 | どの権限状態や割り当てに対する更新・失効か |
| 処理の対応 | どの要求に対する受け付け・適用・停止・解放の結果か |

これらを一つのトークンやメッセージへ格納することは要求しない。
認証済みの通信、検証済みのデータ、管理する接続状態などを組み合わせて確認できるようにする。
受信した情報だけで、指示元が自身の許可範囲を拡大できないようにする。

D-Plane は、検証済みで有効期限内の権限情報を使って処理できる。
パケットごと、操作ごとに C-Plane へ問い合わせることは要求しない。
ただし、反映済みの失効や新しい接続・割り当ての状態を、古い情報で上書きしない。

要求・更新・失効・完了通知は、対象資源と処理に対応付ける。
遅延、重複、順序逆転、再起動、接続の引き継ぎ、SFU 移行によって、旧資源への指示を新しい資源へ適用しない。
操作と失効が競合する場合は、既存仕様の確定順序に従う。

D-Plane からの状態通知と処理結果も、送信元、対象資源、現在の担当、要求との対応を確認する。
要求の受け付け、権限の適用、通信停止、資源解放を区別する。
受け付け通知だけで、停止・解放まで完了したとは判断しない。
結果が不明な場合は、共通の資源管理に従って照合する。

C-Plane との通信や権限情報の取得に失敗した場合も、確認済み情報の有効期限と用途ごとの停止条件に従う。
確認不能になっただけで、直ちにすべての既存通信を停止することは要求しない。
必要な確認ができないまま期限に達した場合は、対象の処理・通信を停止する。
再接続・再試行だけで期限を延長しない。

内部サービスの資格情報や権限伝達用の秘密情報を、Browser SDK・React SDK に渡さない。
サービス認証用の鍵・資格情報と、TURN・ICE・DTLS・E2EE の鍵・資格情報を無条件に共用しない。
ログや処理結果に秘密情報を含めない。

サービス認証、権限情報の配布、再確認、失効通知、結果照合にも、処理量・保持状態・待機時間の上限を設ける。
具体的な通信方式、同期方式、識別情報の形式、Rust の実行方式は、この段階では固定しない。

## 有効期限・権限変更・失効の反映

有効期限と反映期限は、用途と対象ごとに管理する。

| 対象 | 期限に達した場合の扱い |
|---|---|
| トークン | そのトークンによる新しい認証を拒否する。既存接続への影響は、失効対象と現在の利用権限から判断する |
| 利用権限 | 対象の操作・通信を許可しない |
| 保持している権限情報 | 必要な再確認ができなければ、対象の処理・通信を停止する |
| 失効の反映 | 対象コンポーネントで拒否・通信停止を完了する |
| プロトコル状態 | TURN・ICE・DTLS など、各仕様の期限・更新・終了条件を適用する |

一つの情報を更新しても、ほかの期限を自動的に延長しない。
TURN 資格情報の通常の期限切れと既存 Allocation の継続条件は、TURN 仕様を維持する。

C-Plane は、権限変更・失効の対象、適用する変更、決定した時点を識別できるようにする。
失効の反映期限は、C-Plane が失効を決定した時点を起点とする。
外部認証基盤での変更から C-Plane が失効を決定するまでの条件は、「外部認証基盤との連携」で定める。
外部での変更、失効の決定、各コンポーネントでの停止を、同時に完了したとは扱わない。

各コンポーネントは、失効の反映期限内に、対象の新しい操作を拒否し、対象通信を停止する。
トークン単体の失効では、そのトークンによる新しい認証を拒否する。
参加端末や利用者の通信権限を失効させた場合は、既存通信にも停止を適用する。
失効対象外で、必要な権限・接続・暗号条件を満たす通信は継続できる。

失効通知を送受信した後も、対象への反映が完了したかを確認する。
対象コンポーネントで権限変更を適用し、必要な拒否・停止が行われたことを確認する。
資源解放は通信停止と区別し、解放確認まで共通の資源管理に従って計上する。
反映結果が不明な場合は、完了と断定せず、照合と必要な停止処理を行う。

失効通知の欠落や、C-Plane と D-Plane 間の通信断を考慮する。
保持している権限情報を使える期間には有限の上限を設ける。
通知が届かない場合も、情報の有効期限と再確認の仕組みによって、失効の反映期限を超えて対象通信を継続しない構成とする。
毎回 C-Plane へ問い合わせることは要求しない。

権限情報を取得できなくなっただけで、すべての既存通信を直ちに停止することは要求しない。
確認済み情報を利用できる期限と、その用途の停止条件に従う。
期限内に必要な確認ができなければ、対象の処理・通信を停止する。
再接続、要求の再送、同じ通知の再受信だけで期限を延長しない。

権限情報の期限を延長するには、その対象について使用可能な権限が継続していることを確認する。
古い情報が遅れて到着した時刻を起点に、有効期間を新しく数え直さない。
時計のずれ、処理の中断、再起動によって、期限を超えた情報を利用しない。
期限を安全に判断できない場合は、その情報による新しい許可や期限延長を行わない。

権限変更の順序は、通知の到着順だけで判断しない。
対象の利用者・参加端末・資源と、変更前後の関係を確認する。
適用済みの失効や新しい接続・割り当てを、古い権限情報、更新結果、再試行で取り消さない。
失効後に権限を再付与する場合は、新しい正当な変更として確認する。

権限変更・失効と、資格情報の発行・更新・操作実行・送信開始が競合する場合は、既存仕様の確定順序に従う。
送信待ち・再送待ちのデータにも停止条件を適用する。
既に実際の送信処理へ引き渡したデータの到着や、受信済みの平文を取り消せるとは保証しない。

再起動・SFU 移行・担当変更後も、必要な失効情報と現在の権限を確認する。
状態を復元できない場合は、確認できていない処理・通信を再開しない。
失効記録の削除によって、古い資格情報や権限情報を再び有効として受け入れない。
記録の保持期間と回収条件は、古い情報が受け入れられる期間と合わせて定める。

反映期限、再確認間隔、権限情報の有効期間、記録の保持期間は、設定と試験で確認できるようにする。
値はこの段階では固定しない。
同期・通知・再確認・照合の方式も、後続の方式選定で決定する。
通知の欠落、分断、並行更新、再起動を含む条件で、期限内の拒否・停止と古い状態への復帰防止を検証する。

## 署名・検証と鍵の管理

資格情報の署名・検証方法は、用途ごとに選定する。
すべての資格情報に署名付きトークンを要求しない。
署名、MAC、参照先への照会、プロトコル固有の認証など、採用した方式で必要な検証を行う。

署名・MAC・ハッシュ・暗号学的な乱数生成には、既存の安全な実装を利用する。
暗号アルゴリズムを独自実装しない。
利用を許可するアルゴリズム、鍵形式、鍵の強度と用途を設定し、入力された資格情報の指定だけで変更しない。

署名や MAC の検証に成功しても、それだけで操作を許可しない。
発行元・利用先・用途・対象・有効期間・失効と現在の権限は、「用途別の資格情報と検証条件」に従って確認する。
署名は改ざんを検出するために使い、資格情報の内容の秘匿は保証しない。

鍵の管理では、次を区別する。

| 対象 | 管理する内容 |
|---|---|
| 発行用の鍵・秘密情報 | 使用できる発行処理、用途、保管先、アクセス権限、使用期間 |
| 検証用の鍵・情報 | 信頼する発行元、利用用途、取得元、更新条件、受け入れ期間 |
| 鍵の識別情報 | 対象の発行元・用途・鍵を取り違えずに選ぶための対応 |
| 更新・失効の記録 | 新旧の切り替え、受け入れ終了、漏洩時の対象と処理結果 |

発行用の秘密情報にアクセスできる処理を限定する。
Browser SDK・React SDK に、サーバー側の署名鍵や TURN の共通秘密情報を渡さない。
検証者にも発行能力を与える共通秘密方式と、発行用秘密鍵を渡さず検証できる非対称署名方式は、配布範囲と漏洩時の影響を比較して選定する。

検証鍵は、設定した信頼関係と用途に基づいて取得・選択する。
資格情報に含まれる鍵の識別子や URL だけを根拠に、任意の鍵・接続先を信頼しない。
不明な鍵を受け取った場合も、未検証の鍵で受け入れたり、検証を省略したりしない。
鍵取得の再試行には、処理量・待機時間・保持状態の上限を設ける。

通常の鍵更新では、新しい発行用鍵への切り替えと、各検証側への反映を調整する。
新旧の鍵を受け入れる期間と条件に上限を設ける。
旧鍵を受け入れる場合も、資格情報自体の期限・失効・現在の権限を確認する。
鍵の更新や検証鍵の再取得によって、資格情報の有効期限を延長しない。

鍵の漏洩や不正使用が疑われる場合は、通常の更新と区別して扱う。
発行用の鍵が漏洩した場合は、その鍵による新規発行と検証側での受け入れを停止し、影響する資格情報を無効化する。
鍵の受け入れ停止、資格情報の失効、利用権限の変更は別に判断し、影響範囲に応じて必要な処理を行う。
鍵の漏洩だけを理由に、正規利用者の参加・発行・購読などの権限そのものを必ず取り消すことは要求しない。
対象範囲と反映期限を定め、古い検証鍵の保持だけで受け入れを継続しない。
既存通信を停止するかは、失効対象と現在の権限に従って判断する。
正規利用者が復帰する場合は、既存の認証・認可要件に従って認証と現在の権限を確認し、漏洩した鍵に依存しない新しい資格情報を発行する。
拒否した資格情報の所持だけで再発行を許可せず、旧資格情報や遅延した更新結果を再び有効にしない。

鍵や検証情報を取得できない場合は、確認済み情報を利用できる期限と用途ごとの停止条件に従う。
検証できない新しい資格情報を受け入れない。
再接続・再試行・再起動だけで、鍵の受け入れ期間や権限情報の期限を延長しない。
状態を復元する場合も、受け入れ停止済みの鍵を古い記録から再び有効にしない。

参照型トークンを採用する場合は、参照値に必要な推測耐性を確保し、照会先の認証と通信保護を行う。
照会結果にも、利用先・用途・対象・期限・失効の検証と、有効期限を守った保持を適用する。
トークンの形式が参照型であることだけで、現在の権限や即時の失効反映を保証したとは扱わない。

TURN・ICE・DTLS・E2EE の鍵・秘密情報は、各仕様の生成・配布・更新・削除条件に従う。
参加 JWT の署名鍵を更新しただけで、これらの鍵やプロトコル状態を更新したとは扱わない。

秘密鍵、共通秘密情報、トークン本体を、ログ・監査・診断・エラー報告に出力しない。
不要になった鍵と関連状態は、定めた保持条件に従って削除する。
鍵の保管基盤、配布方式、更新間隔、旧鍵の受け入れ期間、漏洩時の具体的な手順は、後続の選定・設計で決定する。

## 方式選定

認証連携、トークン形式、検証、更新、失効情報の伝達、サービス認証を分けて選定する。
一つの方式を採用したことだけで、ほかの方式まで決定したとは扱わない。
方式は用途ごとに選べる。

ルーム参加用のアクセストークンには、参加 JWT を使用し、独自のトークン形式は作らない。
JWT の発行・解析・署名検証には、既存ライブラリを利用する。
TURN・ICE・DTLS・内部サービスなど、ほかの用途の資格情報まで JWT に統一することは要求しない。

| 選定する項目 | 比較する候補・条件 |
|---|---|
| 外部認証との連携 | 外部アプリケーション経由の連携、認証基盤との直接連携、OAuth 2.0・OpenID Connect の利用範囲 |
| 参加 JWT の署名方式 | 非対称署名方式を優先し、Ed25519 を候補として、安全性、ライブラリ対応、鍵管理、相互接続性を評価する |
| 検証方法 | JWT の署名・情報の検証、現在の利用権限・失効状態のオンライン照会や有効期限内の情報の利用、その併用 |
| 更新方法 | 外部アプリケーション経由の再発行、更新用資格情報の利用 |
| 失効情報の伝達 | 通知、定期的な再確認、その併用 |
| サービス認証 | 実行環境に適した相互認証と、サービスごとの操作制限 |
| 鍵管理 | 保管・配布、通常更新、漏洩時の受け入れ停止と復旧 |
| 権限情報の保持 | 保持する範囲、有効期間、再確認、再起動・移行時の復元条件 |

JWT はトークン形式、OAuth 2.0 は認可の仕組み、OpenID Connect は外部認証との連携に関わる選択として扱う。
これらを同じ目的の代替候補として比較しない。

外部認証との連携方式は、既存基盤の対応機能、外部アプリケーションの認証方法、委任範囲、利用者との対応、停止・失効情報を取得できる条件で評価する。
連携方式を採用しても、外部認証の成功だけでプラットフォームの操作権限を与えない。

JWT の検証時に必要な情報と、発行後の権限変更・失効を確認する方法を合わせて評価する。
ほかの用途で参照型トークンを検討する場合は、照会先への依存、遅延、可用性、情報の保持期間と失効の反映期限を評価する。
トークン形式を選ぶ際も、オンライン照会の要否と失効を保証する方法は別に決める。

ローカル検証では、署名などの検証と、現在の権限・失効の確認を区別する。
オンライン照会でも、結果を保持して利用する場合は、その間の権限変更を確認できない期間を評価する。
照会結果を保持して減らせる負荷と、古い情報を使う期間を、失効の反映期限と合わせて評価する。[RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)

参加 JWT は、署名検証だけで操作を許可しない。
許可アルゴリズム、発行元、利用先、用途、対象、権限、有効期限、鍵の選択と検証規則を定め、現在の利用権限と失効状態も確認する。
同じ発行元の異なる用途の JWT を、相互に受け入れない規則を設ける。[RFC 8725 §3](https://www.rfc-editor.org/rfc/rfc8725.html#section-3)

参加 JWT の署名は非対称署名方式を優先して検討し、Ed25519（EdDSA）を候補とする。
具体的な署名アルゴリズムと JOSE の識別子は、安全性と採用ライブラリ・実行環境の対応を確認して決定する。
Ed25519 を評価する際は、専用の `Ed25519` 識別子と、非推奨となった従来の `EdDSA` 識別子への対応・互換性を区別する。[RFC 9864](https://www.rfc-editor.org/rfc/rfc9864.html#section-2.2)
この段階では、Ed25519 や特定の `alg` 値の採用を確定しない。

OAuth 2.0 を採用する場合は、ブラウザーとサーバー側の役割に応じてフローを選定し、利用先・資源・操作の制限と、盗用・再利用への対策を評価する。
更新用トークンを Browser SDK に保持させる場合は、漏洩時の影響、ローテーションまたは送信者への結び付け、再利用の検出と失効を評価する。[RFC 9700 §2](https://www.rfc-editor.org/rfc/rfc9700.html#section-2)
具体的なフローや更新用トークンの採用は、この段階では決定しない。

Signaling の認証方式は、ブラウザーの WebSocket API で任意の認証ヘッダーを設定できない条件を満たす必要がある。
資格情報を URL・ログへ露出させず、認証前の接続・処理を制限し、認証した利用者と接続を対応付けられることを確認する。
HTTP Cookie などを利用する場合は、既存の第三者サイトからの不正な接続・操作への対策も維持する。

失効の伝達方式は、通知が一切届かない場合も含めて評価する。
通信分断、時計のずれ、処理中断、再起動、SFU 移行でも、設定した反映期限内に対象の拒否・停止を完了できることを確認する。
保証に必要な時計誤差や処理遅延などの前提を明示し、その前提を確認できない場合の停止条件も定める。
通常どおり通知が届く場合の測定だけでは、期限の保証を確認済みとしない。

各候補は、セキュリティ要件、遅延・処理量、依存先の障害、運用負荷、鍵更新、相互接続性、検証・保守のしやすさで比較する。
実装・運用の複雑さとして、独自に実装する範囲、追加コンポーネントと依存関係、同期・復旧・鍵更新の手順、検証・監視の負担も比較する。
同じセキュリティ要件と機能要件を満たす場合は、独自実装や追加コンポーネントを必要以上に増やさず、理解・検証・保守しやすい方式を優先する。
必要な機能を削除したり、認証・認可の条件や失効の反映期限を緩めたりすることで候補を適合させない。

選定結果には、採用範囲、設定、依存する基盤、成立に必要な条件、確認結果、残る制約を記録する。
方式の選定、数学モデルの検証、実装、統合試験は、それぞれ完了した範囲を記録する。
未採用・未実装・未検証の範囲を、対応済みとして扱わない。
参加 JWT の使用は確定とし、OAuth 2.0、OpenID Connect、トークンの更新・失効・検証方式、サービス認証、具体的な鍵管理基盤・暗号方式・更新間隔は引き続き未確定とする。

## 自作範囲・既存実装の利用

認証連携、認可、資格情報の発行・更新・失効の制御は、TypeScript の C-Plane として実装する。
各プロトコルでの認証と権限の適用は、それぞれのコンポーネントが担う。
論理的な責務の分離と、実行プロセスの分離は同一視しない。

| 実装する部分 | 責務 |
|---|---|
| 外部認証との連携 | 信頼する連携先の設定、認証結果の受け入れ、外部利用者と参加者の対応 |
| 認可 | 対象資源・操作・現在の権限・委任範囲の確認 |
| 参加 JWT の発行・更新 | 発行要求の確認、許可範囲と有効期間の決定、更新結果の管理 |
| 資格情報の検証への組み込み | 用途別の検証設定、対象との対応、現在の権限・失効状態の確認 |
| 権限変更・失効の反映 | 更新順序、通知・再確認、期限管理、適用・停止結果の照合 |
| プロトコルとの連携 | TURN 資格情報の発行、接続・用途との対応、各コンポーネントへの権限伝達 |
| 鍵管理との連携 | 発行・検証に使う鍵の選択、更新、受け入れ停止、漏洩時の復旧 |
| 監査と資源管理 | 必要な操作記録、処理量・保持状態の制限、結果不明からの照合 |

C-Plane は、共通の検証条件と権限情報を管理する。
実際に資格情報を受け入れるコンポーネントは、その用途に必要な検証と認可を適用する。
すべてのコンポーネントが参加 JWT を直接検証することは要求しない。
D-Plane などは、既存仕様に従って C-Plane から受け取った検証済みの権限情報を利用できる。
その場合も、指示元・対象・操作・有効期限・反映済みの失効との対応を確認する。
共通の検証処理は再利用し、各コンポーネントへ不必要に重複実装しない。

外部アプリケーションのログイン、パスワード管理、利用者登録・管理は、既存の認証基盤を利用する。
外部認証基盤の機能を、プラットフォーム内へ重複実装しない。
外部基盤が認証を行っても、プラットフォーム固有の権限と委任範囲の確認は省略しない。

JWT の生成・解析・署名検証、暗号処理、安全な乱数生成には既存ライブラリを利用する。
JWT や暗号アルゴリズムを独自実装しない。
ライブラリが保証する検証と、アプリケーション側で指定・確認する発行元、利用先、用途、対象、期限、権限、失効を区別する。
解析や署名検証の成功だけで、操作を許可しない。

OAuth 2.0・OpenID Connect などを採用する場合も、標準のプロトコル処理には既存実装を利用できる。
採用した実装の設定と、外部利用者・委任範囲・参加権限との対応は、プラットフォーム側で確認する。
これらの方式の採用は、引き続き未確定とする。

鍵の保管、永続化、サービス認証、メッセージ配送、時刻管理、入力検証には、既存のライブラリや基盤を利用できる。
既存基盤が提供する順序・永続性・期限・障害回復の保証と、プラットフォーム側で補う条件を確認する。
同じ要件を満たす場合は、独自実装や追加コンポーネントを必要以上に増やさない。

TURN・ICE・DTLS の認証処理は、各コンポーネントの仕様に従う。
C-Plane に同じプロトコル処理を重複実装せず、利用許可・資格情報・処理結果を対応付ける。
Browser SDK・React SDK に、サーバー側の発行権限や秘密情報を持たせない。

既存実装の内部バッファ、キャッシュ、再試行、鍵取得、照会待ちも資源管理に含める。
ライブラリ自身の制限または組み込み側の制御により、必要な上限と期限を保証する。
失敗時に認証・認可を省略したり、期限切れの情報を使い続けたりする構成を採用しない。

採用する実装・基盤のバージョン、設定、依存機能、検証範囲を記録する。
セキュリティ修正を追跡し、更新時は影響する検証条件を再確認する。
実装と検証は、共通仕様の「実装・検証の共通方針」に従う。

## セキュリティ

認証、権限付与、資格情報の発行・更新・失効、管理操作、状態取得、通知購読に、それぞれ必要な認証・認可を適用する。
認証済みの利用者・アプリケーション・内部サービスでも、対象資源と操作範囲を確認する。
資格情報の発行や権限変更によって、要求元の委任範囲を超える権限を与えない。

参加 JWT は、許可したアルゴリズムと鍵で署名を検証する。
署名のない JWT、許可していないアルゴリズム、不正な署名を受け入れない。
発行元・利用先・用途・対象・権限・有効期限と、現在の利用権限・失効状態を確認する。
使用開始時刻が指定されている場合は、その条件も検証する。
JWT 内のアルゴリズムや鍵の指定だけで、検証側の設定を変更しない。

外部認証の情報、参加 JWT、更新用資格情報、管理用・内部サービス用の資格情報を、別用途として無条件に受け入れない。
資格情報の検証に失敗した場合、別用途として試し直したり、弱い検証条件へ切り替えたりしない。
TURN・ICE・DTLS には、各仕様の認証・検証条件を適用する。

外部入力は、形式・サイズ・値・対象・更新順序を実行時に検証する。
署名済みの情報でも、その発行元が対象の利用者・ルーム・操作を扱えることを確認する。
表示名、メールアドレス、参加者 ID、参加端末 ID の一致だけで、利用者や接続の引き継ぎを許可しない。

鍵取得や外部照会の接続先は、信頼する設定から選ぶ。
資格情報に含まれる URL や識別子を、そのまま任意の外部接続や鍵の取得に利用しない。
外部照会結果にも、対象、用途、期限、失効の条件を適用する。

資格情報の受け渡しと内部通信は、既存の通信保護要件に従う。
ブラウザーの WebSocket API の制約を理由に、資格情報を URL へ含めない。
ブラウザーが自動送信する資格情報を利用する場合は、第三者サイトからの不正な接続・操作を防ぐ。
Origin の確認だけで、利用者認証や操作権限の確認を済ませない。

更新・再発行・再接続では、要求元と対象の現在の権限を確認する。
盗用・失効した資格情報の所持だけで、新しい資格情報や別の参加端末の操作権限を取得させない。
再送や応答の消失を利用して、有効期間や権限を意図せず拡大させない。

失効、鍵の受け入れ停止、接続の引き継ぎが反映済みの場合は、古い資格情報や権限情報で覆さない。
通知の欠落・通信分断・時計のずれ・再起動時の扱いは、「有効期限・権限変更・失効の反映」に従う。
確認不能だけを理由に既存通信を一律に即時停止することは要求しないが、確認済み情報を利用できる期限を超えて継続しない。

鍵の漏洩時は、対象鍵の受け入れ停止、資格情報の失効、利用権限の変更を区別する。
必要な処理と正規利用者の復帰は、「署名・検証と鍵の管理」に従う。
復旧のために、漏洩した鍵や拒否済みの資格情報を再び信頼しない。

C-Plane から受け取った権限情報を利用するコンポーネントは、指示元・対象・操作・期限と、反映済みの変更を確認する。
参加 JWT を各コンポーネントで重複検証することは要求しない。
同一プロセス内の検証が保証する範囲は、「サービス認証と権限の伝達」に従う。

未認証要求、認証試行、資格情報の発行・更新、鍵取得、権限照会、失効通知、結果照合に、処理量・保持状態・待機時間の上限を設ける。
認証済みの要求にも適用し、再試行・重複要求や複数処理の並行実行で上限を回避させない。
過負荷時にも認証・認可を省略せず、失効期限を守るための処理を無制限の待機キューへ蓄積しない。

トークン本体、秘密鍵、共通秘密情報、更新用の秘密情報を、URL・ログ・監査・診断・エラー報告へ出力しない。
Browser SDK・React SDK にサーバー側の秘密情報を渡さず、C-Plane・D-Plane に E2EE の秘密鍵・復号鍵を渡さない。
監査には、要求元、対象、操作、判断結果と、発行・適用・停止の対応を確認するために必要な情報だけを記録する。
監査・状態照会にはアクセス制御と保持期限を適用する。

## 受け入れ条件

外部認証との連携処理、C-Plane、Browser SDK、Signaling、D-Plane を組み合わせて検証する。
通常動作に加え、不正要求、権限変更、通知の欠落・重複・順序逆転、通信分断、時計のずれ、再起動、SFU 移行を発生させ、次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| 外部認証の受け入れ | 設定した連携先と検証条件に従う。認証成功だけで参加・操作を許可しない |
| 利用者の対応 | 異なる認証基盤の同一識別子、同じ表示名・メールアドレスを理由に、利用者を誤って統合・引き継ぎしない |
| 委任範囲 | 外部アプリケーションが扱える利用者・資源・操作・有効期間を確認し、その範囲を超える権限を付与・発行しない |
| 操作別の認可 | 参加・発行・購読・DataChannel・状態取得・通知・管理操作を個別に確認する。自分の参加端末の権限で別の参加端末を操作しない |
| 参加 JWT の署名 | 許可したアルゴリズムと鍵だけで検証する。署名なし、不正署名、アルゴリズムや鍵の取り違えを拒否する |
| JWT の情報と期間 | 発行元・利用先・用途・対象・権限・有効期限を検証する。使用開始時刻がある場合はその条件も確認し、現在の利用権限・失効状態を適用する |
| 資格情報の用途分離 | 外部認証・参加・更新・管理・内部サービス・TURN・ICE の情報を別用途として無条件に受け入れない |
| 更新・再発行 | 現在の権限を確認し、権限や期限を意図せず拡大しない。再試行や応答消失で重複処理や失効の取り消しを起こさない |
| トークンの期限切れ・単体失効 | 新しい認証を拒否する。既存接続の継続は、失効対象と現在の利用権限に従って判断する |
| 通信権限の失効 | 対象の操作・通信を反映期限内に停止する。対象外の許可された通信を不必要に終了しない |
| 失効と処理の競合 | 資格情報の発行・更新・操作実行・送信開始との確定順序を守る。有効期限内の古い情報でも、反映済みの失効を覆さない |
| 通知が一切届かない場合 | 保持情報の有効期間と再確認により、失効の反映期限内に対象通信を停止する。再接続・再試行で期限を延長しない |
| 時計・中断・再起動 | 時計のずれ、処理中断、再起動で期限を数え直さない。必要な状態を確認できなければ、新しい許可・延長・再開を行わない |
| 停止結果の確認 | 通知の送受信と、実際の適用・拒否・通信停止・資源解放を区別する。結果不明を完了と扱わない |
| サービス認証 | 指示元サービス、対象、操作権限、処理結果の対応を確認する。別プロセス間では相互認証と通信保護を適用する |
| 検証済み権限情報の利用 | D-Plane が参加 JWT を直接検証しない構成でも、指示元・対象・操作・期限・変更状態を確認する。毎回の C-Plane 照会を前提としない |
| 通常の鍵更新 | 新旧鍵の切り替えと受け入れ期間を守る。更新や再取得だけで資格情報の期限を延長しない |
| 鍵漏洩と復旧 | 対象鍵の発行・受け入れを停止し、影響する資格情報を無効化する。利用権限の変更は別に判断し、正規利用者は再認証・認可後に新しい資格情報で復帰できる |
| プロトコルとの連携 | STUN の認証不要範囲、TURN の認証・所有者確認・期限切れ方針、ICE 世代、DTLS 相手検証を維持する |
| SFU 移行・担当変更 | 新旧接続・資源と権限情報を区別する。古い資格情報・更新・完了通知で新しい状態を変更しない |
| 外部照会・鍵取得 | 信頼する接続先だけを利用する。入力中の URL・鍵指定で任意の取得先や検証条件へ切り替えない |
| ブラウザーでの認証 | 採用した方式が WebSocket API の制約を満たす。資格情報を URL に含めず、未認証処理を制限し、必要な第三者サイト対策を適用する |
| 資源上限・過負荷 | 未認証・認証済みの要求、並行処理、再試行でも上限を超えない。過負荷を理由に検証や失効期限を緩めない |
| 秘密情報と監査 | 資格情報・鍵・共通秘密情報をログ等へ露出させない。監査で要求・判断・適用・停止の対応を確認でき、アクセス制御と保持期限を守る |

ログアウトでは連携先の設定に従い、既存通話を必ず終了するとはしない。
アカウント停止・明示的な権限失効では、必要な操作・通信が期限内に停止することを確認する。

反映期限の測定は、C-Plane の失効決定から、対象コンポーネントでの拒否・通信停止までを対象とする。
通常の通知経路だけでなく、通知の全欠落と再確認経路の障害を組み合わせて検証する。
時計誤差・処理遅延などの成立条件と、その条件を確認できない場合の停止結果を記録する。
通知の受信や停止要求の受け付けだけで、期限を満たしたとは判断しない。

性能試験は、認証・資格情報の発行・更新・照会の頻度、利用者数、権限情報の有効期間、失効対象数、障害条件を固定して比較する。
処理量、応答時間、失効反映時間、依存先への問い合わせ量、CPU・メモリ・保持状態を測定する。
過負荷時も同じ認証・認可・失効条件を維持する。
合否基準は試験前に定め、測定完了と目標達成を区別する。

検証には、共通の実装・検証方針を適用する。

| 検証方法 | 重点対象 |
|---|---|
| TLA+ によるモデル検査 | 委任範囲、資格情報の発行・更新・失効の競合、保持情報の期限、通知欠落、接続引き継ぎ、再起動と停止完了 |
| Fuzzing | JWT ライブラリへの入力と検証設定、アルゴリズム・鍵の選択、発行元・利用先・用途・対象・期限の確認、検証結果に基づく認可処理。外部入力・照会応答の解析、長さ・境界、不正な用途・対象・時刻 |
| Property-based Testing | 権限変更と通知の操作列、期限判定、更新・再試行、対象の対応、失効後の復活防止、資源計上 |
| 形式的な証明の評価 | 委任範囲を超えない発行、権限の組み合わせ、期限計算、更新順序の不変条件について、Lean 4・Verus・Aeneas の適合性を評価する |

JWT の解析・署名検証には既存ライブラリを使用し、その内部実装を独自に検証し直すことを一律には要求しない。
ライブラリへの入力、検証設定、アルゴリズム・鍵の選択、発行元・利用先・用途・対象・期限の確認、検証結果に基づく認可処理は、プラットフォームの検証対象とする。
既存ライブラリの検証に成功したことだけで、プラットフォーム全体の認証・認可が正しいとは判断しない。

安全性に加え、必要な通信・処理・障害回復の前提の下で、更新・停止・照合・回収が完了する活性を検証する。
モデルの前提と実装・実行環境の対応を確認する。
方式の評価、モデル検査、形式検証、Fuzzing、静的解析、統合試験の結果と保証範囲を区別する。

採用した JWT ライブラリ・署名方式・鍵管理構成と、実際のブラウザー・内部サービスの構成で検証する。
未採用の OAuth 2.0・OpenID Connect・更新方式などを、検証済みとして扱わない。
結果には、バージョン、設定、権限・委任条件、期限、時計・障害条件、負荷、検証範囲と観測結果を記録する。
秘密情報を記録へ含めない。
