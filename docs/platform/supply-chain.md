# サプライチェーン対策

依存関係や開発ツールが侵害されたとき、開発端末や CI で不正なコードが動いたり、本番環境が不正に変更されたりするリスクを抑える。

## 依存関係と CI

CI は pnpm と Cargo のロックファイルを使う。依存を追加・更新する PR では、直接依存と間接依存の取得元、新たに実行されるインストール・ビルドスクリプト、Cargo の手続きマクロを確認する。開発ツールの取得元やバージョンを変更する場合も同じ観点で確認する。

pnpm は、新規に依存を解決するときもロックファイルを検証するときも、公開から 24 時間未満の版と公開時刻が不明な版を拒否する。緊急修正で待機を省く場合は、パッケージ名、バージョン、理由を PR に記載し、レビューを受ける。依存に未審査のインストールスクリプトがある場合は、セットアップを失敗させる。実行を許可する場合は、スクリプトの内容と必要性を確認し、パッケージ名とバージョンを指定する。

外部 Action と外部の再利用ワークフローは、配布元で確認した完全なコミット SHA で固定する。参照を更新する PR では、配布元と実行内容を確認する。Action が実行時に取得するツールは、設定できる場合にバージョンを固定する。

CI は zizmor のオフライン検査で SHA 未固定などの問題を検出する。検査対象の収集には `.gitignore` が適用される。`actions.lock` を導入すると、一部のタグ参照もロック済みとして扱われる。その場合は、完全なコミット SHA での固定を確認する方法を見直す。

## GCP の本番配備

PR 検証、通常 CI、成果物のビルド、検証環境への配備には、本番を変更する権限を付与しない。GCP は Workload Identity Federation でリポジトリ ID、保護されたブランチ、所定のワークフロー、本番環境を確認し、承認済みの配備ジョブにだけ本番用の短期資格情報を発行する。

本番の配備ジョブでは、依存のインストールと成果物の再ビルドを禁止する。配備用と実行用の権限を分ける。認証・承認の条件や、成果物の出所を証明する設定の変更は、配備用の権限では許可しない。

担当者は、検証環境で確認した成果物のダイジェストと、本番に適用する Terraform プランを承認する。本番への反映前に、次の条件を確認する。

- 成果物の出所が所定のビルドと対象コミットに結び付いている。
- 成果物のダイジェストと Terraform プランが承認時のものと一致する。

出所が不明な場合、承認がない場合、承認後に内容が変わった場合は、反映を拒否する。切り戻しにも承認済みの成果物を使う。

## 受け入れ条件

- 現行の依存でローカルのセットアップと CI が通る。新規解決では公開直後の依存を拒否する。セットアップでは未審査のインストールスクリプトを、CI では SHA 未固定の外部 Action と再利用ワークフローを拒否する。
- GCP の初回公開前に、PR 検証、通常 CI、所定外のワークフロー、承認前の配備ジョブが本番用資格情報を取得できないことを実環境で確認する。
- GCP の初回公開前に、承認済みの成果物とプランで配備できることを確認する。出所不明の成果物、ダイジェストの不一致、プランの差し替えが拒否されることも確認する。
