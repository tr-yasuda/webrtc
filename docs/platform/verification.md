# 実装・検証方針と性能評価

## 実装・検証の共通方針

正確性と保守性を重視し、コンポーネントの性質と失敗時の影響に応じて検証方法を選定する。
すべての関数に一律の形式検証を要求しない。

状態遷移、並行処理、認可、資源の確保・解放、鍵更新などには、TLA+ によるモデル検査を積極的に利用する。安全性を検証し、必要に応じて活性も検証する。活性を検証するときは、その成立に必要な実行の公平性、通信、障害回復などの前提を明示する。

数学的な不変条件やアルゴリズムの正しさを確認するため、Lean 4 などによる形式的な証明を検討する。
Rust 実装との対応を検証する手段として、Verus・Aeneas なども評価する。
これらの具体的な採用は、対象への適合性を確認して決定する。

パケット解析、状態遷移、入力検証などには、Fuzzing と Property-based Testing を利用する。
正常系だけでなく、異常入力、境界値、通知の欠落・重複・順序逆転、並行処理を重点的に検証する。

TypeScript と Rust の型検査・静的解析は、可能な範囲で厳格に設定する。
警告の抑制や検査の無効化を安易に認めない。
例外が必要な場合は、必要性、適用範囲、根拠を明確にする。

不要な抽象化、重複実装、過剰なファイル分割、意味のないコメントやドキュメントを増やさない。
呼び出し元から、主要な判断、実行順序、副作用、結果、失敗時の扱いを追えるようにする。
振る舞いと変更理由を追えるようにし、コードから読み取れる処理の言い換えをコメントとして増やさない。

検証結果は、次を区別して記録する。

| 検証方法 | 明示する範囲 |
|---|---|
| 数学モデルの検査 | モデル化した状態・遷移、検査した性質、状態空間の制限と実行上の前提 |
| 数学的な証明 | 証明した命題、定義、使用した公理・仮定と未証明の事項 |
| 実装コードの形式検証 | 対象コード、契約、検証した性質、検証対象外の処理と信頼する部分 |
| Fuzzing・Property-based Testing・その他のテスト | 入力・操作列の範囲、判定条件、実行条件と結果 |
| 静的解析 | 対象コード、適用した検査、設定、警告抑制や無効化した検査 |

各検証では、対象要件、前提、検証範囲、対象外とその理由を明示する。検証ツールが成功を報告した場合も、数学モデル、証明、検証コード、設定を点検し、対象要件が実際に評価されたことを確認する。例えば、事前条件が成立せず検証対象に到達できなかった場合や、判定が無効だった場合は、対象要件を評価したことにはならない。

数学モデルを使った場合は、モデルの状態・遷移が実装のどの処理に対応するかを確認する。モデル検査や証明の成功だけで実装の正しさを判断しない。

- TLA+ のモデル検査では、仕様に必要な状態・遷移と、検証する性質に関係する並行処理・障害条件をモデルが表現しているかを確認する。検査の前提と設定の下で、必要な遷移に実際に到達できることも確かめる。
- Lean 4 などの証明では、公理・仮定の必要性と適用範囲を確かめる。不要な公理や結論を先取りする仮定によって証明を成立させず、未証明の事項は証明済みとして扱わない。
- テストでは、入力生成、期待結果、判定条件、検査設定を対象要件と照合する。必要な処理に到達し、その結果を判定条件で実際に評価していることを確かめる。

形式検証や静的解析を通過させるために、本来必要な機能・セキュリティ要件を削除したり、検証対象を不当に狭めたりしない。
検証対象や前提を限定する場合は、その制約を明示し、範囲外の要件を検証済みとして扱わない。

検証を選定したら、CI で再現・継続実行できる構成を重視し、実行時間に応じて変更時または定期実行に振り分ける。実行時は、ツールのバージョン、設定、実行範囲、再現に必要な条件と結果を記録し、未実行・時間切れ・検証不能はその状態を明記する。仕様・モデル・実装・検証設定を変更した場合は、影響する検証と対応関係を再確認する。

## 収容人数・品質・受け入れ条件

1 ルームの同時参加人数は 100 人を目標とし、次の試験条件で発行・購読・暗号化の条件を固定して収容人数を測定する。

| 項目 | 条件 |
|---|---|
| 参加者数 | 100 人 |
| 音声・カメラ映像 | 全員が同時に発行 |
| カメラ映像 | 720p・30 fps |
| 映像の購読 | 各参加者が他の 9 人を購読 |
| 画面共有 | 1 人が 1080p・15 fps で発行し、他の全員が購読 |
| E2EE | 音声・映像・DataChannel で有効 |

この条件は性能測定の基準とする。
製品としての購読数や画面共有数の上限は、SFU の仕様で定める。

測定では、CPU・メモリ・送受信帯域、音声・映像の遅延と欠落、切断回数を記録する。結果には、サーバー構成、参加端末・ブラウザー、コーデック、ビットレート、音声の購読数、DataChannel の通信量、TURN 経由の割合を添える。100 人に届かない場合も、同じ条件で収容できた人数を記録する。

Chrome・Firefox・Safari 間の送受信を確認する。
DTLS 1.2 と 1.3 は、それぞれ対応する接続相手との試験を行う。

SFU 移行の試験では、暗号化を維持して切り替えられることと、退役期限で自動再接続することを確認し、移行中の音声・映像の中断時間と DataChannel の欠落・重複を測定する。各測定値は、コンポーネントごとの受け入れ条件で合否を判断する。

## D-Plane のプロセス・IPC・復旧

D-Plane の詳細な受け入れ条件は、[D-Plane のプロセスモデルと IPC 境界](dplane.md#受け入れ条件)に従う。統合試験では、少なくとも次を確認する。

| 試験対象 | 確認する結果 |
|---|---|
| プロセスの独立 | Node host の終了で TURN プロセスと SFU Worker が道連れにならず、停止後のプロセスが残らない |
| Node host 再起動 | 生存する Worker のメディアが継続し、新しい Node host がスナップショットとイベント境界から制御を引き継ぐ。古い制御接続のコマンドを実行しない |
| TURN の常駐 | Node host 再起動後も TURN リスナーと既存 Allocation が継続し、Allocation は Allocate 時にだけ確保される |
| TURN の Orphaned | 制御接続が切れたら新規 Allocate を拒否し、既存 Allocation は期限まで継続する。orphan timeout で停止する |
| 同一 epoch の再接続 | 同じ `controllerId` の IPC 再接続を受け付け、古い `controlSessionId` のコマンドを拒否する |
| Worker 再起動 | 影響 Room が再配置され、クライアントが再接続する。ICE / DTLS の状態を復元済みとして扱わない |
| Signaling 再起動 | DB にない Room を即座に閉じず、`assignmentVersion`、`commandId`、所有状態の照合後に孤児を確定する。Quarantine 中は既存メディアを継続し、新規参加と Transport 作成を拒否する |
| Orphaned の認可 | 既知の認可期限が orphan timeout より早い場合はその時点で停止し、期限到達で全メディアを停止する |
| Worker の idle と縮退 | Room 0 かつ予約 0 で 30 秒後に停止し、新規 Room で停止をキャンセルする。Worker 数を 0 にできる |
| 容量予約の競合 | 予約済み容量を含む空き枠 1 に対する同時 Room 作成で、確保が 1 件だけになる |
| 統計の欠測 | バッファ溢れで集計を黙って破棄せず、圧縮または欠測期間を記録する。Signaling は欠測を 0 として扱わない |
| IPC の境界 | メディアパケットと DataChannel 本文が IPC に流れず、UDS が公開ネットワークに露出しない |
