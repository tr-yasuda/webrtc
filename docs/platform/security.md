# 共通のセキュリティ条件

認証・認可・資格情報に共通する条件は、[認証・認可・資格情報](../auth/authorization.md)で定める。

アプリケーションは、参加を許可するルーム・参加者・操作をサーバー側で指定し、権限の発行や管理に使う秘密情報はブラウザーに渡さない。C-Plane は認証を行い、指定された権限を確認する。D-Plane は許可された接続と操作だけを受け付け、SFU を移行するときも移行先に同じ権限を適用する。

## セキュリティ契約の正本

機械的に判定できる条件の正本は、`specs/security/contract.json` とその JSON Schema に置く。
TypeScript と Rust のプロファイル、秘密分類、出力許可条件、監査イベント種別は、契約から生成するかビルド時に一致を検証する。手書きで同じ条件を定義しない。

この文書は、契約の意味、脅威モデル、適用条件、例外、失敗時の扱いを説明する。列挙値やプロファイルの値をここで再定義しない。

コンポーネント登録簿は `specs/security/components.json` に置く。登録簿、適用除外、検証ルール、セキュリティ実装の変更は、`security-contract-change` ラベルがない PR を CI で失敗させ、通常の実装変更と区別してレビューする。

未知の契約バージョン、契約欠落、スキーマ不一致では、既定値へフォールバックせず、新規のセキュリティ判定を拒否する。

## セキュリティ最低基準

### TLS

TLS 1.0 と TLS 1.1 は使用しない。

| 経路 | バージョン | 要件 |
|---|---|---|
| `public-control` | TLS 1.2 以上。TLS 1.3 を優先 | AEAD と ECDHE のみ。接続先の証明書とホスト名を検証する。平文へフォールバックしない |
| `internal-service` | TLS を使う場合は TLS 1.3 | ECDHE と AEAD。相互のサービス認証は方式選定で決める。mTLS を前提にしない |
| `turn` の TLS | TLS 1.2 以上 | TURN の利用認証を別に要求する。TLS 接続だけで中継を許可しない |

TLS 1.2 では、CBC、RSA 鍵交換、NULL 暗号、圧縮、安全でない再ネゴシエーションを使用しない。セッション再開はサーバー発行のチケットに限定し、再開後も元の認証済み主体を維持する。

TLS 1.3 では、鍵交換に ECDHE を使用し、X25519・secp256r1・secp384r1 の範囲で設定する。静的 RSA 鍵交換は使用しない。

TLS 1.3 の PSK は、内部サービス認証の方式選定で明示的に設定された場合だけ使用する。セッション再開では `psk_dhe_ke` を使い、前方秘匿性を維持する。認証を省略する PSK 単独の鍵交換は制御 API に使用しない。

`public-control` では外部 PSK を使用しない。セッション再開の PSK だけを、サーバー発行チケットと元の認証済み主体の維持を条件に許可する。

制御 API では 0-RTT を使用しない。将来、冪等なデータ通信に限って 0-RTT を検討する場合も、別プロファイルと再生攻撃対策を定義する。

### DTLS

DTLS 1.0 は使用しない。DTLS 1.2 と 1.3 に対応し、接続の双方が 1.3 に対応している場合は 1.3 を優先する。
DTLS 1.3 を利用できない相手との接続でも、暗号・証明書の検証条件を緩めない。

到達性確認、ハンドシェイク、断片再構成、再送、KeyUpdate の条件は、[共通 DTLS 仕様](../dtls/association.md)で定める。

## 通信プロファイル

通信は次のプロファイルで保護する。必須制御と禁止するフォールバックの値は `specs/security/contract.json` を正本とする。

| プロファイル | 通信 | 必須の保護 |
|---|---|---|
| `public-control` | Browser SDK・管理 UI・アプリケーションと C-Plane | TLS 1.2 以上、TLS 1.3 優先、AEAD / ECDHE、接続先検証、平文フォールバック禁止、制御 API の 0-RTT 禁止、外部 PSK 禁止 |
| `internal-service` | Management・Signaling・Node host 間の直接通信 | 相互のサービス認証、暗号化、TLS を使う場合は TLS 1.3。方式は内部サービス認証の方式選定で定める |
| `dplane-ipc` | Node host と TURN / SFU Worker | UDS、公開ネットワーク非待受、runtime directory、専用 UID・GID、ファイル権限、peer credential |
| `turn` | TURN クライアントと TURN サーバー | TURN 利用認証、TLS 1.2 以上、DTLS 1.2 / 1.3、DTLS 1.3 優先、認証なし Allocation の拒否 |
| `webrtc-media` | ブラウザーと SFU の音声・カメラ映像・画面共有 | DTLS-SRTP、証明書フィンガープリント照合、DTLS 1.3 優先、SFrame E2EE、E2EE 鍵を C-Plane・D-Plane に渡さない、SFU 移行でカウンターを巻き戻さない |
| `webrtc-data` | ブラウザーと SFU の DataChannel | DTLS 1.2 / 1.3、DTLS 1.3 優先、証明書フィンガープリント照合、DataChannel 本文の E2EE、E2EE 鍵を C-Plane・D-Plane に渡さない |
| `stun-binding` | 単独 STUN Binding | 認証不要の Binding を明示的な例外として許可し、制御経路や TURN の認証へ流用しない |

`webrtc-media` は DTLS-SRTP と SFrame を別の保護層として扱う。どちらか一方の成功で他方を省略しない。
音声・カメラ映像・画面共有には RFC 9605 の SFrame を適用し、DataChannel の本文は [DataChannel 本文の保護](../e2ee/data.md#datachannel-本文の保護)に従う。復号鍵は C-Plane・D-Plane に渡さない。

Node host と D-Plane の UDS のプロセス分離、ファイル権限、peer credential は [D-Plane のプロセスモデルと IPC 境界](dplane.md#プロセス分離と制御ソケットの権限)に従う。

UDS は同一ホスト内の制御経路であり、TLS を要求しない。将来、Node host と D-Plane を別 VM に分ける場合は `dplane-remote` などの別プロファイルを定義し、相互認証と暗号化を要求する。

通信プロファイルの設定・適用宣言の検証と、実際に保護が適用されていることの検証は別である。
設定検証は共通セキュリティ契約の準拠検証で行い、実接続の検証は各コンポーネントの結合試験で行う。

## 秘密情報の分類と出力境界

秘密情報は、少なくとも次の分類で扱う。

| 分類 | 例 |
|---|---|
| 認証情報 | 参加 JWT、ID token、Management API credential、ApplicationSigningKey、TURN / ICE 資格情報、サービス認証の資格情報 |
| 鍵素材 | E2EE の秘密鍵・復号鍵、DTLS の秘密鍵、SRTP/SRTCP の鍵、DTLS Cookie の生成秘密、SCTP State Cookie |
| 本文 | 音声・映像・DataChannel の本文、パケット全体 |
| 制御情報 | SDP や受信メッセージ全文など、認証情報を含み得るもの |
| 識別情報 | 出力してよい ID と、個人情報として扱う情報 |

秘密情報を、通常の文字列、JSON、ログ、監査、公開エラー、URL へ直接渡さない。

出力境界は、ログ、監査、公開エラー、URL、診断、テスト結果を区別する。各境界は許可した型と属性だけを受け付け、任意のオブジェクトや例外を直接受け付けない。

秘密情報の保護は、次の保証手段を分けて扱う。

| 保証手段 | 保証すること | 保証しないこと |
|---|---|---|
| 型システム | 安全なコードで秘密型を通常の出力型へ渡せないこと | `any`、型アサーション、`unsafe`、FFI、第三者ライブラリ内部の迂回 |
| 実行時検証 | 暗黙の文字列化・シリアライズ・検査出力が伏字または例外になること | 明示的に取り出した後の値の追跡 |
| 静的解析 | 許可されていない出力境界でのログ API 使用、許可外の秘密値取り出し | すべての動的な迂回 |
| 出力境界 | 第三者ライブラリのエラーや未知の入力が安全な型へ変換されること | アプリケーションが境界を迂回した場合 |

redaction は、未知のデータや第三者ライブラリの出力に対する最後の防衛線として使う。redaction だけで秘密情報の非出力を保証したとは扱わない。

明示的な秘密値の取り出しは、暗号処理やプロトコル処理の必要な箇所に限定する。取り出した値をログ・監査・公開エラーへ渡さない。

例外処理では、元の例外、スタック、入力値を公開エラーやログへ直接含めない。内部原因は相関 ID で参照し、必要な場合だけアクセス制御された診断境界を通す。

## 認可判定と監査

認可判定と、認可後の操作結果は別のイベントとして記録する。

| イベント | 意味 | 主な項目 |
|---|---|---|
| 認可判定 | ポリシーが操作を許可したか拒否したか | 実行者、操作、対象、許可／拒否、理由、認可判定 ID、相関 ID |
| 操作結果 | 認可後の操作が成功・失敗・結果不明のどれか | 実行者、操作、対象、結果、理由、認可判定 ID、相関 ID |
| リクエスト拒否 | 認証・入力検証など、認可判定より前の拒否 | 段階、理由、対象、実行者または不明、相関 ID |
| 資源監査 | 資源の状態・計数の変更 | 資源 ID、状態変更、計数、操作 ID（ある場合）、相関 ID |

認可判定の許可を操作成功として扱わない。認可拒否を操作失敗として扱わない。操作結果が記録されていない場合、成功を推測しない。

監査イベント ID、操作 ID、認可判定 ID、相関 ID は次のように区別する。

| ID | 意味 |
|---|---|
| 監査イベント ID | 監査レコードを一意に識別する ID。イベントごとに一意 |
| 操作 ID | 要求またはコマンドを識別する ID。再送・冪等性・結果照合に使う |
| 認可判定 ID | 認可判定を記録した監査イベントの ID。操作 ID とは別 |
| 相関 ID | 要求、認可判定、操作結果、資源監査を横断して対応付ける ID。認可判定そのものではない |

監査レコードは共通エンベロープを持ち、認可判定、操作結果、リクエスト拒否、資源監査を payload として区別する。資源監査の保存先・トランザクション・保持期間は資源監査の責務として残す。

`AuthorizationDecision` は認可ポリシーの結果として扱い、実行者は監査エンベロープで組み合わせる。判定関数から実行者を推測しない。

監査レコードは種別ごとに許可されたフィールドと型だけを受け付ける。未知の種別、余剰フィールド、別種別のフィールド、型の合わない値は拒否する。許可フィールドと型は `specs/security/contract.json` の `audit.eventKinds[].fieldTypes` を正本とし、拒否理由に入力値や任意キーを含めない。

監査には、秘密情報、本文、要求全体、SDP、IP アドレス、認証情報、氏名、メールアドレスを含めない。資源監査の `scope_ref` など、既存の保護された参照を使う。

## 入力検証

入力検証の責務は、処理段階ごとに分ける。すべての境界に同じ上限を要求しない。

| 段階 | 主な責務 | 上限・強制方法 |
|---|---|---|
| パース前 | フレーム、メッセージサイズ、読み取り時間、同時接続、バックプレッシャー | 受信前にバイト数・接続数・待機時間を制限する |
| パース中 | 構文、長さ、整数オーバーフロー、深さ、件数、文字列長、未知フィールドの方針 | 線形時間の解析、割り当て前の上限検査、協調的なキャンセル |
| パース後 | 対象・状態・意味の検証、認可入力の整合 | 候補数、入れ子、参照数、処理量を制限する |
| 展開・再構成中 | 圧縮展開、断片再構成、順序待ち | 展開後・再構成後のバイト数、比率、断片数、メモリ、時間を制限する |
| 処理実行中 | 操作の実行、キュー、同時処理、レート | キュー長、同時数、レート、期限を制限する。CPU 律速処理はワーカー／プロセス分離または協調的キャンセルを使う |

処理時間の上限は、実行時に強制できる方式とともに定義する。TypeScript はタイムアウト、キャンセル、ワーカー／プロセス分離、Rust はタイムアウト、キャンセル、プロセス分離などを使う。強制できない場合は、入力サイズ・件数・同時数の上限で代替する。

エラーのフィールドパスは、スキーマで定義されたフィールド名と配列インデックスだけを使う。外部入力の任意キーをそのまま含めず、未知のキーは固定のプレースホルダーに置き換える。パスの長さにも上限を設け、入力値や秘密情報を含めない。

## 保証範囲

共通セキュリティ契約は、機械可読契約、TypeScript と Rust の共通実装、共有テストベクター、準拠検証キット、参照・負のフィクスチャを保証する。

共通セキュリティ契約は、実際の TLS 終端、証明書運用、IDaaS、参加 JWT、サービス認証、UDS の OS 権限、TURN / DTLS / SRTP / SCTP / SFrame のプロトコル実装、監査保存を保証しない。これらは各コンポーネントの結合試験と実行環境で保証する。

設定・適用宣言の検証は、実際の保護が適用されていることの証明ではない。有限回の PBT、Fuzzing、静的解析も、全入力に対する証明ではない。検証範囲と未検証範囲を記録する。
